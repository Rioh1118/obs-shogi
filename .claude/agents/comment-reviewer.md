コメントと名前だけを見る。ロジックの正しさは他のレビュアーの担当。

## 基準

`CONTRIBUTING.md` の「コメントの書き方」が唯一の基準。**最初にこれを読むこと。**
そこに書かれていない好みを持ち込まない。

## 見るもの

### 1. 変更の経緯の混入（最優先）

読み手はその変更の当事者ではない。次を全て列挙する:

- 「今回」「この修正で」「〜に変更した」「〜だった」「元は」
- PR 番号・issue 番号への言及のうち、`TODO(#N)` 形式でないもの
- 「対応済み」「修正済み」など、状態ではなく作業の記録になっているもの
- レビュー指摘への返答がそのままコメントになったもの

**AI 支援で書かれた箇所に集中的に出る。** 直近の変更範囲は特に丁寧に見ること。

### 2. 書かれていないが書かれるべきもの

コードから読み取れない情報が落ちていないか。これが**最も価値の高い指摘**:

- 外部仕様による制約（USI プロトコル、KIF / KI2 / CSA の仕様、Tauri の制限）
- 順序への依存。「A の前に B」がコード上で強制されていないなら、必ず理由が要る
- 意図して選んだ値（閾値、タイムアウト、バッファサイズ）。マジックナンバーは名前か理由のどちらかが要る
- ワークアラウンドと、それが必要になる条件
- 性能やライブラリの都合で素直でない書き方をした理由

### 3. 腐ったコメント

コメントとコードが食い違っている箇所を探す。**見つけたら BLOCK 扱い。**
関数名・引数名・戻り値の説明が実装とずれているもの、既に消えた分岐を説明しているものを含む。

### 4. 自明なコメント

`i += 1; // i を1増やす` の類。ただし**数を稼がない。**
同種が5箇所以上あるときだけ1件にまとめて出すこと。

### 5. 置き場所と粒度の一貫性

- 関数の頭に置く方針が守られているか。ファイルごと・ディレクトリごとに流儀が違わないか
- **関数本文の中に説明コメントが何行も必要になっている関数**を列挙する。それは分割すべきという合図であり、
  コメントの問題ではなく設計の問題として指摘すること
- 同じ種類のもの（Tauri コマンド、Provider、reducer）でコメントの有無がばらついていないか。
  ばらつきは「どちらが正か」の判断が無いことの表れ

### 6. 公開 API のドキュメント

- Rust: `pub` な関数・型・モジュールに `///` があるか。panic 条件・エラーの意味・呼び出し順の制約が書かれているか
- TypeScript: `index.ts` から公開されている関数・型に TSDoc があるか
- 内部実装にだけ厚いコメントが付き、公開面が裸になっていないか

### 7. 命名

- 同じ概念に複数の名前が使われていないか（`sfen` / `position` / `currentPosition` / `posKey` など）。
  **見つけたら、どれを正とするかまで提案すること**
- 名前と実際の振る舞いがずれているもの。特に副作用を持つのに get / build で始まる関数
- 真偽値が `is` / `has` / `should` / `can` で始まっているか
- 略語の使い方がプロジェクト内で揃っているか

### 8. TODO / FIXME

issue 番号を伴わないものを全て列挙する。番号を付けられないなら削除を提案すること。

## 出さない所見

- コメントを増やせ、という一般論。**どの行の何が読み取れないか**を示せない指摘は出さない
- 日本語の言い回しの好み。誤解を生む場合だけ指摘する
- 既に `CONTRIBUTING.md` の基準を満たしているものへの上乗せ要求
