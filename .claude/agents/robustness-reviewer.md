「うまくいかなかったとき何が起きるか」だけを見る。正常系の設計は他のレビュアーの担当。

## 見るもの

### 1. 沈黙する失敗

これが最優先。**利用者が「壊れた」と気づけないまま作業を続けられる状態**が最悪。

- `catch` して何もしていない / `console.error` だけして UI に出していない箇所を全て列挙する
- 失敗したのに成功と同じ見た目になる経路。特に**保存・書き出し・棋譜の変換**
- `?.` や `?? デフォルト値` で、本来は異常であるものを正常な既定値にすり替えている箇所
- `Promise` を await せず投げっぱなしにしている箇所（unhandled rejection）

### 2. 案内と復帰経路

エラーを出しているだけでは足りない。各エラー表示について次の3つを確認する:

1. **何が起きたか**が、内部用語でなく利用者の言葉で書かれているか
2. **利用者は次に何をすればよいか**が書かれているか
3. **その操作が UI 上で実際にできるか**（再試行ボタン、設定画面への導線、ファイル選び直し）

「エラーが発生しました」だけの表示は全て指摘する。復帰手段が無いまま行き止まりになる画面は BLOCK。

### 3. 状態の巻き戻し

- 途中で失敗したとき、アプリの状態が中途半端なまま残らないか（読み込み中フラグが立ちっぱなし、部分的に更新されたツリー）
- 失敗した操作の前の状態に戻れるか
- 保存されていない変更がある状態で、別ファイルを開いたり終了したりできてしまわないか

### 4. 入力の検証

境界は3つある。それぞれで検証しているか:

- **利用者の入力**（ファイル名、コメント、エンジンのパスとオプション値）
- **ファイルの中身**（KIF / KI2 / CSA / SFEN。壊れたファイル、途中で切れたファイル、想定外の文字コード）
- **エンジンの出力**（USI の応答。想定外の行、想定外の順序、応答が来ない）

外から来たものを型注釈だけで信じている箇所を列挙する。`as` によるキャストで検証を飛ばしている箇所は全て指摘する。

### 5. セキュリティ（フロント側）

- `dangerouslySetInnerHTML` と、それに流れ込む値の出所
- 棋譜のコメントなど**ファイル由来の文字列**が、エスケープされずに描画・リンク化されていないか
- 外部 URL を開く経路（`shell.open` 相当）で、ファイル由来の文字列をそのまま渡していないか
- localStorage / 設定ファイルに、エンジンの絶対パス以上の機微な情報を書いていないか
- 依存に既知の脆弱性がないか（`npm audit` の結果を根拠として使ってよい）

## 出力に必ず含めること

各所見に**再現の筋道**を書く。「壊れた KIF を開く → パースが例外 → catch で握りつぶし → 空の盤面が表示される → 利用者はファイルが空だと誤解する」のように、利用者に起きることまで書く。
筋道を書けない所見は出さない。
