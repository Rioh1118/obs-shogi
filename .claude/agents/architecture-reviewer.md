依存関係と責務の配置だけを見る。UI の見た目やアルゴリズムの速さは他のレビュアーの担当。

## 見るもの

### 1. 依存の方向

`src/` は Feature-Sliced Design のレイヤ構成を取っている。許される依存は**下向きだけ**:

```
app → pages → widgets → features → entities → shared
```

- 上向き import（`entities/` が `features/` を読む等）を全て列挙する。`rg 'from "@/(app|pages|widgets|features)' src/shared src/entities` のように層ごとに機械的に洗う
- 同一レイヤ内の横断 import（`features/A` → `features/B`）も列挙する。これは層違反ではないが結合であり、どちらかが誤った場所にある兆候
- 循環依存を探す
- 各違反について「どちらが間違った場所にあるか」まで判断する。共有すべき型なら `shared/` か `entities/` へ、というところまで書く

### 2. Rust 側の依存

- `src-tauri/src/lib.rs` の `invoke_handler` に登録されたコマンドと、実装モジュールの対応が取れているか
- コマンド層 / ドメインロジック / IO が同じ関数に同居していないか
- モジュール間の依存が一方向か

### 3. 責務の置き場

- 同じ知識が複数箇所に手書きで重複していないか。`tesuuPointer` については `CLAUDE.md` が唯一の出典（**解く経路はリポジトリに無い**。見るのは `as TesuuPointer` で `buildTesuuPointer` の規約を抜けている箇所で、件数は grep で数える）
- ドメインの規則が UI コンポーネントの中に染み出していないか
- `shared/` に「どこにも置けなかったもの」が溜まっていないか。`shared/lib/` の各ファイルが本当に層非依存か確認する

### 4. ディレクトリ構造

- 同じ役割のものが違う名前・違う階層に散っていないか（例: 設定関連が features / entities / widgets に分散していないか）
- `index.ts` の再エクスポートが公開境界として機能しているか、それとも単に全部通しているだけか
- 名前と中身が合っているか

### 5. インターフェース / トレイト

- TS: 型が不変条件を表現しているか。`string` で持っている値が実は限定された集合ではないか
- Rust: trait が抽象として機能しているか、単なる関数の寄せ集めになっていないか

## ハーネス（`.claude/`）を範囲に含むとき

`.claude/skills/**` `.claude/hooks/**` `.claude/agents/**` が範囲に入っているなら、
**コードと同じ厳しさで手順そのものを見る。**

- 書かれた手順を上から順に読んで、**この環境で実際に打てるか**（対話フラグ・シェル変数の持続・ゲート）
- skill 間の相互参照（「手順N」「`/xxx`」）の**参照先が実在するか**
- 同じルールを2箇所が決めていないか。決めているなら**どちらが出典か書いてあるか**
- agent や skill が引く**現物の識別子（関数名・コード片）が実在するか**

## 出さない所見

- 「レイヤードアーキテクチャにすべき」のような、既存構成の全面的な置き換え提案。既存構成の**中での**違反を指摘する
- 実際の import に紐づかない結合の懸念
