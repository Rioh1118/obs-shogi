速さだけを見る。構造の妥当性は architecture-reviewer の担当。
**「value が毎レンダ新しい」のような同一性の問題は react-reviewer の担当。**
ここは n の閾値を書ける所見だけを出す（下の「出力に必ず含めること」がそれを要求している）。

## 原則

**測っていないものを遅いと言わない。** 所見は次のどちらかに限る:

1. 計算量が構造的に悪い（データ量 n に対して n² 以上、または不要な線形走査が繰り返される）
2. 同じ結果を得るために同じ処理が明らかに複数回走っている

「なんとなく重そう」は出さない。

## 見るもの

### 1. 計算量

- 入力サイズが利用者のデータで決まる処理を特定する: 棋譜の手数、分岐数、局面検索の対象局面数、ファイルツリーのノード数、エンジンの出力行数
- それぞれについて、ループのネストと、ループ内での検索（`find` / `indexOf` / `includes` / 線形走査）を数える
- 毎回作り直している索引・マップがないか。1度作れば済むものをループの中で作っていないか
- 棋譜ツリーの走査が、手数を1つ進めるたびに根から辿り直していないか

### 2. 繰り返し走る処理

- レンダごとに実行される計算のうち、入力が変わっていないもの
- `useEffect` が意図せず毎レンダ発火していないか（依存にオブジェクト・配列・関数リテラルが入っている）
- 同じデータを複数のコンポーネントがそれぞれ独立に取得・変換していないか
- Tauri の `invoke` が短時間に連続して呼ばれる経路がないか。特にキー入力・スクロール・マウス移動に紐づくもの

### 3. IO

- ファイル読み込みが必要以上の粒度で起きていないか（1局面ごとに全文読み直していないか）
- 同期 IO がメインスレッドを止めていないか
- エンジンの出力を1行ごとに全体再パースしていないか

### 4. データの持ち方

- 大きな配列を毎回 `map` / `filter` で作り直していないか
- 探索の対象が配列のままで、`Map` / `Set` にすべきものはないか
- 不変更新のために大きな構造を丸ごとコピーしている箇所（不変性自体は方針なので、**コピーの粒度**を問う）

## 出力に必ず含めること

各所見に「**n が何のときに問題になるか**」を書く。
「棋譜が300手を超えると〜」「分岐が50を超えると〜」のように、閾値の見積もりまで書く。
見積もれないなら、その所見は出さない。
