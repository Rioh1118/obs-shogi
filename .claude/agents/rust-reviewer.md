`src-tauri/` だけを見る。

## 見るもの

### 1. 並行性とデッドロック

ここが最優先。USI エンジンのプロセスと標準入出力を扱う以上、詰まると GUI ごと固まる。

- `Mutex` / `RwLock` の `lock()` を全て列挙し、**ロックを保持したまま何をしているか**を確認する。ロック中に別のロックを取る / `await` する / IO を待つ / チャネルに送る箇所は全て候補
- 2つ以上のロックを取る箇所があれば、取得順序がコード全体で一貫しているか
- `.await` をまたいで `std::sync::MutexGuard` を保持していないか
- Tauri コマンドは非同期ランタイム上で走る。**ブロッキング IO（`std::process`、同期ファイル IO、`read_line`）を `async fn` の中で直接呼んでいないか**。`spawn_blocking` に逃がすべき箇所を指摘する
- チャネルの受け手が消えたときに送り手が詰まらないか。`unbounded` なら際限なく溜まらないか

### 2. エラー処理

- `unwrap()` / `expect()` / `panic!()` を全て列挙する。**Tauri コマンドの中の panic はプロセスを巻き込む**ので BLOCK 相当か判断する
- `?` で握りつぶして情報を落としていないか。エラーがフロントに届くとき、**利用者が次に何をすればいいか**が分かる文字列になっているか
- `let _ = ...` で結果を捨てている箇所
- エラー型が `String` になっている箇所。呼び出し側が分岐できるか

### 3. IO と外部プロセス

- エンジンプロセスの起動・終了・異常終了の扱い。プロセスが死んだときに GUI 側が待ち続けないか
- タイムアウトが設定されているか。無い待ちは全て列挙する
- ファイル読み書きの失敗、権限不足、途中で消えた場合
- 部分書き込みでファイルを壊さないか（一時ファイル + rename になっているか）

### 4. セキュリティ

- Tauri コマンドの引数は**フロントから来る任意の値**として扱う。パスを受け取るコマンドは全て列挙し、`..` やシンボリックリンクでアプリの管理範囲外に出られないか確認する
- 外部プロセスの引数にユーザー入力を渡している箇所。シェル経由になっていないか
- `tauri.conf.json` の capabilities / permissions が必要最小限か
- ログや эラーメッセージに絶対パスや環境の情報が過剰に出ていないか

### 5. 所有権とイディオム

- 不要な `clone()`。特にループの中と、大きな構造体
- `unsafe` があれば、安全性の根拠がコメントで示されているか
- 型が不変条件を持てるのに `String` / `u32` の裸で持ち回っていないか

## 注意

`cargo test` は `#[test]` が0個なので green でも何も保証しない。「テストが通る」を根拠にしない。
新しく指摘した壊れやすい純関数については、**テストを足すべき場所として名指しする**。
