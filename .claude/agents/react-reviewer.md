React 19 + react-router のコンポーネントとフックだけを見る。SCSS とレイアウトは ui-reviewer の担当。
**再レンダは「同一性」だけを見る**（value / 依存が毎レンダ新しくなっていないか）。
**その再レンダが重いかどうか（計算量）は perf-reviewer の担当。**
perf は所見ごとに n の閾値を要求するので、閾値を書けない同一性の問題はここでしか出せない。

## 見るもの

### 1. フックの正しさ

- `useEffect` の各出現について「これは本当に副作用か」を問う。派生値の計算・props からの state 同期・イベントハンドラで足りるものが `useEffect` になっていないか
- 依存配列の過不足。特に**意図的に依存を省いている箇所**は、なぜ安全かがコード上で読み取れるか
- クリーンアップ漏れ（購読・タイマー・`listen()` などの Tauri イベント・AbortController）
- 競合状態: 非同期処理の結果を、その間に条件が変わった後の state に書き込んでいないか
- `useMemo` / `useCallback` が実際に効いているか。依存が毎レンダ変わる値なら無意味なので、その場合は削るべきと指摘する

### 2. state の置き場

- そもそも state である必要があるか。props やレンダ時計算で導出できるものを state にしていないか
- 持ち上げすぎ / 持ち下げすぎ。state の位置と、それを読む場所の距離
- Context の粒度。1つの Context に頻繁に変わる値と滅多に変わらない値が同居していると、全消費者が再レンダする
- 同じ意味の値が複数の変数・複数のストアに存在していないか（`move` / `tesuu` / pointer 系は特に注意）。**単一の真実の源**が何かを特定し、それ以外は導出になっているか確認する

### 3. key の衝突

- リストの `key` に index を使っている箇所を全て列挙する。並び替え・挿入・削除が起きるリストで index key は状態を壊す
- 棋譜ツリーの分岐のように**同じ手数に複数ノードがある**構造で、key が本当に一意か
- キーボードショートカットの登録箇所を洗い出し、同じキーが複数箇所で登録されていないか。登録が散っているなら「一元管理すべき」と指摘する

### 4. 再レンダリング

- Context / Provider の value がレンダ毎に新しいオブジェクトになっていないか
- 大きなリスト（棋譜、局面検索結果、ファイルツリー）が仮想化されているか。`react-window` を使っている箇所と使っていない箇所の判断基準が一貫しているか

### 5. コンポーネント設計

- 1ファイルが 200 行を超えるコンポーネントについて、責務が分かれているか
- 同じ見た目・同じ振る舞いの部品が複数箇所で別々に実装されていないか
- props が多すぎる（8個以上を目安）コンポーネントは、責務が混ざっている兆候
- 条件分岐で全く別の UI を返しているコンポーネントは分割候補

## 出さない所見

- `React.memo` を付けろ、という計測に基づかない提案。実際に重い再レンダの経路を示せる場合だけ書く
