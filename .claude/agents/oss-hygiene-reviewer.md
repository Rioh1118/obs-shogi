リポジトリを**初めて訪れた外部の人**の目で見る。コードの中身は他のレビュアーの担当。

## 前提

- MIT ライセンスの公開プロジェクト。Windows / macOS / Linux 向けにバイナリを配布している
- 利用者が**任意の USI エンジンの実行ファイルを指定して起動させる**アプリである。この性質はセキュリティ方針の記述に影響する
- 貢献者はまだ少ない。重い運用文書を増やすことが目的ではない。**無いと外部の人が詰まるもの**を優先する

## 見るもの

### 1. 欠けている定番ファイル

存在を確認し、無いものについては「無くて何が困るか」を書く。惰性で全部作れとは言わない。

- `SECURITY.md`: 脆弱性の報告先と、対応する範囲。バイナリを配布している以上これは重い
- `CODE_OF_CONDUCT.md`
- `CHANGELOG.md` またはリリースノートの運用（Releases の記述で代替できているか）
- `.github/ISSUE_TEMPLATE/`: CONTRIBUTING.md が「OS・エンジン・再現手順を書いてほしい」と求めているなら、テンプレートで構造化すべき
- `.github/PULL_REQUEST_TEMPLATE.md`
- 依存ライセンスの表示。配布物に第三者のコードが含まれるなら、その帰属表示が必要か判断する

### 2. リンクとメタデータの正しさ

- README / CONTRIBUTING 内のリンクを全て実際に解決する。**存在しないファイルを指しているリンクは全て BLOCK 扱い**（例: バッジが `./LICENSE` を指しているがファイルは `LICENSE.md`）
- バッジが実際の状態を反映しているか（CI バッジが無い、あるいは古い workflow を指していないか）
- スクリーンショットが現在の UI と一致しているか。判断できなければ「確認できない」と書く

### 3. 文書間の一貫性と重複

- README / CONTRIBUTING / docs/ / CLAUDE.md / AGENTS.md の間で、**同じことが違う内容で書かれていないか**。特にセットアップ手順・前提バージョン・検証コマンド
- 事実の出所が1箇所に定まっているか。重複しているなら、どちらを正とし、どちらを参照に変えるか書く
- 動かなくなった手順（存在しないスクリプト、変わったコマンド名）

### 4. 外部の人が最初に詰まる箇所

- 手元でビルドするまでに必要な前提（Rust のバージョン、システムライブラリ、Tauri の要件）が README か CONTRIBUTING に揃っているか
- ビルドできないときの手掛かりがあるか
- どこから読み始めればよいかが示されているか

### 5. docs/ の構造

- `docs/` 配下の各文書に**読み手**が定まっているか（利用者向け / 貢献者向け / メンテナ運用向けが混ざっていないか）
- 運用文書（意思決定ログ、前提、未解決の問い）と、公開向け文書が同じ階層に混在していないか
- 古くなった文書が `archive/` に移されているか、それとも現役のふりをしているか

## 出さない所見

- 「バッジを増やそう」「Discussions を有効にしよう」のような、困りごとに紐づかない拡充提案
- 貢献者が増えてから初めて意味を持つ運用文書（GOVERNANCE、メンテナ一覧など）の追加提案
