## lint / hook で強制できるもの

- **BE-01 で、報告書の見出しの書式が4通りあることが分かった** ——
  book-to-main の `### <ID> (<深刻度>`、`yaneuraou-db` r5〜r9 の `## <ID> (<深刻度>,`、
  r1〜r4 の「`## HIGH` 節＋MEDIUM の表」、`game-engine` の `### R<N>-<H|M><n>`。
  検査を書くなら4通り持たせるか、書式を寄せるかを先に決める
- **合体見出しの深刻度は機械では割れない**（`C-02 / C-03 / C-04 [BLOCK / HIGH]` は
  ID 3・深刻度2）。**「ID 数 ≠ 深刻度数の見出しは内訳の照合から外し、総数だけ見る」**と
  決めておかないと、この形が出るたびに手で判断することになる
- **範囲行のコミット数は `git rev-list --count` で照合できるが、
  「所見数＝コミット数」を仮定にできない** —— 1コミットが複数の所見を担う回がある。
  結果欄のハッシュの異なり数と突き合わせる形なら取れる
- **BE-05 の族は機械化できる** —— `.claude/reviews/**` の見出しから採番の綴りを集めて
  `REVIEW_TAG` に食わせ、**1件も当たらない形があれば落とす**。
  今回の `X-YN`（42種）はそれで出る
- **BD-01 の型は `EXPECTED_MIN` / `DRIFT_ALLOWANCE` と同じ形** ——
  床に上限を対にして、実測が `床 + 幅` を越えたら「床を上げろ」で落とす。
  余裕がどれだけ残っているかが常に見える
- BD-02 / BD-03（床のコメントに書いた変異の効き目が実測と違う）は機械で防げない。
  **床のコメントに変異名と減少率を書かない**か、書くなら同じ変異をテストとして持つか
