# レビュー: やねうら王テキスト定跡 (.db) reader — ラウンド5

対象: `feat/91-yaneuraou-db-reader`（issue #91）
観点: rust / robustness / perf / architecture / comment
基点: `c20fae8`（R4 の報告書）

R4 の修正で入った退行と、表の遅れが出たラウンド。所見7件（BLOCK 0 / HIGH 2 / MEDIUM 3 / LOW 2）。

---

## G-01 (HIGH, rust): 行長の文面が上限を1つも伝えていなかった → 修正済み `18c391d`

`megabytes` は MB 固定なので、`MAX_LINE_BYTES = 4096` が **`0.0MB`** になる。

    2行目が長すぎる（0.0MB 超）。定跡ファイルではないかもしれない…

どの行も 0.0MB は超えるので、文面が何も言っていない。既存のテストは
`contains("長すぎる")` しか見ないので緑のまま通っていた。

同じ関数は展開の上限（6 GiB）にも当てている。行長から展開の上限まで1つの
物差しに通すので、桁で単位を選ぶ形（`format_size`）にした。

変異: 単位を MB 固定に戻す → 2件落ちる。

## G-04 (HIGH, robustness): 長すぎる注記で正しい定跡を拒否していた → 修正済み `18c391d`

本家は注記の中身を見ないので、**4 KiB を超える注記を1行持つだけの定跡を普通に読む。**
こちらはそれを丸ごと拒否し、文面は「別のファイルを選び直すこと」。
正しい定跡に対する効かない復帰操作になっていた。表の不変条件1
（本家が読める定跡は、こちらでも読める）の未申告の例外。

注記なら残りを読み捨てて読み進む（`discard_rest_of_line`）。確保は
`MAX_LINE_BYTES` ずつで頭打ちなので、F8 が守っている性質は保たれる。
自由に伸びうるのは注記だけなので、ここを通せば残りは短い。

変異: 長い注記も拒否する → `a_note_longer_than_the_line_limit_is_skipped_not_rejected`。

## G-05 (MEDIUM, robustness): 上限の文面が、比べられない2つの数字を並べていた → 修正済み `eef4785`

`MAX_FILE_BYTES`（2.1GB）は `MAX_EXPANDED_BYTES`（6.4GB）より小さいので、
**文面の1つ目の数字は2つ目より必ず小さい。** 例外は無い（F0 を通った時点で確定する）。

    この定跡は展開すると大きすぎて開けない（1.0GB のファイル /
    展開できるのは上限 6.4GB 相当まで）。より小さい定跡を開くこと

利用者は「1.0GB が 6.4GB の上限に引っかかった」と読む。矛盾しているのでアプリの
不具合だと判断するか、「上限まで余裕がある」と逆方向へ動く。R4 F-03 の目的
（どれくらい小さい定跡なら開けるかを判断できる数字）は、この2つからは達成できない。

出すのは同じ量どうしにした。**上限に当たった時点で読めていたバイト数**が、
この形の定跡なら開ける大きさそのもの。2つの上限の向きはコンパイル時 assert で固定した。

## G-02 (MEDIUM, comment): 単価の doc が R4 の較正前のまま → 修正済み `18c391d`

R4 で単価を 150/100 → 280/150 に直したとき、**それを説明していた doc を直していなかった。**
同じファイルの中に2つの単価が同居し、古い方（1.95 GB）を信じると「4 GiB で足りる」と
結論して上限を下げる方向へ動く。

数字は定数の doc にだけ置き、他はリンクにした。リンクなら壊れたときに rustdoc が拾える（#305）。

## G-06 / G-07 (MEDIUM / LOW, comment): 表の遅れ → 修正済み `eef4785`

- F8 に「注記なら捨てて読み進む」が入っていなかった（**直したその日のうちに再発**）
- 「埋まっていないセル」が (S2, E0) / (S2, E3) を挙げていたが、これは踏んでいる
- 逆に (S1, E0) / (S1, E1) / (S1, E3) が印だけ付いて通っていなかった → テストを1本足して埋めた

## G-03 (LOW, perf): 反論して見送り

`keep_first_of_each_move_everywhere` を読み込み中に挟む案。R4 で同じ形が
**26倍遅く**なることを実測している（10 000 ブロックで 18.8s vs 0.34s）ので採らない。
測定は #197 にコメント済み。
