# レビュー: やねうら王テキスト定跡 (.db) reader — ラウンド8

対象: `feat/91-yaneuraou-db-reader`（issue #91）
観点: rust / robustness / comment / perf
基点: `c8992e7`（R7 の報告書）

所見17件（BLOCK 1 / HIGH 3 / MEDIUM 13）。**このラウンドで、上限の見積もりが実物と
同じ形で破れていることが分かった。**

---

## P-01 (HIGH, perf): 単価が実物の形で上界になっていなかった → 修正済み `67d14a6`

`flush` が溜めた `Vec` を容量ごと渡していた。`push` の倍々成長が残す空きは
展開後の 28%（`keep_first_of_each_move_everywhere` の doc が自分で書いている）で、
**それを落とすのは読み切った後**なので、ピークには必ず全部乗る。

R6 の較正が片方の軸しか動かさない形（局面だけ／1局面に大量の手）で取られていた。
**両方が同時に効く実物と同じ形でだけ破れる。** 実測（459,000 局面 × 9 手。
実物の平均は 7.15 手）:

|        | 実 footprint | 見積もり | 比       |
| ------ | ------------ | -------- | -------- |
| 修正前 | 1,254MB      | 812MB    | **1.54** |
| 修正後 | 546MB        | 812MB    | 0.67     |

比は線形なので、見積もりで上限（7 GiB）に当たる直前の定跡は実 11 GB 前後。
ファイルは 1.2GB 程度で前段（`MAX_FILE_BYTES` 2 GiB）を通る。**`MAX_EXPANDED_BYTES`
の doc が上限の根拠に挙げている「16GB の機械でスワップに入ってアプリごと落ちる」
そのもの。**

単価を上げるのではなく、吸収しようとしている空きを作らない。長い列は移し替えない
（移し替えの瞬間だけ2本持つので逆に膨らむ。実測 +47.8%）。

## G-01 (BLOCK, comment): コメントが実装と逆 → 修正済み `d0060c5`

「ここで上書きすると、完全な定跡を『途中で切れた』と診断する」の**次の行が
まさに上書きしていた**。従う読み手はその行を消す方向へ動く。名指ししている結果も
現在の実装に無い（`last_line_terminated` の行き先は `log::warn!` 1箇所）。

退避して潰して戻す往復が無操作だったので、構造ごと直した。**このコミットに
対応するテストは無い**（行き先が `log::warn!` だけで観測できない）。

## R-01 / H-01 (HIGH, rust / robustness): 指し手でない行に「指し手が書かれている」 → 修正済み `9b4d006`

**両観点が独立に挙げた。** R7 の `1fa2676` は見出し探索の側だけに形の検査を入れ、
本体のループを触っていなかった。

    見出し無し → やねうら王テキスト定跡として読めない（1行目: <!DOCTYPE html>）。…
    見出し有り → 局面より先に指し手が書かれている（2行目）。取得し直すか…

見出しがある側は**事実でないことを言い、しかも行を引用しない**ので、利用者は
2行目が何なのか確かめられない。配布元が 404 の HTML を返した定跡がこの形になる。

既存のテストが「ここに別のテキスト」に対して「局面より先に指し手」を期待値として
固定していた（＝誤りをテストが守っていた）。

## H-02 (HIGH, robustness): BOM 付きで1行目の長い注記が拒否される → 修正済み `fb471cb`

BOM を落とすのが長さの検査より後にあった。`is_note` は ASCII 空白しか飛ばさないので、
`0xEF` が先頭にあると1行目の注記が注記と判定されない。同じ中身が BOM の有無だけで
拒否される。R5 G-04 で直した穴の残り1経路。

直す最中に、`raw.len()` で長さを見ると BOM の3バイトぶん上限をすり抜けて行の残りが
次の行として読まれることを踏んだ。判定は読んだバイト数で見る。

## R-02 (MEDIUM, rust): 引用が切る前に入力全体を複製 → 修正済み `5858b74`

**R7 の `b098fb2` で自分が入れた退行。** 制御文字の可視化に `str::replace` を
使ったので、120 字に切る前に入力全体（制御文字だらけなら3倍）を確保する。
`to_book_key` はコマンド境界から任意長の文字列を受け、しかも `spawn_blocking` の
外を通る。実測で 20M の入力に 808ms。

パス用は最初から切ってから組んでいた。**同じことを2箇所で書き分けたのが原因**なので、
1つのヘルパに通す。`error.rs` に `excerpt` を直接見るテストが1本も無かったので足した。

## H-03 (MEDIUM, robustness): 局面が無い定跡に「取得し直す」 → 修正済み `f8d31c1`

**見出し1行だけのファイルは利用者が自分で作れる。** ShogiHome は空の定跡をその形で
書き出し、全ての指し手を消した定跡も同じ 23 バイトになる。取得元が無いので
「取得し直す」は実行できない。不変条件1の差の表にも H5 が入っていなかった。

## P-02 (MEDIUM, perf): 空きマスの run ごとにヒープ → 修正済み `3d8751c`

`flush_empty` の `to_string()` が局面あたり 17 回。実物で 3,800 万回。
`write!` にして 2.63s → 2.25s（−14%）。

## 機械で止まらないと分かったもの

- **単価が上界であること。** 自前アロケータで数えた追跡ピークは比 1.63 の形でも
  見積もりを下回る。破れているのは malloc の丸めと断片化を含む footprint の側で、
  それはテストプロセスの中から取れない。**R6 の較正が1点で足りると読めてしまったのと
  同じ穴が、軸の組み合わせの側に残っていた**
- `last_line_terminated` の行き先（`log::warn!` のみ）
- `excerpt` の確保の順序（出力が同じ。守っているのは共通ヘルパの形）
