### [HIGH] R4-01 文字コードの「印」に閾値が無く、NUL が1つ混じるだけで UTF-16 と断定する

- 場所: `search/kifu_reader.rs` の `detect_encoding`
- reviewer: **3人とも**（全員が独立に実測した）
- `even.cmp(&odd)` は差1でも断定する。バイト数に対する割合も、
  反対側の番地に NUL がほぼ無いことも、長さが偶数であることも見ていない

  ```
  [NUL なし] detect=None     -> KIF Error: at line 4 ...   2 パス      （正しい）
  [NUL 1つ]  detect=UTF-16BE -> UTF-16BE としては読めたが … at line 1 … 軨趇誄腆閽軨…
  ```

- NUL 末尾詰めは書き込み中に落ちたファイルや Windows 製ソフトの出力で現に出る。
  **R3-01 で塞いだ故障が別の「印」で再発していた**
- 逆向きも起きる。低位バイトが `0x00` の文字（`　` `一` `─`）が多い本物の
  UTF-16LE は UTF-16BE と判定される

### [HIGH] R4-02 「KIF / KI2 / CSA は欄を落としても1バイトも変わらない」が誤り

- 場所: `kifu.rs` のテストの doc
- reviewer: rust / robustness（どちらも実測）
- 書き出しは `same` と `promote` を局面から作り直さず、**JKF の欄をそのまま読む**

  | 欄                     | 本文                                                |
  | ---------------------- | --------------------------------------------------- |
  | `same`                 | 変わる（`同　` が座標に戻る）                       |
  | `promote`              | 変わる（**`２二角成` が `２二角` になる＝別の手**） |
  | `capture` / `relative` | 変わらない                                          |

- この誤った一般化が「差が見えるのは `jkf` 形式だけ」の根拠に使われており、
  **`promote` が落ちたときに手が変わることを「見なくてよい」と決めていた**
