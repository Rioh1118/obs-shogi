**産物（対局の Rust API）そのものの欠陥は、r24 から0件が続いている。**
増え続けているのは、私が回を重ねるごとに厚くしてきた**診断の機構**の側。

`/implement` はこの場合の問い方を3つ挙げている。順に当てる。

### 1. その機構は、いま実装している機能が要求しているか

要求していない。対局機能に要るのは「失敗したときに理由を追える1行」で、
**枠を対局ごとに割ることも、出来事の種別を3つに分類することも要求されていない。**

### 2. 同じ判断をする場所を数える

「この行を絞ってよいか」を決める場所が**5つ**ある——`is_frequent` / `is_terminal` /
`needs_every_line` / `frequent_warn` / `rare_warn`。集約できる。

### 3. 判断を変えたら、その判断が正当化していた機構がまだ要るかを測り直す

**測り直した結果、前提が偽だった**（R27-H1）。3つの分類はすべて
「宛先が消えると `emit` が失敗し続ける」を根拠にしているが、
tauri 2.11.1 の現物では**購読者がゼロなら `emit` は成功して返る**。
守っていたはずの1行は、それが要る場面では**1行も書かれない**。

→ **分類を畳み、診断を「情報がある場所」へ移す**（下の修正計画）。

## 前提が偽だった

### R27-H1 `emit` は宛先が居なくなっても `Ok` を返すので、守っていた1行はその場面で書かれない

`src-tauri/src/engine/commands/game.rs:92-130`、`game/types.rs` の3つの分類、
`docs/state-transitions/failure-surfacing.md` の F-19。

robustness が tauri 2.11.1 のソースを読んで確認:
`emit_js_filter` はその webview がその event を購読していなければ `emit_js` を呼ばずに `Ok`、
ウィンドウが閉じていれば `webviews_lock()` に居ないので**反復そのものが0回で `Ok`**。
Rust 側の `Listeners::emit_filter` も購読者ゼロで `Ok`。残る失敗は直列化だけで、
`GameEvent` が運ぶのは `String` / 整数だけなので実質起きない。

筋道: 対局中にウィンドウを閉じる → 次の `MoveDecided` の `emit` は**成功して返る** →
フロントが裁定を返さないまま `RULING_TIMEOUT` → `finish(Aborted, "no ruling came back")`。
**ログに残るのは `start: ok game_id=…` だけで、その対局がどう終わったかを書いた行は1行も無い。**

R26-M8 が `moveDecided` を枠から外したのは、この1行を守るためだった。

### R27-H2 連打が「続く」場合、絞りは1間隔あたり121行を通す（doc は「1秒1行」と書いている）

`src-tauri/src/engine/commands/game.rs:157-158`（doc）と `:196-209`（実装）。

rust が実測:

```
1秒ごとに通った warn 行数: [121, 121, 121, 121]   総呼び出し=388247
```

`LogThrottle::new` は新しい枠の先頭を必ず通す。連打が1間隔続くと120個の枠が一斉に
`is_open` になり、次の未知 ID が `retain` で全部落として自分を挿す→**そこから119個は
`len < MAX` の枝を素通りして順に挿さる**。1間隔ごとに確定で120＋1行。

1行は約170バイトなので、**200KB は10秒前後で一周する**。R25-H2 が塞いだ形が
121倍に減っただけで戻っている。

`an_unknown_id_flood_still_gets_throttled` は 120+1000 回をマイクロ秒で回し切るので、
枠が1つも `is_open` にならない。**観測しているのは最初の1間隔だけ。**

### R27-H3 `usi_move` が長さも改行も無検査のまま、断り文句とログ行へ丸ごと出る

`src-tauri/src/engine/game/session.rs:1970-1985` の
`format!("move is too long: {usi_move}")`。

`GameId` は `Display` が48文字で切り、制御文字を潰しているのに、
**隣の欄には何も掛かっていない。** `submitGameMove(id, "black", "x".repeat(300_000))` で
300KB の1行がログへ出て、その1行だけで予算を一周させられる。
9バイト以上あれば改行を混ぜられるので、`GameId::Display` の doc が名指しで警戒している
「その後ろに好きなログ行も作れる」がそのまま成立する。

既存のテストは `validate_usi_move("7g7f\nquit")` が `is_err()` であることしか見ていない。

## 機構の説明が現物と食い違う

### R27-H4 `TIMED_OUT` の doc が「機械は見ていない」と書いているが、同じラウンドでその機械を置いた

`src-tauri/src/engine/types.rs:79`。`timeout_marker` を入れたコミットは
このファイルに触れていない。**`TIMED_OUT` を grep すれば真っ先に出る場所。**

読んだ人は「綴りは人が守る規約」と判断し、赤を踏んだときに
「知らないラチェットに引っ掛かった」として走査の限界に沿って回避する。

### R27-H5 「目印が無ければ設定の誤り」と4箇所が書いているが、その契約は同じラウンドで TSDoc から落とした

`timeout_marker.rs:3-6` / `:81-82`（**TSDoc に帰属させている**）、`CONTRIBUTING.md:312`、
`session.rs:97-98` / `:2255-2256`。

`0d7a2c5`（ラチェットを置いた）→ `3ed5373`（TSDoc から断言を落とした）の順で、
**同じラウンドの後ろのコミットが前のコミットの前提を消している。**

読んだ人は Rust 側だけを読んで「目印さえ入れれば分類は完成」と判断し、
`failed to run the spawn task` / `ready channel closed` に目印を入れる方へ倒れる
——**内部の取り落としが「再試行すれば通る」として案内される。**

### R27-M1 `timeout_marker` の「走査の限界」が逆を書いている

`src-tauri/tests/timeout_marker.rs:12-16`「変数を1つ挟めば素通りする」。

rust が変異で確認: 素通りではなく**誤検出で赤くする**（報告に出るのは `reason` の3文字だけ）。
`format!` が長くなって変数へ括り出した人が赤を踏み、doc を読んで
「素通りするはずのものが落ちた＝走査が壊れている」と診断する。

### R27-M3 doc の引き剥がし（7回目）

`src-tauri/tests/scanning/mod.rs:23-29`。`use std::path::Path;` が
`skip_literal_or_comment` の doc と関数の間に入っている。

`cargo doc` でこの関数は**説明の無い `pub fn`** として出る。
「`'{'` は文字リテラル」「`br#"..."#` は raw」という**なぜこの関数が要るのか**が
唯一書かれている4行が剥がれている。

**`///` の直後が `use` になっているのは全体でこの1件だけ**なので、機械化すれば緑で始められる。

### R27-M4 `verify-gate.sh` のヘッダが直っていない。**ラウンド26の報告書の「12件すべて着手」が不正確**

`.claude/hooks/verify-gate.sh:6`「`cargo が見るもの（*.rs / Cargo.*）`」。

R26-M5 は `CONTRIBUTING.md` と `verify-gate.sh` の2箇所を指していたが、
修正コミットは `CONTRIBUTING.md` しか触っていない。**報告書に書いた
「12件すべて着手」は、この1件について事実と違う。**

### R27-M5 `scanning/mod.rs` のラチェットが索引に無く、索引の門番は構造的にそれを見られない

`no_test_counts_delimiters_by_hand` は `tests/` 全体を歩くリポジトリ横断のラチェットだが、

**「両方に載っていないと落ちる」と2箇所が書いているが、サブディレクトリでは落ちない。**

## 失敗経路

### R27-M6 番人が決めた終局は1行も残らず、同じ物理状態を別の検出器が見たときだけ `error` が出る

`session.rs:1191-1249` の3つの枝（`stalled_turn` / `has_expired` / `RULING_TIMEOUT`）は
`finish` を呼ぶだけで、`finish` もログを書かない。一方 `on_search_outcome` と
`hand_turn_to` は同じ状態に対して `error` を出す。

**どちらの番人が先に当たったかで痕跡の有無が変わる**ので、ログを根拠に
「この対局は正常に終わった」と読めない。

### R27-M7 終局した対局は `close_game` まで10Hz の拍を回し続け、対局の数にも上限が無い

`session.rs:788-800` の `tick_loop` が抜けるのは `tx.upgrade()` が失敗したときだけ。
`Phase::Over` に入った後の `on_tick` は即 return するので、**何もしない拍が残り続ける。**

`GameManager::start` は同時に開ける対局の数を見ていない。人対人はエンジンを1つも
起こさずに返るので、`startGame` を回すだけで対局がいくらでも増える。
**絞りの枠には上限があるのに、実体の対局の側には無い。**

### R27-M2 時間に依存するテストが、外すと存在しないバグを名指しで報告する

`commands/game.rs:450-474`。2つ目の assert が通るのは「最初の junk 枠がまだ 20ms
経っていない」ときだけ。実測の余裕は32倍だが、`cargo test --lib` は204本を並列で回す。

外れたときに落ちるのは**期待と逆の性質**を主張する行なので、
踏んだ人は `retain` / `is_open` に無いバグを探すことになる。

### 「対象を疑う」の結果、落としたもの

`is_frequent` / `needs_every_line` / `frequent_warn` / `rare_warn` を**落とした**。
正当化していた前提（宛先が消えると `emit` が失敗し続ける）が偽で、
守っていたはずの1行はそれが要る場面で書かれていなかった。

代わりに `finish` が1行書く。**全部の終わり方が通る唯一の場所**なのに、
それまで1行も書いていなかった——番人が決めた終局は痕跡が残らず、
どちらの検出器が先に当たったかで痕跡の有無が変わる状態だった。

診断まわりの所見は r25=4 / r26=6 / r27=7 と増え続けていた。**厚くするのを
やめて畳んだ**ぶん、次のラウンドで測り直す。

- `finish` で拍の旗を降ろさない
