# ラウンド2 — `search` の欠陥（`main` に当て直した分）

対象は `review/388-on-429-all`。ラウンド1の修正そのものをレビューした。

観点は rust / architecture / robustness / comment / react / oss-hygiene。

## このラウンドの共通の原因

**ラウンド1が「旗を足す」ところで止まり、「出す口を1つにする」まで行っていなかった。**

旗（`scan_failed` / `partially_unreadable`）は増えたのに、`EVT_INDEX_STATE` を
組む場所は差分適用・全件構築・コマンドの3箇所に残っていた。旗を知らない側が
`IndexStatePayload::of`（全部 `false` から始まる）で組むので、**あとから出たほうが
緑で塗り潰す**。

そのうえ、ラウンド1の修正が3つ新しい穴を開けていた。

1. `build_failure` を `build` 段へ動かしたことで `build ↔ project_manager` の環ができた
2. `carried_over` に**繰り越した件数ではない値**を渡していた（文言が逆を言う）
3. 走査に失敗した全件構築を `restart` + `Ready` で終えていた——**`main` より悪い**。
   `main` は `Building` のまま置き去りにするので、検索は少なくとも「更新中」と言えた。
   空の索引を `Ready` にすると、`query_service` は段しか見ないので
   **0件が「最新」として並ぶ**

## 自分が作った退行

**`git checkout <file>` で変異を戻そうとして、その回の編集ごと消した。**
`indexHealth.ts` は既にコミット済みだったので、未コミットの追加が HEAD へ戻った。
気付いたのは直後の grep。**変異テストの復元はコピーから戻すこと**——
`git checkout` は「変異だけ」を戻す道具ではない。

## この報告書の訂正（R3 で判明）

**「`announce_state` 1つに閉じた」は言い過ぎだった。** 閉じたのは終端
（`Ready` / `Empty`）を出す口だけで、進行中の段（`Restoring` / `Building` /
`Updating`）は5箇所が生で出したまま。ファイル数で数えると「3箇所」は
1つも減っていない。**6人中4人のレビュアーが独立に指摘した。**

**「6本足した」テストにも穴があった。** `Built` の腕に旗を1本足す変異が
実測で生き残る。成功した全件構築という**いちばん普通の経路**だけ
assert が無かった。

R1 に続いて2回連続で「直した」と書いたものが直っていない。
**表を書く前に、直したはずのものに変異を当てること。** doc に書いた不変条件は
機械が見ていないかぎり嘘になる——R3 で `tests/state_is_announced_once.rs` を足した。
