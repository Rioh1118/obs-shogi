### [HIGH] R15-02 R14-01 と同じ形が長さの欄4つに残っている。68バイトのキャッシュで 1.08 GB

- 場所: `search/index_cache.rs:521`（本命の `map_len`）、同種が `:502` / `:537-538` / `:564`。
  doc は `:448-452`
- reviewer: **rust / robustness / comment の3人**（rust と robustness が別々に実測）
- `checked_file_id` が守っているのは `file_id` だけで、長さの前置きは4つとも無検査

  ```rust
  let map_len = r.read_u32()? as usize;
  let mut path_to_id = HashMap::with_capacity(map_len);
  ```

- 68バイトの blob で `map_len` だけを変えたときの最大常駐（baseline 5.5 MB）:

  | `map_len`       | 最大常駐    | 所要       |
  | --------------- | ----------- | ---------- |
  | 1,000,000       | 7.8 MB      | 0.80 ms    |
  | 40,000,000      | 72.6 MB     | 19.2 ms    |
  | **500,000,000** | **1.08 GB** | **353 ms** |

- **`HashMap` だけが危ない。** hashbrown は制御バイトを memset するので実際にページを触る。
  `rec_len` / `nodes_len` / bucket の `n` を1億にしても常駐は増えなかった
  （`Vec::with_capacity` は macOS では遅延予約）。ただし**それは OS 依存**
- 到達性: 単ビット反転で `map_len` が1億を超えたのは **241件 / 9,253（2.6%）**、
  ランダム破損で **584件 / 22,357（2.6%）**。実プロジェクトの `map_len` は小さいので、
  **最上位ビットが1つ反転するだけで 2.1e9 になる**
- **`checked_file_id` の上限そのものも破れる。** `ft_len` も同じ blob の無検査 `u32` なので、
  `checked_file_id(0xFFFFFFFE, 0xFFFFFFFF)` は `Ok` を返す
  （22万件の破損試行では1件も出ていないので、実害として測れたのは `map_len` だけ）
- **doc（`:451`）は「確保量が入力の長さで頭打ちになるのがここで欲しい性質」と書いている。
  その性質は成立していない。**
