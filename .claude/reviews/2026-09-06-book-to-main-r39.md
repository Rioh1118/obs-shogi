### BK-01 (HIGH, 1人が実測): 台帳に、この PR が足した失敗が1行も無い

台帳への差分は**採番規約の前書きだけ**で、表の行は0行。

`InvalidHandle` の復帰が操作で逆になることも知らないまま画面を作る。

**これは台帳が F-27 について自分で書いた失敗の再演** ——
「Rust の経路が増えたという理由だけで後から足された。
『始められなかった』を落とすと、パスを選び直す導線そのものが設計から抜ける」。

- 結果: 対応済み `a4356a54`（F-31〜F-34 を追加。§4 も定跡を含む形へ）

### BK-02 (HIGH, 1人が実測): 拡張子が判別できないとき、開けない3形式を勧めている

> 拡張子から定跡の形式を判別できない（.db / .bin / .sbk / .ybb）

このうち `.bin` / `.sbk` / `.ybb` は `support()` が `None` を返すので
`UnsupportedFormat` で落ちる。**案内どおり `.bin` を用意して開き直すと2度目の行き止まり。**

同じモジュールの `UnsupportedFormat` は「読める形式が1つある状態では
『別のファイルを試しても同じ』ではない。次にやれること（.db なら開ける）を出す」と
書いてテストで固定しているのに、**その判断がこの枝にだけ当たっていない。**

加えてこの message は動詞で終わっておらず、
**不変条件3（message は「次に何をすればよいか」で終わる）を満たさない。**

- 結果: 対応済み `41002d4d`

### BK-03 (MEDIUM, 1人が実測): 定跡でないファイルを「大きすぎる定跡」として説明している

上限の doc は自分でこの検査の目的を書いている ——
「明らかに定跡でないものを1バイトも読まずに落とす」「`.db` は SQLite でも使う拡張子」。

ところが文面は定跡前提だった ——「この**定跡**は大きすぎる。より小さい**定跡**を開くこと」。

3GB の SQLite を選ぶと1バイトも読まずにここへ落ちるが、利用者は小さい定跡を探しに行く。
**同じファイルが 2GiB 未満なら「別の形式のファイルかもしれない」が出る**ので、
大きさだけで説明が逆になる。同じ取り違えを避ける注記は `read_line` の側に既にあり、
**いちばんそれが要る枝にだけ無かった。**

- 結果: 対応済み `8959130f`（既存テストは「2.1GB」と「こと」しか見ておらず
  この変更で落ちないので、その assert も足した）

### BK-04 (MEDIUM, 1人が実測): 読み飛ばした欄が log にしか出ない

`DroppedFields` の doc は**「落とした事実がどこにも出ないと、誤読みだと分かる
手がかりが利用者にも報告を受けた側にも無い」**と書いているのに、
出していたのは `log::warn!` だけ。**アプリにログを見る導線は無い。**

欄がずれた定跡を開くと `optional_number` が `Err` を `None` に潰して
**開くこと自体は成功する**（1つの綴りのために数百 MB を捨てない、という正しい判断）。
全候補手の `value` / `depth` が `null` になるが、
**利用者にはそれが「もともと無い」のか「読み損ねた」のか区別する材料が1つも無い。**

- 結果: 対応済み `a0b4f648`（`parse` → `YaneuraouDbReader` → `OpenedBook` →
  `BookInfo` へ通す。**両方向の変異で落ちることを確認** ——
  常に 0 を返す形でも、常に非0を返す形でも）

### BL-03 (MEDIUM, 1人が実測): 抽象と具象が相互依存になっている
