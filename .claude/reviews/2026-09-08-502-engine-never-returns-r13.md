## 所見

### HIGH-1 排出が固定回数のままでは、実時計への依存が残る（architecture）

「タイマーが無いから決定的」は誤り——`act` が回す work loop は実時計の予算で yield するので、
1段が複数ターンに割れうる。**足りない回に「別の結末になった」と読まれるのが最悪の壊れ方**で、
`startGate` は「追い越された畳みが健全なエンジンを殺した」（＝守っている性質そのものの名前）で落ちる。

### HIGH-2 `initializer` の `finally` の同一性判定は観測できる（robustness。実測）

r12 で私が「観測できない」と書いた3つのうち1つに列が在った。潰すと、**次の畳みが
飛んでいる起動を待たずに IPC を撃つ**——起動処理中のエンジンが落ち、
畳みは `catch` で捨てられるので**画面には何も出ない**。

### HIGH-3 ※2 と不変条件1 が、現物の呼び手には作れない窓を「起こる遷移」として書く（comment / robustness）

`initialize` は起動の門で塞がれており、門が開くのは `shutdown` を通ったときだけで、
そこで `inFlight` も同じ同期区間で空く。**「門が開いている ∧ `inFlight` が非 null」は存在しない。**
同じファイルの別の箇所は「provider を張り直す列でしか踏めない」と逆を書いていた。

### HIGH-4 この PR が消した欠陥を、仕様がまだ「いまも在る」と書いている（oss-hygiene）

`tab=general` を書いている仕様は**4枚**あり、r12 で直したのは2枚だけ。残る2枚のうち2箇所は
**「いま満たしていないこと」＝残タスクの一覧**なので、読んだ人が着手する。

### HIGH-5 `startGate` の冒頭 doc が「門4つ」、`engine.md` は「5つ」（comment / oss-hygiene）

r12 が潰したのと同じ形（同じ機構についてコードの doc と台帳が別のことを言う）が場所を変えて再発。

### MEDIUM-6 〜 MEDIUM-11

- 窓を見る assert 3つが、**緑では空配列に当たる**（react / robustness）。3本目は窓の前提を1つも持たない
- 「2プロセスを止めているのは in-flight の畳み込み」は測ると**逆**。畳み込みの枝は1つの provider の中では一度も踏まれない（robustness。実測）
- `onEngineGone` に書いた順序の制約が、React では起こり得ない割り込みを前提にしている（comment / react）
- 鏡の理由「読むのは全部 `await` の継続」が事実でない（`analyzingRef` はタイマーとイベントからも読まれる）（react）
- `drain` の doc「多すぎても遅くならない（実時間はほぼ0）」が実測と2桁違う（comment / react / architecture）
- `analysis.md` ※2 だけが上限を直値で書き、**打ち切りの引数を落としている**（oss-hygiene）
- 測定注記1件だけがブランチ名を省略形で書いている（oss-hygiene）
- **コミット2本のメッセージと中身が入れ替わっている**（oss-hygiene）

### 差分の外

- **`startingSeqRef` は、`initialize_start` の dispatch 回数以外に効いている先が無い**（architecture。実測）。
  この門は r8 で入り、**r9 で BLOCK を自分で作り**、r9〜r12 で4ラウンド直し続けている。
  #502 の受け入れ条件とは線が繋がっていない。**落とす候補として名指しされた**
- `restart()` の署名（architecture の回答）——**いま型を厚くするのは負債**。読み手が0なので、
  `EngineContextType` から命令形の動詞ごと降ろすのが筋。`docs/IDEAS.md` の既存項目へ

### 反論（`startingSeqRef` を落とさなかった理由）

architecture の測定（門を潰すと StrictMode の1本しか落ちない）はそのとおりで、
**利用者に見える差が無い**という指摘も正しい。それでも残す理由は2つ。

- **落とす変更は、それ自体が新しいレビューを要る。** 13ラウンド目に本番コードの機構を
  1つ外すのは、r9 で同じ場所に BLOCK を作った経緯からしても割に合わない
- architecture 自身が出した条件（「落とせないなら、この門が守っているものを1本のテストで
  名指しすること」）は**満たしている**——門を潰すと StrictMode のテストが落ちる
