### [HIGH] `winner` に `Color.Black === 0` を入れているので、`if (winner)` が先手勝ちを引き分けと同じに潰す

- 場所: `src/entities/game/lib/gameOutcome.ts:51-55`、`src/entities/game-session/api/tauri.ts:128-134`、`src/entities/game-session/api/rust-types.ts:37`
- 根拠:

  ```ts
  export interface GameOutcome {
    kind: GameOutcomeKind;
    /** 引き分けなら null */
    winner: Color | null;
  }
  ```

  実測: `judgeGameOutcome({startSfen:"4k4/9/3GP4/9/9/9/9/9/4K4 b - 1", usiMoves:["6c5b"]})`
  → `{"kind":"checkmate","winner":0}`。`typeof winner === "number"`、`!!winner === false`。

- なぜ問題か: 唯一の宛先である `endGameByRule(gameId, winner: Side | null, detail)` は
  `Side = "black" | "white"` を取る。`Color` から `Side` への変換は
  `ruleColor.ts` にも `entities/game-session` にも**無い**ので、呼ぶ側が自分で書く。
  そこで自然に出る綴り —— `outcome.winner ? "white" : "black"` / `outcome.winner ?? null` /
  `if (!outcome.winner) 引き分けにする` —— は**全て先手勝ちを取りこぼす**。
  `Color.Black` が `0`、引き分けが `null` で、どちらも falsy だから。
  tsc は `Color | null` の真偽判定を通すので落ちない。
  利用者に起きること: 先手が詰ましたのに「引き分け」または「後手の勝ち」で棋譜に残り、
  盤上は詰みなのに結果だけが違う。**どこにもエラーは出ない。**
- 直し方: `winner: Color | null` をやめ、falsy な正常値が存在しない形にする。
  `GameOutcome` を `{ kind: GameOutcomeKind; result: "black" | "white" | "draw" }` にするか、
  最低限 `ruleColor.ts` に `toSide(color: Color): Side` を置いて、
  `GameOutcome.winner` の型を `Side | null` にする（`Side` は同じ entities レイヤなので
  `no-restricted-imports` には当たらない）。

### [HIGH] トライルールが直前の手を見ず盤面だけで判定するので、玉が動いていなくても成立する

- 場所: `src/entities/game/lib/gameOutcome.ts:86-89`、`src/entities/game/lib/gameOutcome.ts:135-137`
- 根拠:

  ```ts

    const piece = shogi.get(5, color === Color.Black ? 1 : 9);
    return !!piece && piece.color === color && piece.kind === "OU";
  }
  ...
  if (rules.jishogiRule === "try" && isOnTrySquare(shogi, lastMover)) {
    return Ok({ kind: "tryRule", winner: lastMover });
  }
  ```

  実測1: `startSfen:"4K4/9/9/9/4P4/9/9/9/8k b - 1"`（先手玉が既に5一）、`usiMoves:["5e5d"]`（**歩を突いただけ**）、
  `{jishogiRule:"try", maxMoves:0}` → `{"kind":"tryRule","winner":0}`。
  実測2: 両玉が互いのトライ地点に居る `"4K4/9/9/9/9/9/9/9/4k4 b - 1"` を `usiMoves:[]` で掛けると
  `{"kind":"tryRule","winner":1}` —— **1手も指されていないのに後手の勝ち**が返る。

- なぜ問題か: 直前の手が玉の移動であることも、移動先がトライ地点であることも見ていない。
  `docs/spec/features/game-play.md` は「トライルール = 相手玉の初期位置に**着いた**側」と書いており、
  `isOnTrySquare` の doc も「**着いた時点で**成立する。玉がそこへ動けたなら王手はかかっていない」と
  「動いた」ことを前提に安全性を論じているが、実装はその前提を検査していない。
  利用者に起きること: 局面編集や `initialMoves` 付きで、玉が既に5一（5九）に居る局面から対局を始めると、
  次に手番が回ってきて**何を指しても**その瞬間に「トライルールで勝ち」と表示され対局が終わる。
  両玉が該当する形では、勝者が「最後に指した側」という規則に無い基準で決まる。
- 直し方: `record.current.move` を見て、`move instanceof Move` かつ
  `move.pieceType === PieceType.KING` かつ移動先が `(5, lastMover === Black ? 1 : 9)` のときだけ成立させる。
  `usiMoves` が空のとき（`record.current === record.first`）は必ず `null` を返す。
  `isOnTrySquare` の doc にある安全性の議論（王手がかかっていない）も、
  この条件が入って初めて成り立つ。

### [HIGH] USI 文字列の末尾のごみを黙って捨てるので、フロントとエンジンが別々の局面を進める

  // 途中までの棋譜を `Ok` として返すので、短い局面を「現在局面」と誤って裁定する

  実測（`judgeGameOutcome`）: `{startSfen: 平手, usiMoves:["7g7f7f"]}` → `{"success":true,"data":null}`。

- なぜ問題か: `Record.newByUSI` の「黙った打ち切り」を避けるために手で回しているのに、
  1手ぶんの黙った打ち切りは `createMoveByUSI` の中に残っている。

  `unplayable_move`（上の所見で割るなら `unreadable_move`）を返す。
  tsshogi の `Move` は `usi` を持っているので1行で足りる。

  利用者の言葉に翻訳すると「2手目の 9i8i が指せませんでした」までしか書けず、
  次に何をすればよいか（この対局の棋譜を保存して残す／エンジンを替える／
  開始局面を確認する）を案内する材料が無い。復帰の導線が無い点は
  `docs/spec/features/game-play.md` の「復帰導線が無い（#374）」と同じ穴だが、
  こちらは**型の側で情報を落としている**ので、画面を足す段になっても復元できない。
- 直し方: `unplayable_move` に、その手を指す直前の局面（`record.position.sfen`）を足す。
  `buildRecord` のループの中では手に入る。呼び出し側はそれを盤に出せるので、
  「ここまでは進んでいて、この手で止まった」を見せられる。

## lint / hook で強制できるもの

- **falsy になりうる正常値を「有無」で使わせない**: `Color.Black === 0` を
  `Color | null` に載せる形は、この差分だけの話ではなく再発する。
  `src/__tests__/` に走査を1本足して、`shogi.js` の `Color` を
  `T | null` / `T | undefined` の形で公開面に出している宣言を落とす。
  （既に `cursorConstruction.test.ts` が同種の「型で防げない誤用」を走査で止めている前例がある）
- **`catch` の握り潰し**: `moveValidation.ts` の `catch { return true }` と
  `catch (e) { console.log(e); ... }` は、oxlint の `no-console` を
  `src/**`（テストを除く）で `error` にすれば後者だけは機械で止まる。
  前者（空 `catch` で既定値を返す）は走査を書くしかない
  —— `catch` 節の中に `return` しか無いものを `src/entities/**` で禁じる検査。
- **`switch` の網羅**: `jishogiDeclaration.ts:57-58` のような
  「union を三項で2択に潰す」形は、`switch` + `never` に統一すれば tsc が止める。
  規約として書くより、`JishogiRule` を受ける関数の三項を走査で落とすほうが確実。
- **テストからしか到達しない公開面**: `npm run ratchet:knip` はテストファイルを入口として数えるので、
  「本番の呼び出し側が1つも無い新規モジュール」を検出できない
  （実測: `judgeGameOutcome` も `judgeDeclaration` も unused に上がらない）。
  この差分のように「呼ぶ側はまだ無い」と明言して入れる面が今後も出るなら、
  `src/**` からテストを除いた入口で数える2本目のラチェットを置けば、
  「置いたまま忘れられた純関数」をその場で数えられる。
- `npm audit --omit=dev` は 0 件（根拠として使える）。
