## 見積もりの単位が、まだ揃っていない

### R31-H1 `GameId::Display` はバイト上限を守っていない。断りの1行が146→332バイトになる

3人とも同じ場所へ着いた。`src-tauri/src/engine/game/types.rs:70-87`。

```rust
used += ch.len_utf8();            // 入力のバイト数
if ch.is_control() {
    f.write_str("\u{fffd}")?;     // 出力は3バイト
```

制御文字は入力1バイトに対し出力3バイト。`GameId::new("\n".repeat(48))` は
`len() == 48` なので `is_safe_to_retain()` も**真**（24枠の鍵として正規に通る）で、
`Display` は 144 バイトを出す。`Rejection::Unknown` で同じ ID が1行に2回載るので、
`rejection_line` は **332バイト**。

rust の実測:

```
断りが出続けると 30s もたない（1間隔 9960 バイト、30 行 × 332 バイト）
```

`LOG_FILE_BUDGET / 9960 = 20.1` 間隔。約束している30秒に届かない。

**テストが軽い入力を選んだ理由もコメントに残っている。** バイトへ変えた当のコミットが
3箇所に「文字数で切る」と書き残していて、その古い理由から最悪の入力を選んでいる。

`a_game_id_in_text_is_bounded_and_has_no_control_characters` の表明も
`shown.chars().count() <= MAX_ID_BYTES + 1`——**文字数をバイトの定数と比べている**ので、
制御文字48個でも48文字として緑で通る。

### R31-H2 「最悪の入力」を被検査関数に作らせているので、`shown` の緩めを1つも落とせない

`src-tauri/src/engine/game/session.rs:3705-3732`。

```rust
let detail = shown(&"😀".repeat(MAX_DETAIL_LEN * 2), MAX_DETAIL_LEN);
assert!(detail.chars().rev().skip(1).all(|c| c.len_utf8() == 4), …);
```

入力を `shown` に通してから測るので、**`shown` が通す文字クラスしか測らない**。
rust の変異（`shown` を `is_control()` だけに戻す）で全13スイート green。

固定リテラル（`"\u{feff}"`）に差し替えると落ちる（実測 4,219 バイト）。

### R31-H3 `MAX_SUMMARY_LEN` に式が1本も無い。8192 に戻して全13スイート green

`src-tauri/src/engine/utils.rs:148-156`。`utils.rs` に `#[cfg(test)]` が1つも無い。

`MAX_WIRE_FIELD` は 8192 バイトまで名前を通すので、これは
「`setoption` の名前を素で載せる」＝ラウンド30で塞いだ現物に戻る。
掃き出し（`PENDING_LIMIT = 32`）が折れれば **262KB を一度に**書く。

`MAX_DETAIL_LEN` の doc が言う「**上限があるだけでは足りない——予算との関係を式で持つ**」が、
同じラウンドで新設した定数に適用されていない。

## 潰す範囲と契約

### R31-H4 `shown` の一本化で、**棋譜と画面に出る**値から全角スペース・結合文字・異体字セレクタが消える

3人とも指摘。`utils.rs:130-146` の `c.escape_debug().count() > 2` は
`{:?}` の膨らみを抑えるためのものだが、**`{}` で外へ出る値にも同じ潰しが掛かる**。

```
"持将棋　先手24点"     → "持将棋�先手24点"     （U+3000）
"か\u{3099}んき\u{3099}よく" → "か�んき�よく"   （macOS の NFD）
"❤\u{fe0f}"            → "❤�"                  （異体字セレクタ）
```

`endGameByRule(id, null, "持将棋　先手24点・後手27点")` は上限にも制御文字にも当たらないので、
TSDoc の断り2つ（`…` が付く／制御文字が化ける）の**どちらにも当てはまらない**。
**なぜ化けたのかを調べる手掛かりがどこにも無い。**

### R31-M1 `LOG_FILE_BUDGET` の doc の否定の一文が、直下の `MAX_SUMMARY_LEN` と矛盾している

`utils.rs:165-171`。「**外来の文字列を切り詰める他の上限はここから来ていない**」の直前に
`MAX_SUMMARY_LEN`（まさに外来の文字列を切り詰める上限）を足したので、同じ doc の中で食い違う。

### 潰す範囲を戻したので、`{:?}` を使わない側に倒した

所見は「入口の潰しとログの潰しを分ける」を薦めていた。**分けずに、膨らむ書式を
やめた。** `escape_debug` の潰しは `{:?}` の膨らみを抑えるためだけのもので、
載せる側を `{}` にすれば要らなくなる。分けると潰しが2種類になり、
どちらがどこに掛かるかを読み手が追うことになる。

### 「最悪の入力」の選び方を、4箇所で同じ形にした

`over_line` / `rejection_line` / `dropped_line` / `spawn_ok_line`。

- **入口に上限がある値**（`detail`・`setoption` の名前）は、上限の倍を入れて
  切られた結果を測る
- **入口に上限が無い値**（エンジンの名乗り）は、それだけで予算を使い切る長さを入れる。
  上限の倍で測ると、**切っていなくても予算に収まって変異が生き残る**（実際に生き残った）
- 最悪の文字は**リテラルで持つ**。被検査関数の出力から作ると、その関数の緩めを1つも落とせない

### 落ちない変異を1つ残した

`flushing_the_queue_cannot_rotate_the_log` の `PENDING_LIMIT` の掛け算は、外しても通る。
上限の不等式なので、**測る側を小さくする間違いはどんな `SHARE` を選んでも落とせない**。
両側から挟む表明にすれば落ちるが、それは書式を変えるたびに落ちる change detector になる。
テストの doc に書いて残した。

### 段の表に辺を1つ足した

`registry -> utils`。`utils` が決めるのは「ログの間引き・伏字」で、`registry` の
起動の1行はまさにそれを要る側。`utils` は `types` しか使わないので下向き。
**機械が先に止めた**（3回目）。
