### [BLOCK] 詰み判定が持ち歩の枚数で爆発する。双方が歩2枚で 66 秒かかり、`RULING_TIMEOUT`(30秒) を越える

- 場所: `src/entities/game/lib/moveValidation.ts:246-247`、`src/entities/game/lib/moveValidation.ts:194`、`src/entities/game/lib/gameOutcome.ts:128`
- 根拠:

  ```ts
  // moveValidation.ts:244-249 — 高い検査(canDropPieceAt→isUchifudume)が安い検査より先
  for (const move of allDrops) {
    if (move.kind !== kind) continue;
    if (!canDropPieceAt(shogi, kind, move.to.x, move.to.y, color)) continue;
    if (wouldBeInCheckAfterMove(shogi, move)) continue;
  ```

  ```ts
  // moveValidation.ts:194 — 打ち歩詰めの検査が、相手の合法手を「全部」作る
  const opponentMoves = getAllPossibleMoves(testShogi, opponentColor);
  ```

- なぜ問題か: `hasLegalMove` は盤上の手を先に試すので、指し手が残っている局面では
  0.012〜0.016ms で返る（実測）。**問題は合法手が無い局面**——つまり
  `judgeGameOutcome` が詰み・手詰まりを見つける、対局の最後の1手そのもの。
  そこでは駒打ちが全て数え上げられ、歩の1マスごとに `isUchifudume` →
  `getAllPossibleMoves`（相手の全手）→ その中の歩打ちごとにまた `isUchifudume` …
  と入れ子になる。写した局面の数と時間を、同じ詰み形（先手玉9一を金9八が詰め、
  角7六が支える。後手玉5一の頭5二が空いているので先手の歩打が王手になる）で
  持ち歩だけ振って測った:

  | 先手(手番)の持ち歩 | 後手の持ち歩 | `hasLegalMove` が返るまで | 局面の写し      |
  | ------------------ | ------------ | ------------------------- | --------------- |
  | 0                  | 0            | 0.7ms                     | —               |
  | 1                  | 0            | 4.7ms                     | —               |
  | 2                  | 0            | 15ms                      | —               |
  | 1                  | 1            | 86ms                      | 503回           |
  | 1                  | 3            | 3ms                       | —               |
  | 2                  | 1            | 3,002ms                   | —               |
  | 3                  | 1            | 2,975ms                   | —               |
  | **2**              | **2**        | **66,593ms**              | **1,558,624回** |

  例外は1回も出ておらず（`drop` の throw 0回、`isUchifudume` の `console.log` 0回）、
  純粋に再帰の広がりである。再帰の深さは別途 18 まで伸びることを確認した
  （双方が歩9枚の形で、20秒打ち切りまでに深さ18・全数え上げ2738回）。
  条件は「手番側が歩2枚以上」「相手も歩1枚以上」「相手玉の頭が空いていて二歩にならない」。
  **どれも実戦の詰み局面でふつうに揃う。**
  そして `judgeGameOutcome` はレンダラのメインスレッドで走り、返せなければ Rust の
  `RULING_TIMEOUT`（`src-tauri/src/engine/game/session.rs:145` の30秒）が
  `over { aborted, winner: null }` で畳む。**詰ませた瞬間に UI が固まり、
  30秒後に勝敗が消える。**

- 直し方: 2つ入れる。
  1. `moveValidation.ts:246-247` の順を入れ替え、`wouldBeInCheckAfterMove` を
     `canDropPieceAt` より先に見る。積の条件なので結果は変わらない。
     同じ詰み局面で実測 先4/後4 0.9ms、先6/後6 0.6ms（現状は先2/後2 で 66秒）
  2. `isUchifudume` の中の相手の応手検査から**駒打ちを外す**。打った歩の王手は
     玉に隣接するので合駒が利かず、逃れ手は玉の移動か歩を取る手しかない。
     併せて `getAllPossibleMoves`（`moveValidation.ts:194`）を `hasLegalMove` に替える——
     同じ答えで、実測 46.57ms → 0.104ms

### [HIGH] `judgeGameOutcome` が毎手 `Record` を根から作り直すので、1局の合計が手数の2乗で伸びる（400手で2.8秒、差分実装なら2.6ms）

- 場所: `src/entities/game/lib/gameOutcome.ts:91-107`、`src/entities/game/lib/gameOutcome.ts:119`
- 根拠:

  ```ts
  const record = new ShogiRecord(position);
  for (const [index, usiMove] of progress.usiMoves.entries()) {
    const move = record.position.createMoveByUSI(usiMove);
    if (!move || !record.append(move)) {
  ```

- なぜ問題か: 入力が `{ startSfen, usiMoves }` なので、1手ごとの裁定のたびに
  根から `append` し直す。tsshogi の `append` は1手ごとに `position.sfen` の生成、
  王手判定、`displayText` の整形を伴うので、実測 0.03〜0.04ms/手。1回の裁定は:

  | 手数 n | `judgeGameOutcome` 1回 | うち `Record` 組み立て |
  | ------ | ---------------------- | ---------------------- |
  | 0      | 0.14ms                 | 0.04ms                 |
  | 100    | 4.6ms                  | 0.40ms                 |
  | 400    | 16.0ms                 | 7.5ms                  |
  | 800    | 28.4ms                 | —                      |
  | 1600   | 42.2ms                 | —                      |
  | 2000   | 60.0ms                 | 84.6ms（別測定）       |

  毎手呼ぶので合計は2乗で効く。乱数で作った実戦形の棋譜で、全ての手について
  1回ずつ裁定した合計:

  | 対局の長さ | `judgeGameOutcome` の合計 |
  | ---------- | ------------------------- |
  | 100手      | 275ms                     |
  | 200手      | 656ms                     |
  | 300手      | 1,175ms                   |
  | 400手      | 2,839ms                   |

  同じ400手を `Record` を使い回して1回ずつ `append` した場合は **2.6ms**（約1000倍差）。
  **300手を超えると1手あたり10msを超え**（実測 400手で16ms）、既定の
  `DEFAULT_GAME_RULES.maxMoves = 1000`（`gameRules.ts:40`）まで指すと1手30ms・
  合計17秒（400手の実測から2乗で外挿）、Rust の `MAX_PLIES` = 2000 まで行くと
  1手60〜85msでメインスレッドが止まる。切れ負けの秒読みで毎手この時間を
  持っていかれる。

- 直し方: 対局セッションの間だけ `Record` を持ち回る。`GameProgress` を受ける形は
  変えずに、直前の `usiMoves` を覚えて**前方一致なら差分だけ `append`** する
  判定器を作る（`createGameOutcomeJudge(startSfen)` を返し、`judge(progress, rules)` を
  生やす形）。前方一致しなければ今の全再構築に落とせばよい。
  `entities/game-session` 側が `moveDecided` ごとに同じインスタンスを使う。

### [MEDIUM] 王手放置の検査が局面を SFEN で写し直すので、終盤の合法手列挙が 35ms かかる（`move`/`unmove` なら1桁下がる）

- 場所: `src/entities/game/lib/moveValidation.ts:15-39`（`wouldBeInCheckAfterMove`）、呼び元は `src/entities/game/lib/moveValidation.ts:223,247` と `src/entities/game/lib/shogiMoveValidator.ts:50,69`
- 根拠:

  ```ts
  const currentSfen = shogi.toSFENString();
  const testShogi = new Shogi();
  testShogi.initializeFromSFENString(currentSfen);
  ```

- なぜ問題か: 候補1手につき SFEN の生成と解析を1往復する。実測で
  移動手 0.079ms/回、歩打ち 0.014ms/回。`Shogi.prototype.drop` は内部で
  `getDropsBy` を丸ごと作り直して線形に探すため（`node_modules/shogi.js/cjs/shogi.js:153`）、
  駒打ちの検査はさらに重い。1局面の列挙で往復する回数を数えると、平手30回・
  中盤140回・終盤313回で、`getAllPossibleMoves` の時間はそれぞれ 3.0ms / 14.3ms / 35.6ms。
  **合法手が300を超える終盤（大駒と歩を持ち合う形）で 35ms** になり、
  60fps の1フレーム（16.7ms）を超える。この経路は UI から直接叩かれる——
  持ち駒をクリックすると `getLegalDropsByKind` が走り（`src/entities/game/model/provider.tsx:631` と
  同 `:189` の `useMemo` で**1クリックにつき2回**）、相手の持ち駒が20枚を超える
  入玉形で歩を選ぶと実測 46.5ms/回、つまり1クリックで約93ms 固まる。
  通常の中盤（相手の持ち駒4枚）では 3.0ms なので、効くのは持ち駒が10枚を超えてから。
- 直し方: `shogi.js` は `unmove` / `undrop` を持っている
  （`node_modules/shogi.js/cjs/shogi.js:117,165`）。写しを作らず、
  `move` → `isCheck` → `unmove`（取った駒の種類を渡す）で戻す。実測で
  移動手 0.079ms → 0.008ms、歩打ち 0.014ms → 0.003ms。
  巻き戻しは `try`/`finally` で必ず走らせること——途中で throw すると
  盤が壊れたまま呼び出し側に返る。`shogi.js` の `move` は行き所のない駒を
  黙って成らせるので、`unmove` に渡す `promote` の判定を間違えないこと。

  `legalMoves` の `useMemo` の依存だけ読んだ

  網羅的な計測はしていない。測ったのは完全な詰み局面のみ
- 計測は1台・1回ずつで、GC の揺れを均していない。表の数字には ±20% 程度のばらつきがある

## lint / hook で強制できるもの

- 「合法手が1つでもあるか」を知りたい場所で `getAllPossibleMoves(...).length === 0` /
  `.length > 0` と書くのを禁じる oxlint の `no-restricted-syntax` は書ける。
  今回の `moveValidation.ts:194` はまさにその形で、46.57ms → 0.104ms の差がある
- 上の2件（爆発と2乗）は静的検査では拾えない。**閾値付きの性能テストなら固定できる**——
  `src/entities/game/lib/__tests__/` に「双方が歩2枚の詰み局面で `judgeGameOutcome` が
  200ms 以内に返る」「400手の棋譜を毎手裁定した合計が 200ms 以内」を置けば、
  今回の 66,593ms と 2,839ms は両方とも赤くなる。数字は機械の閾値であって
  実測値ではないので、`EXPECTED_MIN` と同じくラチェットとして置くこと
