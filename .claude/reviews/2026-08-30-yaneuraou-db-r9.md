## R-01 (HIGH, rust): 閾値の直上に、R8 で塞いだのと同じ穴が残っていた → 修正済み `2e84864`

R8 P-01 の直し（`flush` でちょうどの大きさへ移し替える）は、**長い列を移し替えない
という閾値を置いたので、穴を 33 手以上の局面へ移しただけだった。** `push` の倍々
成長は `len` が2の冪を1つ超えた直後に最大の空きを残す（33 手 → 容量 64）。

実測（1局面あたりの手数を掃引）:

| 手/局面 | 9    | 32   | 33       | 65   | 257      |
| ------- | ---- | ---- | -------- | ---- | -------- |
| 修正前  | 0.72 | 0.73 | **1.20** | 1.02 | **1.34** |
| 修正後  | 0.69 | 0.62 | 0.79     | 0.70 | 0.63     |

33 手の形は見積もり/ファイルサイズ比が 9.27 なので、見積もりが 7 GiB に達するのは
ファイル 811MB 前後で `MAX_FILE_BYTES` の前段を素通りする。実物の配布定跡は
平均 7.15 手/局面なので現行の実害は無い。

**閾値を消すのではなく、空きそのものを作らない。** 溜める側を刻みで伸ばせば、
空きはその数で頭打ちになる。退化した形（1局面 × 400万手）も比 0.94 で退行しない。

`LONG_MOVE_LIST` と `SCAN_LIMIT` を同じ定数にしたのも戻した。**動かしたい向きが
逆**（走査は低くしたい／移し替えは高くしたい）で、片方を直した人がもう片方を壊す。

## 確かめて、所見にならなかったもの

- **不変条件1**: ShogiHome の実物 fixture 8本すべてが期待どおり開ける。
  v1.20.0 以前の空欄書式と行末コメントも欄がずれない
- **黙って「0局面の定跡」として開くもの**: 無い。別形式の囮28本（本物の SQLite /
  gzip / KIF / CSA / 7z / SFEN リスト …）を通して、開けたのは注記だけが Shift_JIS の
  正しい定跡1本のみ
- **panic**: release 40万件 / debug 4万件のランダム入力で panic と
  `debug_assert` の発火なし
- `first_token` の区切りは `parse_move` と揃っている。`body_started` への改名で
  条件は1つも変わっていない。3つの上限に迂回路は無い
