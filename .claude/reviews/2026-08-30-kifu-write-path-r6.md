# レビュー kifu-write-path ラウンド6

- 日付: 2026-08-30
- 範囲: `fix/kifu-write-path`（`main` = `9aa963b` からの差分）
- 走らせた reviewer: `robustness` / `react`
- 対象コミット: `109e945`
- 前ラウンド: [r5](2026-08-30-kifu-write-path-r5.md)

**2体が独立に、r5 の直しが開けた同じ BLOCK へ当てた。** どちらも probe を書いて実測している。
所見は3つの根に分かれる。

1. **預かりを「本文の一致」で捨てていた** → 保存済みの本文がディスク上で巻き戻る
2. **`background` が並行書き込みを許した** → コメントの保存が分岐の削除を取り消しうる
3. **鍵と中身の出どころが別だった** → 移った先のエディタが前の手の本文で mount される

## 所見

### [BLOCK] R6-1 保存に成功したあとも預かりが残り、次にその手を開くと**古い本文で上書きする**（2体）

- 場所: `KifuCommentNote.tsx` の成功時の破棄
- 根拠: 捨てる条件が**本文の完全一致**しかない。

  ```ts
  if (retainedRef.current.get(target.key)?.draft === text) retainedRef.current.delete(target.key);
  ```

  預かりは r5 の直しで `"skipped"` の出口からも積まれるようになった。そこで積まれるのは
  「まだ書いていない本文」なので、**利用者がその続きを書いて保存に成功すると、
  保存された本文と預かりは必ず食い違う** → 一致しないので**永久に残る**。
  掃除する場所は他に1つも無い。

  実測（**書き込みの失敗は1度も起きていない**経路）:

  ```
  3) editor initial: aaa           ← 棋譜を戻して開き直すと預かりが出る（正しい）
  4) calls: [["aaa と続き"]]        ← 書き足して自動保存が成功
  4) alert: ""                      ← 画面は完全に正常
  6) editor initial: aaa            ← 開き直すと**古い本文**が出る
  6) alert: "保存できませんでした…棋譜が切り替わったので…"
  6) calls: [["aaa と続き"],["aaa"]] ← 900ms 後に自動保存が古い本文を書く
  6) comments(memory): ["aaa"]      ← 「と続き」が消えた
  ```

- なぜ問題か: 操作は全部**正常系**。5手目に打つ → 別の棋譜をクリック（預かりに入る。
  r5 が意図した動作）→ 戻って続きを書く → 保存成功、赤い箱も消える → あとで開き直す。
  すると古い本文と「保存できませんでした」が復活し、**利用者が何もしなくても
  900ms 後に自動保存がディスクとメモリを古い本文へ潰す**。
  巻き戻しでも失敗でもなく、**成功した保存が後から取り消される**。
  しかも画面のエディタは新しい本文を出したままなので、**食い違いを知る手がかりが1つも無い**。
  ノート本体が「書いた本文はこのまま残っています」と断言している当のしくみが、
  **保存済みの本文を消す側に回っている。**
- 直し方: 破棄の判定を**預かりの実体**（参照）で行う。`await` の前に取っておき、
  戻ったときに同じものなら捨てる。`expectedJkf` / `pendingDelete.query` と同じ形で、
  このブランチで**4例目**。
- 導入コミットの sha: `40424f4`（**ラウンド5で私が**、条件付き破棄と `"skipped"` の預かりを
  同じコミットで入れた。組み合わさって初めて成立する）
- 主張を固定するテスト名: `KifuCommentNote.test.tsx`
  「預かりのあとで保存に成功したら、同じ手へ戻っても古い本文は出てこない」（変異で確認）

### [BLOCK] R6-2 `background` が並行書き込みを許し、コメントの保存が分岐の削除をディスク上で取り消しうる（robustness）

- 場所: `provider.tsx` の `edit` の `announce`、`types.ts` の `pendingWrites` の doc
- 根拠: `edit` は `background` のとき `write_started` / `write_ended` を**一度も撃たない**ので、
  コメントの自動保存（このアプリで最も頻繁に走る書き込み）は数に入らない。
  `pendingWrites === 0` かつ `isLoading === false` のまま `persistence.save` が走るのが常態になる。
  `write_kifu_to_file` は `#[command] async fn` で、**Tauri は並行に走らせる**。
- なぜ問題か: r5 の直しは「一覧の行を止めない」ことだけを狙っていたが、同時に
  **分岐の削除とコメントの自動保存が同じファイルへ同時に書けるようになった**。
  `atomic_write` なので壊れたファイルは残らないが、**後に着地したほうが勝つ**。
  コメントの保存 → 分岐の削除、の順に撃ってコメントが後に着地すると、
  **削除がディスクから消え、メモリだけ削除済みになる**。確認ダイアログは成功として閉じ、
  次に開き直すまで誰も気づかない。以前は `busy` が削除の起動そのものを止めていたので
  この重なりは作れなかった。**「起こりえない」から「起こりうる」に変わっている。**
  加えて型の doc（「走っている書き込みの本数」）が現物と食い違うので、
  `isLoading` を「書いていない」の意味で読む次の実装が入る。
- 直し方: 2つ。
  - **書き込みを `persistIfPossible` で直列化する**（5つの経路が必ず通る1点）。
    順に流せばこの並びは作れない
  - `background` は「利用者を待たせるか」だけの旗にし、**本数は常に数える**
    （`pendingWrites` と `blockingWrites` に分ける）
- 導入コミットの sha: `40424f4`（**ラウンド5で私が入れた**）
- 主張を固定するテスト名: `reducer.test.ts`「止めない書き込みも本数には数える」。
  **直列化そのものは未検証**（`GameProvider` にテストが無い → #276）

### [HIGH] R6-3 書きかけのまま別の手へ移ると、移った先のエディタが前の手の本文で mount される（react）

- 場所: `KifuCommentNote.tsx` の `key` と `initialMarkdown`
- 根拠: `key` は props（`cursor` / `absPath`）から**そのレンダで**変わるのに、
  `draft` を新しい面の値へ差し替えるのは**コミット後の効果**。
  `LexicalComposer` は `initialConfig` を `useMemo(..., [])` で1回しか読まない（現物で確認）ので、
  鍵が変わったコミットで mount した中身が最後まで残る。
  `OnChangePlugin` は `registerUpdateListener` だけで mount では発火しないので `draft` も同期し直されない。
  実測: `mount 時の initialMarkdown: ["", "5手目のメモ"]`（2つ目が7手目の面）。
- なぜ問題か: 7手目のノートに5手目の本文が出る。`draft` は空なので**画面と state が食い違う**。
  ここで1文字打つと Lexical は「5手目のメモ＋その1文字」を返すので、
  **7手目へ5手目の本文が書き込まれる**。何も打たずに閉じれば、画面に出ていた本文は跡形もなく消える。
  どちらに転ぶかを予測する手がかりが画面に無い。
  `main` は `initialMarkdown={sourceText}` だったのでこの経路は無い。**R4-3 の直しが作った穴。**
- 直し方: 面を1つの値（`Editing`）にまとめ、**レンダ中に確定させて**鍵も中身もそこから組む。
  効果で差し替えると必ず1レンダずれる。
- 導入コミットの sha: `18be853`（**ラウンド4で私が入れた**）
- 主張を固定するテスト名: `KifuCommentNote.test.tsx`
  「移った先のエディタを、前の手の本文で組まない」（変異で確認）。
  **既存のモックが `initialMarkdown` を捨てていたので、まずモックを直した**
  （mount 時の値で固定する板にした）。直す前は、鍵を props から取る変異を当てても緑のままだった

### [HIGH] R6-4 保存中に来た自動保存が黙って捨てられ、再試行も張られず、「保存済み」だけが出る（2体）

- 場所: `KifuCommentNote.tsx` の `isSaving` の門番とタイマーの効果
- 根拠: 門番は預かりに積むだけで `setSaveError` を呼ばない。
  タイマーの効果の dep は `[draft, face, dirty]` なので、**撃った自動保存が捨てられても
  3つとも変わらず、張り直されない**。実測:

  ```
  B) 2本目は撃たれたか calls: 1     ← 撃たれていない
  B) alert: ""                       ← 画面には何も出ない
  C) 保存中/保存済み: "保存済み"     ← **「あい」は書かれていないのに保存済み**
  D) 5秒待っても calls: 1            ← 再試行は無い
  ```

- なぜ問題か: 前提は「1回の保存が 900ms のデバウンスより長くかかる」で、
  ネットワーク越しのワークスペースや大きな棋譜では起こる。
  そのとき利用者が見るのは**「保存済み」**で、最後に打った文字はどこにも無い。
  #227 が塞いだ「失敗を成功と表示する」が、失敗ではなく**捨てた書き込み**の側から復活している。
  さらに、そこで積まれる預かりが **R6-1 の種**になる（成功した保存と本文が食い違うため以後ずっと残る）。
  加えて「この面で初めての失敗では閉じない」の判定材料が預かりなので、
  **見せていない skip が「1回目」を使い切る**。
- 直し方: **保存を直列化して、捨てる判断そのものを無くす**。
  前の保存が終わってから次を流せば「撃てないから捨てる」が起きない。
- 導入コミットの sha: 門番は `41bf046`（#204）だが、
  **捨てたものを預かるだけで再試行しない形にしたのは `40424f4`**（ラウンド5）
- 主張を固定するテスト名: `KifuCommentNote.test.tsx`
  「保存中に来た自動保存を捨てず、前の保存が終わってから書く」

### [HIGH] R6-5 確認を閉じられるようにしたことで、削除の失敗がどこにも出なくなった（robustness）

- 場所: `KifuStreamList.tsx` の `confirmDelete`、`ConfirmDialog.tsx`
- 根拠: r5 の直しで `closeOnEsc` / `closeOnOverlay` の制御を外したので、
  **書き込み中でも閉じられる**。一方、失敗の書き戻しは R3-2 の compare-and-swap のままで、
  閉じた後は `prev === null` なので `{...prev, error}` が**一度も評価されない**。
  `state.error` には載るが読み手は0（#277）。
- なぜ問題か: 出口を開けた理由そのものが「書き込みが返ってこない状況」だった。
  待たされた利用者が Escape で閉じ、書き込みが失敗して返ると、巻き戻しがメモリを戻すので
  **消えたはずの枝が一覧に戻る。画面には一言も出ない。**
  利用者が見るのは「削除したはずの変化が勝手に生き返った」だけ。
  巻き戻しが飛んだ場合（#301）はさらに悪く、**メモリからは消えたままディスクには残る**のに無言。
  **R5-5 が塞いだ「出口ゼロの行き止まり」が、「出口＝失敗の消滅口」に化けている。**
- 直し方: 閉じられていても失敗を出す。`error` があるとき実行ボタンは押せないので、
  r5 が禁じた「閉じた確認が復活して古い指定のまま再実行される」形にはならない。
  ただし**棋譜が変わっていたら開き直さない**（別のファイルの枝についての確認は読めない）。
  突き合わせは押した時点のパスと**返った時点**のパスで行う。
- 導入コミットの sha: `40424f4`（**ラウンド5で私が** `closeOnEsc` の制御を外した）
- 主張を固定するテスト名: **未検証**（`KifuStreamList` にテストが無い → #276）

## 検査そのものにぶつかった1件

`persistIfPossible` の中で列に流す関数を `run` と名付けたら、`asyncResultUse` の走査が
**別ファイル（`GameFileTreeBridge.tsx`）の無関係な `void run();` を落とした**。
この走査は「`AsyncResult` を返す関数の**名前**」を全ファイルから1つの集合に集めて、
その名前の裸呼び出しを探す。ローカル変数名の衝突を区別しない。

自分の側を `writeOnce` に改名して回避した。走査の作り直しはこの PR の範囲外だが、
**INDEX.md の「横断検査は最初から TypeScript の parser を使う」の実例が1つ増えた**。

## 確認して問題が無かったもの

- **`doSave` の `showing` 判定は正しい面を見ている。** `loadedFaceRef` を書き換えるのは
  面の効果1箇所だけで、`await` の前後で読み違える経路が無い
- **`finally { setIsSaving(false) }` が面をまたいでも壊れない**（`isSaving` は面の属性ではない）。
  unmount 後に撃たれても React 19 では no-op
- **`"skipped"` の預かりが `handleRequestClose` で捨てられることは無い**（`"failed"` のときだけ）
- **`retainedRef` が別のファイル・別の分岐へ漏れることは無い**（鍵が `absPath` を含む）。
  漏れるのは同じ鍵に対する**時間方向**だけ（R6-1）
- **autosave の dep に `dirty` を足してもタイマーの張り直しは増えていない**（実測）
- **`face` の identity はレンダを跨いで安定している**（`editorKey` はプリミティブな文字列）
- **`deleting` が別の削除へ持ち越されることは無い。** 確認を閉じても `deleting` は下りないが、
  その間 `state.isLoading` が真なので `busy` が新しい削除の起動を全部止める
- **`confirmDelete` の二重実行は起こせない**（`deleting` の間は実行ボタンが `disabled`）
- **`reducer.ts` の `pendingWrites` の対は揃っている。** 撃つ4経路すべてが同じ `try` の
  `finally` を持ち、早期 return は全て `write_started` より前。
  `game_loaded` / `reset_state` の持ち越しも入っている
- **`Modal` の焦点の閉じ込めは、実行ボタンが `disabled` になっても効く**
  （`FOCUSABLE` が `:disabled` を外すので `focusout` → `pullBack()` がキャンセルへ寄せる）
- **key の衝突は無い。** キーボードの登録もこの差分で増えていない
- **この差分に新しいセキュリティの口は無い。** `dangerouslySetInnerHTML` / `innerHTML` /
  `shell.open` 相当 / `localStorage` への書き込みは1つも増えていない。
  差分中の `as` はテスト用の branded 型だけ

## 6ラウンドで繰り返した形

r1→r6 まで、**毎回「前のラウンドの修正そのもの」が次の所見になった**。
r6 で分かったのは、r5 の直しが**別の穴を開けていた**こと。

- 「行を止めない」ために `background` を足したら、**並行書き込みを許した**
- 「本文を捨てない」ために預かりを増やしたら、**保存済みの本文を巻き戻す種になった**
- 「出口ゼロを塞ぐ」ために閉じられるようにしたら、**失敗の消滅口になった**

3つとも「守るものを1つ足したら、別の守りが外れた」形。
**旗を1つ増やすとき、その旗が何を止めていたのかを先に数える。**
このラウンドの直しは、パッチを足すのをやめて
**「面を1つの値にする」「書き込みを1列にする」**という不変条件の側へ寄せた。
