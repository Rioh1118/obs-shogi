## 指定された6点の確認結果（所見にならなかったもの）

**1. 駒打ちの検査順の入れ替え（`moveValidation.ts:247-253`）は結果を変えない。**
実測で確かめた。乱数プレイアウト540局面と、打ち歩詰め・二歩・行き所のない駒・
双方が歩9枚を含む手作り7局面で、旧順（`canDropPieceAt` → `wouldBeInCheckAfterMove`）と
新順の返す集合が**完全一致**（`from`/`to`/`kind`/`color` で突き合わせ）。
理由も裏が取れる —— `shogi.js` の `getDropsBy`（`node_modules/shogi.js/cjs/Shogi.js:228`）が
既に二歩と行き所のない駒を除いているので、`canDropPieceAt` がこの経路で足しているのは
`isUchifudume` だけ。両方とも写した盤で判定する副作用の無い述語なので積の順は効かない。

**2. `isUchifudume` の `!hasLegalMove(...)` は `getAllLegalMoves(...).length === 0` と同じ答え。**
同じ543局面の**全ての歩打ち候補**について1つずつ突き合わせて差分ゼロ。

**3. `reachedTrySquare` に穴は見つからなかった。** 実測:
`G*5a`（玉以外が5一へ着く駒打ち）→ `null`、`5b5a+`（玉の手に `+`）→ `unplayable_move`、
玉が5一に居るまま歩を突く → `null`、後手の `5h5i` → `tryRule/white`、
5一の駒を取って着く手 → `tryRule/black`。`endsWith` の当たり方も正しい ——
USI の移動は `from(2)+to(2)[+]` なので4文字なら末尾2文字が着地点、`+` が付く手は
玉の手ではありえない。doc の安全性の主張（「`record.append` が合法手しか積まない」）も
実測で裏が取れた —— 飛の利きへ玉を動かす `5b5a` も、王手放置の `5b5a` も `append` が `false` を返す。

**4. `USI_MOVE` は通すべき手を弾いていない。** 乱数プレイアウトで tsshogi が
`isValidMove` を通した指し手 **38,758 通り**の綴りを全て通す（弾いたものは0件）。
`5b5a+` のように正規表現を通るが局面で成立しない綴りは `record.append` が落とし、
`createMoveByUSI` は `+` を落とさず `move.usi === usiMove` を保つ（実測）ので、
r1 が心配した「読める分だけ採る」経路は塞がっている。

**5. `winner: Side` で落ちた経路は無い。** `toSide` / `fromTsColor` / `opponentOf` は
全て呼ばれていて、`perpetualCheck` の勝者を反転させる変異はテストが落とす。

**6. `unplayable_move` の `sfen` は「その手を指す直前」で正しい。**
2手目で落とす経路で `"4k4/9/9/9/9/9/9/9/5K3 w - 1"`（1手目を指した後 ＝ 2手目の直前）が返ることを実測。
なお `gameOutcome.ts:168` の `before` は**等価な変異**——`record.append` は
失敗したときに `record.position` を進めないので、3つ目の枝を
`record.position.sfen` に書き換えても全44件が緑のまま。防御としては無害だが、
「積んだ後では次の局面になる」という理由はこの枝には当たっていない。

### [MEDIUM] トライ判定の「着いたのが玉か」の検査が、テストで固定されていない

- 場所: `src/entities/game/lib/gameOutcome.ts:135-137`、
  `src/entities/game/lib/__tests__/gameOutcome.test.ts:107-140`
- 根拠:

  ```ts
  // 玉以外もその地点へ動ける。着いたのが玉であることを盤で確かめる
  const piece = shogi.get(square.x, square.y);
  return !!piece && piece.color === color && piece.kind === "OU";
  ```

  実測した変異: この行を `return !!piece;` に置き換えると、
  `gameOutcome.test.ts` / `moveValidation.test.ts` / `jishogiDeclaration.test.ts` の
  **40件が全て緑のまま通る**。トライの4本はどれも玉が動いて着く形しか使っていない。

- なぜ問題か: この行は `endsWith` の検査と**別の穴**を塞いでいる。
  `endsWith("5a")` は着地点しか見ないので、玉以外が5一へ着く手（駒打ち `G*5a`、
  飛の `5e5a`、金の `4b5a`）を全て通す。いまの実装は正しく `null` を返す
  （実測: `judgeGameOutcome({startSfen:"9/4K4/9/9/9/9/9/9/k8 b - 1", usiMoves:["G*5a"]}, {jishogiRule:"try"})`
  → `{"success":true,"data":null}`）が、**この正しさを守っているテストが1本も無い。**
  筋道: 誰かが「`endsWith` で着地点は見たのだから駒種の検査は重複」と読んで削る →
  テストは全て緑 → トライ設定の対局で、5一へ**何かを打った／動かしただけ**で
  その瞬間に勝ちになる → 利用者は盤に玉が居ないのに「トライルールで勝ち」と告げられ、
  対局が `endGameByRule` で確定する。**どこにもエラーは出ない。**
- 直し方: `gameOutcome.test.ts` の「トライルール」describe に1本足す。
  `"9/4K4/9/9/9/9/9/9/k8 b G 1"` に `usiMoves:["G*5a"]` を掛けて `null` を期待すれば、
  上の変異が赤くなる（実測で確認済み）。

### [MEDIUM] `USI_MOVE` の駒打ちと成りの枝を通る指し手列が、テストに1つも無い

- 場所: `src/entities/game/lib/gameOutcome.ts:147`、
  `src/entities/game/lib/__tests__/gameOutcome.test.ts:14-38`（局面定数）
- 根拠:

  ```ts
  const USI_MOVE = /^(?:[1-9][a-i][1-9][a-i]\+?|[PLNSGBR]\*[1-9][a-i])$/;
  ```

  `gameOutcome.test.ts` の `usiMoves` に現れる綴りは `5i4i` `5a4a` `6c5b` `8d8c`
  `9c9a` `5b5a` `5g5f` `9i8i` `5i3i` `5i4i4i` の10種だけで、
  **`*` を含む駒打ちも `+` を含む成りも1つも無い。**
  実測した変異は2つとも40件が緑のまま:
  - 駒打ちの枝を消す `/^(?:[1-9][a-i][1-9][a-i]\+?)$/`
  - 成りを消す `/^(?:[1-9][a-i][1-9][a-i]|[PLNSGBR]\*[1-9][a-i])$/`

- なぜ問題か: この正規表現は**エンジンが返した綴りを門で止める唯一の関門**で、
  弾かれた手は `unplayable_move` になる。`gameOutcome.ts:74-85` の doc は
  それを「対局を中断して利用者に見せるほかない」と定義している。
  筋道: 誰かが正規表現を絞る（駒打ちの `*` を書き落とす、`\+?` を消す）→
  テストは全て緑 → 対局で最初の駒打ちか最初の成りが出た瞬間に
  `judgeGameOutcome` が `Err` → 呼ぶ側は doc どおり `abortGame` →
  **角交換して打った1手で対局が中断され、勝敗が `winner: null` で消える。**
  いまの実装はこれを正しく通す（実測: `["7g7f","3c3d","8h2b+","3a2b","B*4e"]` は
  5手とも `Ok(null)`）ので、守られていないのは**現在の正しさ**だけである。
- 直し方: `gameOutcome.test.ts` の「局面を組み立てられないとき」の隣に、
  成りと駒打ちを含む列が通ることを見る1本を足す。上の5手をそのまま
  `expect(judge({ startSfen: HIRATE, usiMoves: [...] })).toBeNull()` にすれば
  両方の変異が赤くなる。

### [MEDIUM] 値段のラチェットは、赤くなるときは**無言で止まる**。しかも P1 の片側だけ戻すと緑のまま

- 場所: `src/entities/game/lib/__tests__/outcomeCost.test.ts:11-15`、
  `src/entities/game/lib/__tests__/outcomeCost.test.ts:52-64`
- 根拠:

  ```
   * **赤くならず、返ってこないこともある。** 数え上げは同期なので vitest の
   * 打ち切りが効かない（入れ子を戻して実測したところ 200 秒で返らなかった）。
   * この2本のどちらかで `npm run test` が止まったら、それがこの検査の赤である。
  ```

  実測（この差分の HEAD に変異を当てて計測）:

  | 変異                                                              | `2P2p` | `4P4p` | `9P9p` | 判定                        |
  | ----------------------------------------------------------------- | ------ | ------ | ------ | --------------------------- |
  | 無し（現状）                                                      | 23ms   | 1ms    | 1ms    | 緑                          |
  | 駒打ちの検査順だけ元へ戻す                                        | 13ms   | 9ms    | 2ms    | **緑**                      |
  | `isUchifudume` を `getAllLegalMoves(...).length === 0` へだけ戻す | 13ms   | 3ms    | 3ms    | **緑**                      |
  | 両方戻す                                                          | —      | —      | —      | 240秒で無出力のまま強制終了 |

  両方戻した実行の出力は `RUN v5.0.0 ...` の1行だけで、テストファイル名も
  タイムアウトの行も出ないまま240秒経過した。

- なぜ問題か: 2つある。
  1. **赤の出方が「無言のハング」**。`git commit` は `.claude/hooks/verify-gate.sh` が
     横取りして `npm run verify` を走らせるので、この状態でコミットすると
     **端末に何も出ないまま止まる。** 「どのテストで止まったか」を知る手掛かりが
     画面に1つも無く、書いてある案内（＝止まったらそれが赤）は
     `outcomeCost.test.ts` を開かないと読めない。復帰は Ctrl-C しかない。
  2. **片側だけの後退を1件も検出しない**。しかも `moveValidation.ts:247` の
     コメントは「**積の条件なので結果は変わらない**」と書いてあるので、
     次に読む人が順序を「意味の無い並び」と受け取って戻す動機がそろっている。
     戻しても緑で通り、崖の1歩手前に静かに移る。
- 直し方: 壁時計をやめて、**数え上げの回数**を固定する。
  `moveValidation.ts` にテスト専用の呼び出し回数カウンタ（`wouldBeInCheckAfterMove` の
  入口で加算し、リセットと読み出しを export）を置き、
  `judgeGameOutcome({startSfen: matedWithPawnsInHand("2P2p"), usiMoves: []}, NO_LIMIT)` の
  1回あたりの回数に上限を張る。決定的で、台の速度に依存せず、
  片側だけの後退でも回数が跳ねるので赤くなり、**同期ループを走らせないので止まらない。**
  壁時計の2本はそのまま残してよい（そちらは別の後退を拾う）。

## lint / hook で強制できるもの

- **「変異が生き残る新規分岐」を数える仕組み**。この r2 の3件はどれも
  「実装は正しいがテストが守っていない」で、`npm run verify` では区別が付かない。
  変異解析を全体に掛けるのは高いが、**この差分で入った `entities/game/lib/` の
  4ファイルに限って**手で当てた変異が3つ生き残っている。
  `.claude/knowledge/mechanization-backlog.md` に「新規モジュールへの変異当て」を
  積む価値がある（r1 でも「doc が主張しているのにテストが固定していない分岐」として
  同じ根が出ており、two-strikes に当たる）。
- **壁時計で閾値を張るテストの禁止**。`outcomeCost.test.ts` の
  `expect(elapsed).toBeLessThan(...)` は、この repo で初めて入った壁時計の閾値。
  `src/**/__tests__/**` で `performance.now()` と `toBeLessThan` を同時に含むファイルを
  走査で落とす検査を置けば、次に同じ形が増えるのをその場で止められる
  （既に `src/__tests__/cursorConstruction.test.ts` が同種の走査の前例）。
- r1 が挙げた「`catch` の握り潰し」「falsy な正常値」「`switch` の網羅」は
  この差分で解消済み、または backlog へ送られている。r2 で新しく足すものは無い。
