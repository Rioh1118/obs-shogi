### S1 — 上限ごと落としたので、深い側に同じ穴が残った

r5 は「閉じの字下げを開きに一致させることを CommonMark は求めない」を根拠に
`closeIndent >= openIndent` を外したが、**上限も一緒に落とした**。CommonMark の閉じは
「字下げ3スペースまで」で、無制限ではない。結果、フェンスの**中身**である字下げされた
バッククォート3連の行が閉じとして採用される。踏む形は「箇条書きの中のフェンスの書き方を
markdown フェンスで囲んで説明する」で、行を並べると

| 行     | 中身                                   |
| ------ | -------------------------------------- |
| 1      | バッククォート3連 + `markdown`（開き） |
| 2      | `- 例:`                                |
| 3      | （空行）                               |
| 4      | 4スペース + バッククォート3連          |
| 5      | 4スペース + `中身`                     |
| 6      | 列0 + バッククォート3連（本物の閉じ）  |
| 7 以降 | 見出しやリンクを含む本文               |

となる。4行目が閉じになり、中身が本文として漏れ、6行目の本物の閉じが**新しい開き**になって
ファイルの残り全部が空行に潰れる。r5 の Q5 が名指しした「検査が黙って盲になる」が、
浅い側から深い側へ移っただけだった。robustness が本体に一時テストを当てて実測している
（見出しもリンクも消え、`中身` だけが残る）。

**この穴は r5 が作ったものではない。** r4 の `closeIndent >= openIndent` でも
`4 >= 0` で同じく閉じるので、r4 の時点から素通りしていた。

### S2 — 直し自体は正しいが、テストが規則の実例になっていない

oss-hygiene が CommonMark 参照実装（`commonmark` npm）に掛けて確かめた。r5 が足した
テストの入力（箇条書きの中で4スペース開き・列0で閉じ）は、参照実装では
**「字下げ不足でリスト項目が終わり、そこでフェンスも終わり、列0の ``` が新しい開きになる」**
と解釈される。`[本物](real.md)` はコードブロックの中に入り、リンクにならない。
テスト名とコメントが主張する規則の実例ではない。

**修正そのものは正しい。** 規則を本当に踏む入力（開き3スペース・閉じ列0）で新旧を
突き合わせると、参照実装は `real.md` をリンクとして描き、r4 版だけが取りこぼす。

あわせて r5 報告書 Q5 の「（GitHub でも prettier でも正しく見える）markdown」は、
GitHub が使う cmark-gfm 系の解釈と食い違う。**報告書が事実に反している。**

### S3 — F4 が起きた形そのものが固定されていない

`README.md` の階層図は**コードフェンスの中**にあり、名前は裸（バッククォートもリンクも無い）。

```
L1    ├─ search.md            （未作成）インデックスと検索セッション
```

一方 `staleUncreatedNames` の `test.each` 5件はすべてコードスパン形かリンク形で、
裸の名前の行が1件も無い。走査側も「フェンスを落とさない」ことに依存しているが、
その依存を書いたコメントもテストも無い（隣のリンク検査は逆に `stripFences` を通す）。

robustness が3つの変異をすべて**生存**させた（17/17 緑のまま）:

- 正規表現をコードスパン形・リンク形だけに絞る
- 階層図の罫線（`├└│`）を含む行を無視する
- 走査側を `stripFences(...)` に通す（「リンク検査と同じくフェンスを落とすべきでは」と
  考えた人が入れる変異）

**保護があるのはリンク形と在庫表の形だけ。** この検査は r1 の F4（表はあるのに索引が
「未作成」と言い続ける）の再発防止として作られたのに、F4 が起きた形が守られていない。
r5 の Q2 で「行単位の判定」だけをモジュール直下に出し、**走査本体を出さずに止めた**ことの帰結。

### S5 — `tesuuPointer` は棋譜をまたぐと一意でない

`jkfplayer.ts` の `getTesuuPointer` は `` `${tesuu},${JSON.stringify(...)}` `` を返すので、
**どの棋譜でも開始局面は必ず `"0,[]"`**。r5 で足した `state.cursor?.tesuu` も `0 → 0` で、
この穴は塞がらない。

棋譜 A を開いて**カーソルを動かさずにホイールで一覧を流し**、ツリーで棋譜 B を選ぶと:

1. `file-tree/model/reducer.ts` の `kifu_loading` は `jkfData` を落とさず、`kifu_opened` が
   直接差し替える。よって `GameFileTreeBridge` は `resetGame()` を経由しない（実際に読んで確認）
2. `loadGame` → `game_loaded` で `cursor` は `tesuu=0` / `"0,[]"`
3. `view.player` が null を挟まないので `div.kifu__list`（`overflow: auto`）は unmount されず、
   DOM の `scrollTop` が残る
4. deps 3つとも `Object.is` で等しく、effect は走らない

盤とカーソルは B の開始局面なのに、一覧は B の 50 手目あたりを表示したままになる。
**この穴も r5 が作ったものではない**（`d8b6438` 以前から `tesuuPointer` だけを見ている）が、
このブランチはこの effect の deps を3回書き換えており、範囲の中にある。

### S6 — 「必ず連動する」は片方向しか成り立たない

成り立つのは「`tesuu` が変われば `tesuuPointer` も変わる」だけ。逆は偽で、
`tesuu=3` の本譜にいるときに te=3 の分岐メニューから変化を選ぶと、
`buildCursorWithForkSelection` が `{ tesuu: 3, forkPointers: [{te:3,forkIndex:0}] }` を返し、
**`tesuuPointer` だけが変わる**。「必ず連動する」を信じた読み手は `tesuuPointer` の方を
dep から外してよいと判断でき、外すとこの経路で追従が止まる。

`app.md` ※2 はこの差分で「`game.md` の E15 と ※4 が持つ。取得に失敗したときに旧ワークスペースへ
書き込む経路だけが未検証」に書き換わった。一方 #245 はタイトルが

「やること」に「`game.md` の E15 の行を埋める」を挙げている。**その E15 も ※4 も、いま埋まっている。**
