# レビュー: やねうら王テキスト定跡 (.db) reader — ラウンド7

対象: `feat/91-yaneuraou-db-reader`（issue #91）
観点: rust / robustness / comment（**perf はセッション上限で落ちた。ラウンド8で回す**）
基点: `c8992e7`（R6 の報告書）

所見16件（BLOCK 0 / HIGH 0 / MEDIUM 16）。**このラウンドの主題は「ガードのコードは
あるが、守るテストが別の理由で通っていた」。** 変異を1回当てれば分かるものが6件あった。

## 変異が空振りしていた境界 → 修正済み `5b559e1`

### R-01 行長の境界（H8）

`a_line_at_the_length_limit_is_accepted` の埋め文字が `#` なので、その行は**注記**。
長さの枝より先に読み捨てへ落ちるので、`>` を `>=` にずらしても 138件全緑。
R4 が「改行付きだと区別できない」に気づいて改行を外したが、**入力が注記である
ことを見落としたまま「変異が空振りした」と doc に書いていた。**

境界が効く条件は2つ（末尾に改行が無い / 注記でない）。指し手行を空白で上限
ちょうどまで伸ばす形にし、`is_note` でないことも assert で固定した。

### R-04 申告局面数の境界（H4）

既存の2本が極端な値でしか見ていない（申告 125 万対 1局面、または一致ちょうど）ので、
`<` を `+ 1 <` へずらす変異が通る。**H4 は切れの検出を単独で担う唯一の関門**
（H7 は改行の無い定跡を拒否できない）なので、境界が1つずれると最後の1局面だけ
落ちたファイルが黙って開く。

### R-02 指し手拒否の文面の引用

R6 G-02 は見出し探索側の `excerpt` を直したが、**指し手側の呼び出しはどのテスト
からも守られていなかった。** 3,000 バイトの綴りをわざわざこの経路へ通しているのに
長さを1つも見ていない。`truncate_path`（4096字）への差し替えが全緑で通る。

### R-03 `unread` の持ち越し

R6 で入れた新しい状態変数だが、`index` も `consumed` も1本も固定されていない。
どちらも**見出しの無い定跡でだけずれる**ので、見出し付きのテストしか無い状態では
壊しても気づけない。行番号を二重に進める変異と、読んだ量から落とす変異が
両方とも全緑だった。

## H-02 文面がファイルについて事実でないことを言う2経路 → 修正済み `626e97d`

**`89178f2` が文面とテストを両方消していた。** 5本のテストと2本のコンパイル時
assert を消したのと同じ範囲置換で、UTF-8 失敗の「形式違いかもしれない」という
案内（R1 A-13 の修正）も巻き込まれている。**同じコミットによる3件目の被害。**

残っているテストは行番号と「こと」しか見ないので、実測で

    gz.db → 1行目に文字として読めないバイトがある。定跡を取得し直すか、…

「文字として読めないバイト」は利用者の言葉ではないし、`.bin` を `.db` に
付け替えただけのファイルでは「取得し直す」を何度やっても直らない。

もう1件は見出しの検査を外した副作用。注記だけのファイルに「定跡ファイルが空」と
言う。**空ではない。** 利用者はエディタで中身を見てアプリの不具合と判断する。

## R-05 / H-01 局面より先の指し手の診断が、見出しの有無で割れていた → 修正済み `1fa2676`

見出し無しの側は、**誰が見てもやねうら王の指し手行を引用しながら「別の形式の
ファイルかもしれない」と言う。** R6 H-01 が HIGH として直した自己矛盾が、
指し手行に残っていた。

あわせて不変条件1の差の表に **(S2, E8) が抜けていた**。本家は
`BookMove::from_string` に渡すだけで失敗しないので、これも中身由来の差で、
しかも1行のためにファイル全体を倒す。同じファイルの `optional_number` の doc は
逆の判断を明記しているので、なぜ分かれるかを書いた。

## H-01 不可視文字が引用で見えない → 修正済み `b098fb2`

欄をタブで区切った定跡は本家なら読めるが、こちらは全体を拒否する。そのとき

    5行目が指し手として読めない（8c8d	none	1	1	1）

**引用のどこも壊れて見えない。** 制御文字を可視化する（`truncate_path` が同じ
理由で既にやっている）。実在の定跡がタブ区切りで配られているかは未確認。

## H-03 大きさの検査の呼び出し位置が無防備 → 修正済み `3cba047`

R6 A-02 で検査を形式の分岐より前へ出したが、**移した先の呼び出し自体が同じ性質の
まま**だった。既存3本はどれも `check_file_size` を直接呼ぶので、`open_reader` から
その1行を消しても全緑。sparse file（実測 0.33 ms / ディスク 0 ブロック）で
`open_reader` を通す。中身は1バイトも書いていないので、読みに行けば必ず
`InvalidContent`。つまり「読まずに落ちた」ことまで見ている。

## R-06 / H-04 一時ディレクトリの固定名 → 修正済み `106a8c1`

**両観点が独立に挙げ、片方はこのレビュー中に実際に踏んだ。** `temp_dir()` は
ワークツリーをまたいで共有されるので、worktree を並べて `verify:rust` を同時に
走らせると片方の後片付けが他方の実体を消す。出るのは非決定的な赤で、再実行で
消えるため誰も原因を追わない。レビュアーは一度これを変異の検出と誤読している。

`file_system` と `ai_library` は既にプロセス ID を混ぜていて、`book` だけが固定名
だった。共通の置き場に寄せ、`tests/temp_dir_names.rs` で機械で見る。

## G-01 コメントに経緯が混入（6箇所） → 修正済み `c448164`

所見はコメントの内容だったが、**なぜ機械で止まらなかったかを見たら、検査自体は
正しく、走っていなかった。** `commentHistory.test.ts` は `RUST_SRC` を走査対象に
含み、禁止語に「ラウンド」「残っていた」も入っている。走らなかったのは
verify-gate の分類で、`.rs` を `rust` にしか入れていないため、Rust しか触らない
コミットでは vitest が一度も走らない。**検査の置き場と走らせる条件がずれていた。**

## 機械で止まらないと分かったもの

R6 から持ち越しの宿題（表の ✓ にテスト名を書く規約）に加えて:

- **変異が空振りする境界テスト。** `cargo-mutants` を常用に入れるのは
  `verify:rust` の 2分15秒を大きく超えるので採らない。`/implement` の
  「境界を見るテストは、その境界が効く入力で書けているかを変異で確かめる」を
  実際に守るしかない（今回6件とも、変異を1回当てれば1分で分かった）
- **`excerpt` の掛け忘れ。** `Excerpt(String)` newtype にすれば `with_path` と
  同じくコンパイラが強制できる（rust reviewer の提案）。範囲外として次ラウンドへ
