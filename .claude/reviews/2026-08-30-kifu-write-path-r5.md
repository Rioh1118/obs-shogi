  alert: ""                        ← 失敗した事実も残らない

- 導入コミットの sha: 門番そのものは `41bf046`（#204）。

### [BLOCK] R5-2 出ていく面の書き込み結果が、いま画面に出ている**別の面**に着地する（2体）

- 場所: `KifuCommentNote.tsx` の `doSave` の `await` 以降
- 根拠: `doSave` は**書く先**を引数で受け取るようになったが、**書き戻す先**は受け取っていない。
  面の効果は `void doSaveRef.current(prev, …)` を撃った**直後に**同期で
  `setDraft(sourceText)` / `setSaveError(null)` を撃つので、非同期の結果は
  必ず**新しい面が描かれた後**に着地する。窓ではなく確定した順序。

  probe の実測（5手目に「Aのメモ」→ 7手目へ移動 → 保存は `Err`）:

  ```
  calls: [[5,["Aのメモ"]]]
  alert on face B: "保存できませんでした。書いた本文はこのまま残っています。boom-A…"
  editor initial: ""          ← 7手目のエディタは空
  ```

  成功も同じで、**7手目に「保存済み」が出る**（7手目には何も書いていない）。

- なぜ問題か: 3つとも別々の壊れ方をする。
  1. **箱が指している本文が画面に無い。** 利用者は7手目に書いたものが失敗したと読む
  2. **`handleRequestClose` の「初回の失敗では閉じない」が壊れる。**
     `saveError` が他の面から漏れて立っているので、7手目の**初めての**失敗が
     「2回目」と判定されて閉じ、`retainedRef` も捨てる。
     ノートは「失敗を1度は必ず見せてから閉じる」という約束を、見せていない失敗で使い切る
  3. **「保存済み」が嘘になる。** さらに `setBaseText` が別の面の本文を入れるので
     `dirty` が偽になり、その面の自動保存が根拠なく立ち上がる
- 直し方: `await` の直後に `loadedFaceRef.current?.key === target.key` を見て、
  一致するときだけ `setSaveError` / `setBaseText` / `setSavedFlash` を書く。
  預かりは面に紐づいているのでその外側で行う。
  「初回の失敗か」も `saveError` ではなく**その面の預かりがあるか**で持つ。
- 導入コミットの sha: `18be853`（**ラウンド4で私が** `doSave(target, text)` の形に変えたときに、
  書き戻す側は `target` を使っていない）
- 主張を固定するテスト名: `KifuCommentNote.test.tsx`
  「出ていく面の失敗を、移った先の面に出さない」（変異で確認）。
  **「初回の失敗か」の判定を `saveError` から預かりへ移した部分は未検証** —
  `showing` の門番を入れた時点で `saveError` は面をまたがなくなるので、
  この2つは今の配線では等価になり、変異させても落ちない。
  **直接的な表現として残してあるが、テストが固定しているのは合わせ技の結果だけ**

### [HIGH] R5-4 巻き戻しが飛んだことが呼び出し元に返らず、確認ダイアログが危険な再試行を勧める（react）

- 場所: `reducer.ts` の `jkf_restored` の早期 return、`ConfirmDialog.tsx` の文言
- 根拠: `dispatch` は成否を返さないので、`deleteBranch` の `Err` は
  「戻したうえで失敗した」と「戻さずに失敗した」の**どちらも同じ値**になる。
  受ける `confirmDelete` は区別せず、ダイアログは常に「もう一度押すとやり直します」と書く。
  再試行が当たる先の検査は `assertBranchIndex`（範囲内かだけ）。
- なぜ問題か: 削除の書き込みを待っている間に別の書き込みが `jkf_replaced` を撃つと、
  巻き戻しは `expectedJkf` 不一致で飛ぶ。メモリは変化1が消えたまま、ディスクには残っている。
  そこで再試行すると `target=1` が**変化2**に当たる。候補が2つしか残っていなければ
  `assertBranchIndex` が throw して、利用者には削除と無関係な理由が出る。
  **K2-1 が、compare-and-swap を入れたことで新しい入口から復活している。**
- 直し方: このラウンドでは**再試行を止めた**（失敗したら実行ボタンを押せなくし、
  文言を「閉じて選び直してください」にする）。閉じて選び直せば、そのときの棋譜に対して
  指定が組み直される。**「戻せたかどうか」を返す構造の直しは範囲外** → **#301 を立てた**
- 導入コミットの sha: 再試行を勧める文言は `431312a`（**ラウンド4で私が入れた**）。
  巻き戻しを条件付きにしたのは `a787119`（ラウンド3）
- 主張を固定するテスト名: **未検証**（`KifuStreamList` にテストが無い → #276）

## 重複・矛盾した所見

R5-1・R5-2・R5-3・R5-7 は2体が別経路で当てている。
R5-4（再試行が危険）と R5-5（実行中に出口が無い）は**逆向きに見えるが両立する**。
どちらも「閉じる道は常に開け、危険な再実行だけ止める」で同時に解ける。

## 確認して問題が無かったもの

- **`face` の identity はレンダを跨いで安定している。** `editorKey` は毎レンダ
  新しく作られるが**プリミティブな文字列**なので `useMemo` の比較は同値になる。
  probe で実測: 打鍵後に 300ms ごとに5回再レンダしても自動保存は1回だけ発火した
- **`doSaveRef.current = doSave` の位置は安全。** 代入はレンダ中、効果の本体はコミット後なので、
  **宣言の順序に関わらず**効果が読むのはそのレンダの `doSave`
- **`retainedRef` が別のファイルの同じ手数で復活することは無い**（`editorKeyFor` が `absPath` を含む）
- **`deleting` が普通の失敗・キャンセルで立ちっぱなしになることは無い**。
  立ちっぱなしになるのは promise が settle しないときだけ（R5-5）
- **`write_failed` の compare-and-swap が、削除の失敗を落とす経路は作れなかった。**
  削除の待ち時間に `state.jkf` を変えられるのは別の `jkf_replaced` だけで、
  盤は `Modal` で覆われ、コメントの自動保存は分岐メニューを開いた時点でタイマーが切れる
- **`write_ended` は負にならない**（`Math.max(0, …)`）
- **`ConfirmDialog` の `error` の箱は要件を満たしている**（領域の常設、独立した面、
  `:not(:empty)` の余白、OS の生文字列を日本語で挟む）
- **key の衝突は無い。** キーボードの登録もこの差分で増えていない
- **`file-tree` の新しい効果に無限ループは無い**
- **この差分に新しいセキュリティの口は無い。** `dangerouslySetInnerHTML` / `innerHTML` /
  `shell.open` 相当 / `localStorage` への書き込みは1つも増えていない。
  差分中の `as` はテスト用の branded 型2箇所だけ

## 5ラウンドで繰り返した形

r1→r2→r3→r4→r5 と、**毎回「前のラウンドの修正そのもの」が次の所見になった**。

r5 で分かったのは、r4 の直しが**半分だけ**だったこと。
`doSave(target, text)` と引数化したときに直したのは「**どこへ書くか**」だけで、

- 「**書かずに戻るときに何を残すか**」（R5-1）
- 「**書き終えたときにどこへ書き戻すか**」（R5-2）

の2つが古いまま残っていた。同じ関数の中で、同じ `target` を使えば直る場所だった。

**引数を1つ足して非同期の宛先を固定したときは、その関数の出口を全部数える。**
早期 return も、`await` の後の setState も、同じ宛先で判断しなければならない。
