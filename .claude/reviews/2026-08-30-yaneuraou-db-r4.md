## HIGH

### F-01 1行ぶんの確保が、どちらの上限にも入っていない

robustness（実測）。`check_expanded_size` は行を**受理した後**にしか走らないので、
行そのものの長さは勘定に入らない。改行を1つも含まないファイルは行＝ファイル全体
になり、`raw` と `buffer` に2部乗る。

```
2 GiB の1行ファイル（F0 をちょうど通る）
  peak memory footprint  4322772000     ← 4.32 GB
```

**上限を 4 GiB にした理由（16 GB の機械でスワップに入る）が、その上限を一度も
通らない経路でそのまま起きていた。**

→ 行長に 4 KiB の上限（F8）を掛けた。

### F-02 単価が実測の 1/1.4〜1/1.8

robustness（実測）。150 B/局面・100 B/手は定常値からの推定で、**上限が守るべき
ピークではなかった。**

```
400 万局面 / 0 手  → 1,063,749,032 バイト = 266 B/局面
1 局面 / 800 万手  → 1,151,821,056 バイト = 144 B/手
```

差は `HashMap` のバケットの空き、拡張中の旧テーブル、畳むときの一時領域。
→ 280 / 150 へ。実物の見積もりが 3.04 GB になるので上限は 6 GiB。

**6 GiB を「安全な量」と読ませない**よう doc に書いた。実物1本で 3 GB 前後を
使うのはメモリ展開の代価で、減らす道は #274。

### F-03 上限の文面が常に同じ数字を2つ出していた

robustness（実測）。検査が1件ごとに走るので、超えた瞬間の走行合計は常に上限と
ほぼ同じ。3倍・30倍・300倍の超過が全部「(100.0MB 以上 / 上限 100.0MB)」。
R3 D-05 の目的が達成されていなかった。→ ファイルの大きさを出す。

### E-01 表が実装に追いつかず、直したはずのバグを仕様として肯定していた

rust / comment。F6 が `total_moves > MAX_MOVES` のままで、**不変条件4が
「手数の上限だけだと `sfen ` 行しか無いファイルが通り抜ける」と書いていた。**
これは直した後の状態では成立せず、この文を現在の仕様として読むと
`check_expanded_size` から局面の項を落とす変更（＝退行そのもの）が表と整合する。

**表の遅れは3ラウンド連続。** 区分の立て方も直した（F6 は読んでいる最中に走る
ので、「最後に1回でいい」と読ませない）。

## 空振りした変異

**行長の境界のテストを、最初 改行付きの行で書いて空振りした。** `take` が
切っていないので `>` と `>=` を区別できない。末尾に改行が無い形に直した。

これで `/implement` に足した「期待値に検証したい当のものを使わない」と同じ型を、
**境界の条件についても踏んだ**ことになる。境界を見るテストは、その境界が
実際に効く入力で書かないと意味がない。
