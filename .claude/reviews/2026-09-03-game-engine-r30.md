## 生成源が1つに絞れた: 「ログ1行の大きさを手書きの定数で見積もる」

3人が独立に、**同じ式の別の因数**を外していると報告した。

| 因数                      | 書いてある値 | 実測                         | 誰が           |
| ------------------------- | ------------ | ---------------------------- | -------------- |
| `APPROX_LINE`（1行）      | 200 バイト   | **482**（48文字の非 ASCII）  | robustness     |
| `BYTES_PER_CHAR`（1文字） | 4 バイト     | **10**（`escape_debug`）     | rust / comment |
| `MIN_HISTORY_INTERVALS`   | 30 間隔      | 間隔の長さが式に入っていない | rust           |

3ラウンド続けて**この式の別の場所**を直している（r28 で導入、r29 で片方を直し、r30 で3つとも外れていた）。
`CLAUDE.md` の two-strikes に照らして、**見積もるのをやめる**。

**テストの中で実際の1行を `format!` で組んで測る。** そうすれば
「何バイトに膨らむか」を人が数える場所が無くなる。

## 見積もりが外れている

### R30-H1 3つの因数すべてが外れていて、保証が成り立っていない

**(a) `APPROX_LINE = 200` が実測の2.4倍外れている**（robustness、`commands/game.rs:446-467`）

`GameId::Display` が切るのは48**文字**でバイトではない。しかも
`log_rejection` の書式（`"{op} rejected game={game_id}: {e}"`）と
`Rejection::Unknown` の文言（`"unknown game: {id}"`）で、**同じ ID が1行に2回載る**。

```
uuid    : payload=116 bytes
48 emoji: payload=428 bytes   (is_safe_to_retain=true → 枠の鍵としても通る)
```

接頭辞込みで最悪 **482バイト/行**。30行/間隔で 14,460バイト → **13.8間隔で一周**。
約束している30間隔に届かない。

**(b) `BYTES_PER_CHAR = 4` が `escape_debug` の展開を見ていない**（rust / comment、`session.rs:3696-3712`）

`finish` は `detail={:?}` で出す。`shown` が潰すのは `is_control()`（Cc）だけで、
`Cf` / `Cs` / `Co` / `Cn` / `Zs` は素通りし、`Debug` が `\u{XXXX}` へ展開する。

| `detail`（512文字）                          | 実際の1行 |
| -------------------------------------------- | --------- |
| U+FEFF（BOM。文書から貼ると混入する）        | 4,199     |
| U+3000（全角スペース。日本語に普通に混ざる） | 4,104     |
| U+10FFFF                                     | **5,223** |

主張は「1/50（4,000バイト）を超えない」。**今日すでに偽**（1/38）。

rust の変異: `MAX_DETAIL_LEN` を 512 → **976** で全13スイート green。
実際の最悪は約 9,860 バイト＝予算の**1/20**。

**(c) `MIN_HISTORY_INTERVALS` が間隔の長さに掛かっていない**（rust、`commands/game.rs:445-465`）

doc は「30間隔＝30秒」と時間で語るのに、**式に `REJECTION_WARN_INTERVAL` が1度も出てこない**。

rust の変異: `REJECTION_WARN_INTERVAL` を 1秒 → 200ms で全13スイート green。
実際は 150行/秒 × 200バイト = 30KB/秒で、**約6.7秒で一周**する。

### R30-H5 `cmd_summary(SetOption)` が最大 8KB の名前を、絞りなしの `warn` に載せる

`utils.rs:191` / `protocol.rs:351` ほか。`validate_settings` が見るのは
`name.len() > MAX_WIRE_FIELD` だけなので、**ちょうど 8192 バイトの名前は通る**。

筋道: `setoption` の名前欄に8000文字を貼ったエンジンで対局を始める →
評価関数を読めずに即死 → 書き込みが EPIPE で失敗 → **1行 8.3KB の warn**。
利用者がパスを直そうとして「開始」を25回押すと、
**直そうとしている当のエラーの説明が消える。**

`LOG_FILE_BUDGET` の doc の「**外来の文字列を切り詰める他の上限はここから来ていない**」は偽——
`cmd_summary` はその10行下にある。

積み置き（`PENDING_LIMIT = 32`）の掃き出し経路（`protocol.rs:1007` ほか）に入れば
32 × 8.2KB = 262KB を**一度に**書く。そこへ入らないことを固定しているものは無い。

### R30-H4 `rejection_ops` が、`[a-z_]` 以外を含む `op` を黙って数から落とす

`commands/game.rs:413-433`。

rust の変異: `log_rejection("abort", …)` → `log_rejection("abortGame", …)` で
**全13スイート green**。`rejection_ops()` は 6 ではなく 5 を返し、上限の式が1口ぶん緩む。

**この関数を置いた理由は「手で書くと数え直されない」だった**のに、
文字種の絞りが数え直されない口をもう一度作っている。

コメントも事実と違う。走査自身から取れる `op` は空文字ではなく
`";\n        let source = include_str!("` で、落としているのは文字種の絞りのほう。
`!op.is_empty()` は対応する入力が無く実質死んでいる。

### R30-M6 手書きの字句解析を落とすラチェットは `tests/` しか見ないので、`src/` に置いた走査が素通りした

`tests/scanning/mod.rs:443-444`。`commands/game.rs` の `rejection_ops` は
まさに「走査でもないファイルがついでに数え始めた」現物で、
`rest.strip_prefix('"')` / `rest.find('"')` を持つ。
**`tests/` にあれば確実に落ちていた。**

## 分類と台帳

### R30-H2 状態遷移表の `(G2, E5)` が「何もしない。`Ok`」のまま

`docs/state-transitions/game-session.md:111`。同じ表の `(G2, E3)` は直っているのに
E5 だけ前の姿。`abort` を変えたコミットが表を触っていない。

読んだ人は「終局後の中断は `Ok`＝押しても害が無い」と判断して reject を扱わず、
未処理の promise rejection が出る。**Rust・TS・表の3つのうち表だけが逆。**

### R30-H3 `abort_within_budget` の「失敗は2通り」が3通りになり、**正常系が誤診される**

`session.rs:493-506`。`Ok(Err(e))` の腕のコメントは
「セッションのタスクが先に居なくなった」だけを名乗るが、
いまは `ALREADY_OVER` も同じ腕に落ちる——**投了や詰みで終わった対局を閉じる
すべての正常系**がここを通り、`close: nothing to abort: game is already over` が
毎回 `debug` に出る。

doc は「分類を2箇所に書かない。書くと片方だけ増える」と自分で予告していて、
**その予告どおりに増えていない。**

### R30-M7 台帳 F-28 に `game is already over` が無く、復帰導線がこの断りに当てはまらない

`failure-surfacing.md:100`。列挙する断りの理由8つに終局済みが入っていない。
右の欄は「操作をやり直す」だが、`Phase::Over` は吸収状態なので
**何度押しても同じ `Err`**——行き止まりのボタンができる。
正しい導線は「`over` の結末を採る」で、`abortGame` の TSDoc はそう書いている。

## doc が現物と食い違う

### R30-M1 新しいテストの doc が、直す前の実装を過去形で語っている

`session.rs:3740`「**`abort` だけ `Ok` を返していた。**」

ラウンド29は同じ形を3箇所落としたコミットを持っているのに、
**同じラウンドの別コミットが新しい1件を足している。**

### R30-M2 落とした「1間隔の予算」を、テストの本文コメントがまだ動いている機構として説明している

`commands/game.rs:529`「窓が開いて**予算が戻り**、空いた枠も落とされるので」。
`window` / `spent` は `git grep` で0件。同じ構造体の doc は逆に
「**行数の上限を別に持たない**」と書いている。

### R30-M3 `LOG_FILE_BUDGET` が名指しで禁じている「数字の写し」が、同じラウンドで新しく増えた

`commands/game.rs:442`「**200KB** を200バイトの行で割ると千行しか入らない」。

R28-M4 が7箇所を潰し、R29-M3 が最後の1つを潰した直後に、
**その作業を書いた側が同じファイルで写しを作っている。**

### R30-M4 `shown` の doc は「ログや断り文句へ載せてよい写し」だが、**棋譜に載る値にも使っている**

`session.rs:1026` で `detail` に掛けた結果は `Phase::Over` に保持され、
`Over` イベントでフロントへ返り、`snapshot` が複製する。

筋道: `endGameByRule(id, null, "持将棋\n先手24点・後手27点")`（上限に遠く届かない普通の文言）
→ 届く `detail` は `"持将棋\u{fffd}先手24点・後手27点"`。**改行が化ける。**
上限を超えていないので TSDoc の警告（`…` が付く）に当てはまらず、
**なぜ化けたのかを調べる手掛かりがどこにも無い。**

### R30-M5 TS の「1/50」が、割る相手を変えたまま写っている

Rust は「1行が**ログの予算**の1/50」（＝4,000バイト）、
TS は「人が読む文言は**上限**の1/50も使わない」（＝512文字の1/50＝約10文字）。

TS 側だけ読んだ人は余裕を約10文字と見積もり、
「千日手（連続王手）」（9文字）を「上限に近い」と判断して自前で切り詰め始める。

### R30-M8 `expect_err` の書式引数が展開されず、落ちてもどの操作か分からない

`session.rs:3745-3773`。`Result::expect_err` は `&str` を取るだけなので、
実際の出力は `終局済みの対局で {command} が通っている: ()`。
**3つを回す唯一の目的が「どれが揃わなくなったか」なのに、その1語が出ない。**

名前も広すぎる。終局後の `submit_move` は `"not waiting for a move"`、
`continue_game` は `"not awaiting a ruling"` を返して**揃っていない**。

### R30-M9 `MAX_USI_MOVE_LEN`（バイト）を `shown` の文字数の引数に渡している

`session.rs:2049`。直前の `usi_move.len() > MAX_USI_MOVE_LEN` で弾いているので
いまは一度も切れないが、単位が違う定数が渡っている事実は残る。
