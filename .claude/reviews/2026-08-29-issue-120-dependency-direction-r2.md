## ラウンド1の修正が入れた不具合

### [HIGH] 世代ガードが送信そのものを止めていた（react / robustness が独立に到達）

- 場所: `useEnginePositionSync.ts` の送信ループ
- 中身: 世代を**ループ単位**で捕まえ、不一致で `return` していた。`return` はキューを
  消費せずにループを抜け、`finally` が `inFlightRef` を null にするため、
  切替後に積み直された局面を誰も引かなくなる。
- 帰結: 送信中にエンジンを切り替えると、**新しいエンジンに局面が一度も入らない。**
  `syncedSfen` は null で固定され、解析の同期待ちが通らない。
- **`main` からの後退だった。** 修正前のループは `return` を持たないため、切替後に
  キューを引いて2回目の送信を行っていた。HIGH-3 の中身は「間違った engineKey を書く」で
  あって、送信自体は届いていた。世代ガードの導入でそれが「そもそも送らない」に置き換わった。
- 結果: 対応済み（`09095b8`）。世代は周回ごとに読み、不一致なら `continue`。
  無効化するのは書き戻しであって、キューの消化ではない。
  **私自身でも独立に再現を確認した**（送信履歴 `["SFEN-1"]`、最終 `syncedSfen` は `null`）。

### [HIGH] レイヤ規則に、実際に使われている書き方の穴があった（architecture）

- 場所: `vite.config.ts`
- 中身: 規則は `@/{上位レイヤ}/**` と `../../**` の2本だけだった。レイヤ直下のファイルからは
  `../` **1段**で隣のレイヤに届くため、どちらにも当たらない。
- 帰結: `src/pages/` には直下のファイルが5つあり、`AppLayout.tsx` は既に `../widgets/...` の
  書き癖を持っている。同じ書き方で `../app/...` と書けば、**lint も CI も通ったまま**
  上向き import が入る。ラウンド1の HIGH-1 が指摘した穴が、深さ1に限って塞がっていなかった。
- 結果: 対応済み（`5926676`）。各レイヤの group に `../{上位レイヤ}/**` を並べた。
  プローブで修正前 exit=0 / 修正後 exit=1 を確認した。

**この2件は、ラウンド1の「対応済み」がラウンド2を通さずには信用できないことの実例。**

## ラウンド1では見えていなかった不具合

### [HIGH] 送信が失敗した最中に盤を進めると、新しい局面が黙って捨てられる（robustness）

- HIGH-4 の修正で `queuedSfenRef.current = null` を throw の直前に置いていたが、
  捨てるべきは失敗した target であって、その後に積まれた最新ではない。
- 帰結: 盤は P2、ペインは P1 の候補手、ヘッダは「解析中」、エラーは一切出ない。
- 結果: 対応済み（`09095b8`）。キューを捨てず、失敗は保持して周回の最後に投げる。

### [HIGH] engineKey が変わらないエンジン再起動で「送れていないのに送れたことになる」（react / robustness）

- `engineKey` は `selectedPresetId@selectedPresetVersion` なので、AI ルートの変更のように
  `runtimeConfig` だけが変わる場合はエンジンが再起動しても engineKey は不変。
  無効化の契機を engineKey 1つに絞っていたため、新しいプロセスに `position` が一度も送られない。
- **`main` にも同じ構造がある**（この変更で入った不具合ではない）が、同期状態の唯一の真実の源が
  `syncedSfenRef` になった以上、契機が足りていない。
- 結果: 対応済み（`09095b8`）。`isReady` の false→true でも無効化する。

### [HIGH] 自動再開の同期待ちには打ち切りが無く、失敗すると 16ms ごとに永久に回る（robustness）

- HIGH-4 の修正は**手動開始経路にだけ**上限を入れた。解析中の局面追従（`runRestart`）には
  上限もエラー化も無いままで、片方だけが守られている非対称が生まれていた。
- 結果: 対応済み（`2f45ca4`）。手動開始と同じ定数で打ち切り、`set_error` に記録して止める。

### [HIGH] 棋譜リストの行の memo が、インライン関数2本で完全に無効化されていた（perf）

- `KifuMoveCard` は memo だが、12個のハンドラのうち2本だけがインラインのアロー関数。
  中身は既に `useCallback` なので、被せていた分だけが無駄だった。
- 実測（reviewer による）: 300手のとき駒クリック1回で Card の再レンダが **301回**。
  安定参照にすると **0回**。1クリックが1フレームに並ぶのは手数300前後から。
- MEDIUM-7 で `entities/game` 側は直っていたが、リスト側にこれが残っていたため
  「駒をクリックしただけで再レンダする」が完全には消えていなかった。
- 結果: 対応済み（`a23018b`）。

### [HIGH] `currentSfen` の `|| 1` のコメントが、規約が禁じる形かつ理由が落ちていた（comment）

- 「既存の挙動」は由来であって理由ではない。本当の理由（SFEN の手数フィールドは 1 始まりで、
  `tesuu 0` をそのまま渡すと USI 側で不正な position になる）が書かれていなかった。
  `shogi.js` の `toSFENString` の既定値が `moveCount = 1` であることで裏を取った。
- 結果: 対応済み（`306a96a`）。

### [MEDIUM] 値の変わらない dispatch が全消費者を再レンダさせていた（perf）

- `clear_selection` / `clear_error` / `set_loading` が、値が変わらない場合も新しい
  オブジェクトを返していた。`state` は `contextValue` の依存32個のうち
  「値が変わらなくても identity が変わる」唯一の入口。
- 実際に起きる経路: 空きマスのクリック、棋譜リストでいま居る行のクリック。
- 結果: 対応済み（`7ecfa3c`）。純関数なので**先にテストを書いて落ちることを確認**してから直した。

### [MEDIUM] エンジン切替のテストが2つの失敗を区別できていなかった（react）

- 「`syncedSfen` が null のまま」は (a) 古い書き戻しを捨てた場合と
  (b) 新エンジンへ二度と送らなくなった場合の**両方で成立する**。実際 (b) を素通しした。
- 結果: 対応済み（`09095b8`）。「B への送信が始まっている」と「最終的に立つ」を併記した。

### [MEDIUM] コメント・命名（comment、10件）

`306a96a` でまとめて対応。詳細はコミットメッセージにある。主なもの:

- `useEnginePositionSync` の doc に契約が無かった。特に**アプリ全体で1箇所だけが
  マウントすること**（送信の直列化はインスタンス単位だがエンジンはプロセス1本）
- `DirectoryNode` のコメントが「評価順によっては undefined になる」と、
  **実際には起きていない失敗**を理由に挙げていた（関数宣言なので巻き上げで解決される）。
  禁じているのは `import/no-cycle`
- `renderChild` が key を付ける責務を持つのに型にもコメントにも無かった
- 同期待ちの `2000` が「待ち時間」から「失敗を出す閾値」に格上げされたのに根拠が無かった
- `positionView` → `cursorView`、`applySynced` → `markSynced` / `invalidateSynced`
- `layerBoundaries` の添字合わせ（`slice(1)` 後の `i` が元配列の `i+1`）を `depth` で消した
