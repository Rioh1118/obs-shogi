## 私が作った退行

### C-01 [BLOCK] テスト5本とコンパイル時 assert 2本を消していた

comment。`89178f2`（注記の文字コードの修正）で編集スクリプトのスパン置換を使い、
アンカーの間に挟まっていたテストを巻き添えで消していた。

```
a_book_with_too_many_moves_is_refused                        （MAX_MOVES）
a_book_at_the_move_limit_is_accepted                         （その境界）
a_file_cut_mid_line_is_rejected_even_without_a_declared_count（切れ検出）
a_file_ending_with_a_newline_is_accepted
a_declared_count_of_zero_does_not_bypass_the_empty_check     （# NOE:0 の迂回）
const _: () = assert!(REAL_BOOK_BYTES * 2 < MAX_FILE_BYTES);
const _: () = assert!(REAL_BOOK_MOVES < MAX_MOVES);
```

**同じコミットで別のテストを足していたので本数が減らず気づけなかった。**
ガードのコード自体は残っていたが、それを外す変更が緑で通る状態だった。
ラウンド2の報告書は、この状態で「変異で確認済み」と書いていた。

→ 復元して変異を当て直した。再発防止に `#[test]` の本数のラチェット
（`src-tauri/tests/test_count_ratchet.rs`）を入れた。**カバレッジでは代わりに
ならない** — 落ちるのは「コードが実行されなくなったとき」で、ここで起きたのは
「守るテストだけが消えたとき」。

### C-05 [HIGH] 「二乗にしない」修正が26倍遅くしていた

rust（実測）。R2 B-07 で `existing.append(buffered); keep_first_of_each_move(existing)`
と書いたが、併合1回あたりの仕事が `existing.len()` に比例するので**二乗のまま**。
しかも `HashSet` の枝が毎回全要素を clone するので定数が桁で悪化していた。

| ブロック数 | 私の「修正」後 | 修正前 |
| ---------- | -------------- | ------ |
| 10,000     | 18.8 s         | 0.34 s |
| 40,000     | 412 s          | 38.9 s |

→ 畳むのを読み切った後の1回にした。robustness の再測で
20,000 / 40,000 / 80,000 ブロック = 54.9ms / 103.4ms / 206.5ms（線形）。

### D-01 [BLOCK] `# NOE:` があると切れ検出が丸ごと消える

robustness。**この回の `7ea591e` で私が入れた。** `complete_by_declaration` を
`sfen_lines >= count` で置いたので、切れたファイルに `# NOE:1` を1行足すだけで開く。

```
切れたファイル（NOE 無し）          → ERR
同じファイルに # NOE:0 を足しただけ → OK positions=1
実物を 100MB で切ったもの + # NOE:1 → OK positions=507424
```

`# NOE:0` の迂回を塞いだコメントの2行下で、同じ失敗を繰り返していた。

### C-06 / C-07 [MEDIUM] 完全な定跡を「切れている」と診断していた

rust。注記や空行で終わるファイル、字下げした注記が別の文字コードの場合。
→ 直した（データ行だけを見る / `is_note` を1箇所に切り出す）。

## レビュアーが見つけた設計の誤り

### D-04 [HIGH] 改行終端は切れの根拠にならない（両方向に外れる）

robustness（実測）。

- **拒否の側**: 本家は末尾の改行を要求しない（`book.cpp:705`）。改行が無いだけの
  完全な定跡を拒否していた。復帰操作「末尾に改行を足すこと」は 470MB の
  ファイルでは編集ソフトが開けないので実行もできない
- **見逃しの側**: 行境界でちょうど切れたファイルは素通りする。実物を 100MB で切り、
  28 バイト戻して行境界に合わせただけで `OK positions=507424`。
  **行単位で書き出す生成器が止まった場合は必ず行境界で終わる**ので、
  その経路は 100% 検出できない

→ `log::warn!` に落とし、拒否はやめた。切れの検出は申告との突き合わせだけが担う。

### D-02 [HIGH] 件数では確保の上界にならない

robustness（実測）。`MAX_MOVES` は指し手しか数えないので、**局面だけのファイルは
一度も当たらない。**

```
831.0 MB / 20,000,000 局面 / 0 手 → ピーク確保 3.07 GB で成功
```

ファイルサイズの上限まで伸ばすと約 7.9 GB。→ バイトの見積もりに一本化した
（局面 150 バイト / 指し手 100 バイト、実測）。

### D-03 [HIGH] 実物の手数が実測より 43% 少なかった

robustness。`REAL_BOOK_MOVES` を 1,125 万手としていたが、実測 **16,097,817 手**
（1局面あたり 7.15 手）。`MAX_MOVES = 2,000 万` の余裕は 1.24 倍しか無く、
B-05 で 512 MiB を捨てた理由がそのまま手数側に残っていた。
→ 上限を 4 GiB（展開後のバイト）にし、実物の2倍の余裕をコンパイル時 assert で要求。

### C-02 / C-03 / C-04 [BLOCK / HIGH] 表が実装より古く、古い側を信じると壊れる

comment / rust。F5 の式が B-06 で捨てた条件のまま、F6 / F7 が表に無い、
不変条件4が偽、「埋まっていないセル」の4件が全てテスト済み。
→ 直した。**「埋まっていないセル」は作業リストなので、埋まっているものを
並べると本当に空いている箇所が指名されない。**

### D-05 [MEDIUM] 上限の文面に実数が無い

robustness。大きさ側は実数と上限の両方を出すのに、手数側は上限しか出さない。
「あと少しなのか桁違いなのか」が分からず、「より小さい定跡を開く」を実行する
当てが無い。→ 見積もりバイトへの一本化と同時に直した。

## 空振りした変異

**`REAL_BOOK_MOVES` を古い値へ戻す変異は落ちない。** 上限に余裕がある間は、
間違った実測値を書いても assert が通る。**定数の値が実測と合っているかは
機械では守れない。** 一次資料の表に実測値を1行足し、定数のコメントからそこを
指す形にした。
