**2体とも、r6 で入れた直列化に BLOCK を当てた。** どちらも
**本物の `GameProvider` を render した probe** で実測している。

r6 は「パッチをやめて不変条件へ寄せた」と宣言した。寄せ先は2つで、
**片方は成り立ち、片方は成り立っていなかった**。

- 「**面を1つの値にする**」は成り立った。鍵と中身が1レンダずれる穴（R6-3）は塞がっている。
  ただし**失敗まで同じ値に畳んだ**ので、失敗が dep に載って毎秒の再試行になった（R7-4）
- 「**書き込みを1列にする**」は成り立っていない。列にすると「撃った時点」と
  「走る時点」が離れるのに、**列に積む側は撃った時点の closure を持ったまま**、
  **門番は走る時点の値だけを見る**。どちらで判断するかが1つの列の中で2通りに割れていた

### [BLOCK] R7-1 列で待った書き込みが、待っている間に開いた**別のファイル**へ前の棋譜を書き込む（2体）

- 場所: `provider.tsx` の `persistIfPossible` / `destRef`
- 根拠: 門番は `persistence.absPath !== loadedAbsPath` を**走る時点**で比べる。
  しかしこの2つは**同じ方向へ一緒に動く**（ツリーで別の棋譜を押せば両方 b.kif になる）。
  比べていないのは `jkfToSave` が**どのファイルの棋譜か**。
  列に入る前は「読んだ次のマイクロタスクで書く」だったので実質ずれようが無かったが、
  列に入れたことで**任意に遅れる**ようになった。

  本物の `GameProvider` を render した実測:

  ```
  queued. toA: 1 toB: 0
  switched. loadedAbsPath: /ws/b.kif
  toA: 1 toB: 1
  b.kif へ書かれた header: [{"tag":"A"}]   ← a.kif の棋譜が b.kif に入った
  state.error: null                         ← 門番は素通し。失敗もしていない
  ```

- なぜ問題か: **#245 / #204 がこのブランチで塞いだ「前の棋譜が新しく開いたファイルへ入る」
  そのもの**が、同じ関数の同じ門番の下で再現する。しかも今度は `atomic_write` が
  正常に完了するので、**b.kif は丸ごと a.kif の中身に置き換わる**。
  失敗ではないので `jkf_restored` も `write_failed` も走らず、`state.error` も null。
  巻き戻しも無い。**次に b.kif を開き直すまで誰も気づかず、取り戻す手段はアプリ内に無い。**
  門番のコメントは「ここは5つの書き込み経路が必ず通るので、門番はここ1つで足りる」と
  宣言していたが、守れるのは「橋渡しの effect が走る前の1コミットぶんのずれ」だけだった。
- 直し方: **荷物と宛先を同じ時刻で固定する**（列に入れる前に `destRef` から取る）。
  そのうえで走る時点に compare-and-swap を足し、宛先が変わっていたら書かない。
  このブランチには同じ形の正しい例が4つある（`expectedJkf` / `pendingDelete.query` /
  `face.key` / `dropUnsavedDraftIfUnchanged`）ので**5例目**。
- 導入コミットの sha: `b102ead`（**ラウンド6で私が**列と `destRef` を入れた）

  ```

  B queued. saves: 1                ← 次の自動保存が**列で待つ**
  ```

### [HIGH] R7-3 1本でも返らない書き込みがあると、以後の書き込みが**すべて無言で消える**（robustness）

- 場所: `provider.tsx` の `writeChainRef`、`reducer.ts` の持ち越し

  ```

  after move.  saved:1 pending:2 blocking:1 isLoading:true  error:null moves:2
  after reset. pending:2 blocking:1 isLoading:true
  ```

- なぜ問題か: 刺さるのは**コメントの自動保存**（最も頻繁に走り、`background` なので
  起動した合図すら無い）で足りる。条件（NFS / SMB、他プロセスが掴んでいる、fsync が
  返らない）は R5-5 でこのブランチが既に認めている。

  画面には `error: null`、赤い箱も無し。棋譜一覧は全行 `disabled` になったきり戻らない。

### [HIGH] R7-4 書けない棋譜では、**1回の打鍵が毎秒1本の書き込みを永久に撃ち続ける**（react）

- 場所: `KifuCommentNote.tsx` の自動保存の効果（dep が `[editing, dirty]`）
- 根拠: 失敗すると `setEditing((e) => ({ ...e, error }))` が**毎回新しいオブジェクト**を作る。
  理由が同じ文字列でも identity は変わるので効果が張り直される。
  `dirty` は書けていないので真のまま → 900ms 後にまた撃つ → また失敗。実測:

  ```
  打鍵から 1秒後: 1 / 2秒後: 2 / 3秒後: 3 / 4秒後: 4 / 5秒後: 5
  （対照・成功する棋譜）1秒後: 1 / 2秒後: 1 / 3秒後: 1
  ```

- なぜ問題か: 読み取り専用の棋譜でノートを開いたまま席を立つと、
  **アプリが毎秒 Tauri の `invoke` を撃ち続ける**。1本ごとに `cloneJkf`（棋譜まるごとの
  deep copy）＋ `jkf_replaced` ＋ `jkf_restored` が走るので、盤・一覧・エンジン同期まで
  毎秒作り直される。ネットワーク越しなら毎秒 I/O を叩く。
  画面の文言は「**続けて書けば保存し直します**」で、自動で再試行しないと宣言している。
  **画面の説明とコードの挙動が逆。**
  r5 の dep は `[draft, face, dirty]` で `saveError` は別の state だったので起きなかった。
  **「面を1つの値にまとめる」ことで、失敗も dep に混入した。**
- 直し方: dep を `[editing?.face.key, editing?.draft, dirty]` に絞り、
  同じ理由では `editing` の identity も変えない。
- 導入コミットの sha: `b102ead`（**ラウンド6で私が入れた**）
- 主張を固定するテスト名: **未検証**

## 確認して問題が無かったもの

- **`writeChainRef` は例外で壊れない**（rejected 側にも同じ関数を繋いである）。

  `StrictMode` はこのアプリで有効になっていない（`main.tsx` に記述無し）

## lint / hook で強制できるもの

- **`Promise` の列に積む関数が、closure で捕まえた「実行の実体」を呼んでいる形**（R7-2）。
  列に積む関数が触ってよいのは引数と ref だけ。このブランチは `destRef` / `saveRef` /
  `commitRef` で正しい形を3つ持っているので照合の基準もある
- **`await` を跨いだ compare-and-swap で、比べている2つが「同じ向きに動く値」になっている形**（R7-1）。
  「撃った時点の値を1つも保存していない compare」は検出できる
- **`useEffect` の dep に、その効果自身の副作用が書き換える state が入っている形**（R7-4）
- **`Promise` の列に時間切れも打ち切りも無い形**（R7-3）
- **同じ鍵に対して「新しいほうを残す」と「古いほうを残す」が同じファイルに同居している形**（R7-5）
- **`setState` と親の `onClose()` を同じ続きで撃って、その `setState` を後続の効果が
  読む前提になっている形**（R7-7）。バッチにまとまる以上コミットされない
- **モジュールスコープの `Map` に、アプリ自身が振り直す番号を鍵として入れている形**（R7-8）
- **テストのモックが `onClose` を `vi.fn()` で受けきっていて、親の state を落とす配線を
  再現していない形**（R7-7）。**r6 が実測を誤ったのはこれが原因で、
  probe が緑だったことが「直った」の根拠にならなかった唯一の例**
