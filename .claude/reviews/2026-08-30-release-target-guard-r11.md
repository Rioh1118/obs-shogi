## 所見

### [MEDIUM] R11-1 空打ちの `latest.json` の受入が、11本の url のうち1本しか見ていない

- 場所: `docs/RELEASE.md` の空打ちの確認 3.
- 根拠: 手順は「2本目が `200` を返すこと」しか要求していない。
  一方、同じ文書は「`platforms` は bundle ごとに分かれた**11個の鍵**を持つ」と書き、
  さらに「1つの run の中の4ジョブが同じ `latest.json` を触ることへの保護は無い」
  「`tauri-action` は read-modify-write で排他は無い」と、
  **この受入手順が唯一の観測手段である故障**を明示している。
  実物で数えて11個であることと、鍵名が文書の列挙と一致することを確認した。
- なぜ問題か: read-modify-write が競り負けたときの結果は「url が壊れる」ではなく
  **「鍵が丸ごと落ちる」**。落ちた側のプラットフォームでは更新の確認が「更新なし」を
  返すだけで、`useUpdater` はそれを `idle` として捨てる。**エラーはどこにも出ない。**
  手順どおり撃った人は11本の url が流れるのを眺め、先頭（`darwin-aarch64`）を1つ叩いて
  200 を確認し、緑と判断する。**Windows の鍵が落ちていても受入は通り**、
  その版以降 Windows の利用者は永久に更新を受け取らない。
  受入手順が、同じ文書が「保護が無い」と宣言している唯一の故障を**構造的に見逃す**形だった。
- 直し方: 鍵の数を先に固定し、全 url を叩いて全行 200 を見る。
- 導入コミットの sha: `24a3832`（「<上の url の1つ>」ごとラウンド5で入った）。
  curl の形は `337d820` で直したが、**1本しか見ない点はそのまま残っていた**
- 主張を固定するテスト名: 未検証（`docs/` の手順）

### [MEDIUM] R11-2 退避した `notes.md` を戻す手順が無い

- 場所: `docs/RELEASE.md` の「出し方」と「リリースごと作り直す場合」
- 根拠: 両方とも本文を**取り出す**コマンドで終わっており、`notes.md` はそれ以降
  どこにも出てこない。この文書は他のすべての操作にコマンドを添える方針で統一されている
  （R8-3 で明示）。`gh release edit --notes-file` は実在する。
- なぜ問題か: 手順どおり動くと最後まで復元されない。
  本文を退避 → リリース削除 → 同じタグで dispatch → `createRelease` を通るので
  body は placeholder に戻る。手順はここで終わっているので、
  **100行のノートは作業者のローカルの `notes.md` に残ったまま、
  リリースは placeholder のまま公開される。**
  そこは README の「Releases からダウンロード」と SECURITY.md の
  「サポートしているのは最新版のみ」が両方指す先。
  **R10-1 が防ごうとした「ノートが失われた状態のリリースが公開される」に、
  経路を変えて到達している**（消滅ではなく未復元なので回復可能）。
- 直し方: 両方に戻す側（`gh release edit --notes-file`）を書く。
- 導入コミットの sha: `23482e1`（**このラウンドの直しで入った**）
- 主張を固定するテスト名: 未検証

## このラウンドで分かったこと

r10 で「文書が『毎回やっていること』を書いていない」を直したら、r11 では
**「書いた手順が、その文書自身が挙げている故障を見逃す」**が出た。

どちらも「yml が何をするか」は正しく書けていて、
**yml がやらないこと（人が確かめる、人がノートを書く）の書き方が足りない**という同じ形。
受入手順を書くときは、**その文書が「保護が無い」と認めている故障を、
その手順が観測できるか**を確かめる。
