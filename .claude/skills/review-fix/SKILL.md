レビュー報告書の所見を**1件ずつ**直す。まとめて直さない。

## 手順1: 対象を選ぶ

`.claude/reviews/` の最新の報告書を読む。`$ARGUMENTS` が指す所見を取る。
未指定なら**報告書の「修正計画」の順**に上から取る。

**計画が無いなら先に `/review-plan` を呼ぶ。** 深刻度の並びを順序に読み替えて始めない。
束ねと順序の根拠はそちらが持っている。

取る前に、その所見が**まだ有効か**を確認する。報告書が指す `path:line` を実際に開いて、
指摘された状態が今も存在することを確かめる。既に直っていれば報告書に「解消済み」と追記して次へ。

## 手順2: 直す前に判断する

所見をそのまま実装しない。次を順に問う:

1. **これは lint / hook / 型で機械的に防げないか。** 防げるなら、個別の修正より先にそちらを入れる。
   人の注意に頼るルールは守られない
2. **同種の問題が他にもないか。** 1箇所だけ直すと不整合が増える。範囲を確定してから直す
3. **これは純関数か。** 純関数の壊れやすい挙動なら、**先にテストを書いて落ちることを確認**してから直す。
   このプロジェクトはテストが実質無いので、直した箇所から埋めていく
4. **所見に納得できないなら直さない。** 報告書に反論を書き、理由を残して見送る。
   レビュアーが間違っていることはある

## 手順3: 直す

1所見 = 1コミット。範囲を広げない。ついでの整形・ついでの改名をしない。

## 手順4: 検証してコミットする

`npm run verify`（TS を触ったなら）/ `npm run verify:rust`（Rust を触ったなら）を通す。
PreToolUse フックが commit 時に自動で走るので、落ちればコミットは止まる。**止まったら直す。飛ばさない。**

コミットメッセージ:

```
<type>: <所見の要約>

レビュー <報告書のファイル名> の所見 <番号> に対応。
<何を変えたか / なぜこの直し方にしたか>
```

## 手順5: 報告書に結果を書き戻す

該当の所見に追記する。

```
- 結果: 対応済み（<何をしたか1行>） / 見送り（理由） / 解消済み
  （**短ハッシュと1行の説明を併記する。** ハッシュだけだと rebase で到達できなくなり、
  説明だけだと後から突き合わせられない。ハッシュがあったおかげで
  「別のコミットの手柄を書いていた」を次のラウンドで拾えた）
```

## 手順6: 次へ

計画に残りがあれば手順1に戻る。
消化し切ったら**再度 `/review-round` を走らせる。** そのとき計画の
「次ラウンドの焦点」を reviewer へ渡す（`/review-round` 手順3）。
修正で新しい問題が入っていないかを見るため、
このループは「指摘がゼロのラウンドが1回出る」まで終わらない。

**計画に無いものを直したなら、報告書の計画へ後から書き足す。**
計画と履歴が食い違うと、次のラウンドが何を見ればよいか決められなくなる。

## 禁止事項

- 複数の所見を1コミットにまとめる
- **修正計画を読まずに始める**（無いなら作らせる。`/review-plan`）
- 検証を通さずに「完了」と報告する。通していないなら「未検証」と書く
- テストを弱めて所見を消す
- 報告書を更新せずに次へ進む
