レビューは**2巡で終わる**。所見が尽きるまでは回さない。

## なぜ2巡か

**LLM のレビューは収束しない。** 実測（275本の報告書）:

- 最長は `book-to-main` の**46ラウンド**。うち **r7〜r19 は13ラウンド連続で
  「このラウンドで新しく挙がったものは無い」と書きながら、r46 まで続いた**
- `game-engine` は35ラウンドで r22 以降は10〜17件のまま平ら
- `search-contracts` は r8 で0件を引いた後、r9〜r11 でまた出た。
  **0件は状態ではなく偶然**なので、停止条件に使えない
- r10 以降は**自分の報告書の記述**を批評し始める。コードの材料が尽きるとそうなる

減らないのは所見を1件ずつ潰しているから。**同じ穴を機械で塞ぐまで、次のラウンドで別の綴りで再出現する。**
逆に、機械にした類型は消える（`410-cap-sfen` の doc の腐りは7ラウンド出続けたあと、
走査を入れ切った r8 で0件になった）。

`.claude/knowledge/mechanization-backlog.md` に、入れなかったせいで
2〜17回再提案された項目が並んでいる。

だから成果物は**直した所見の数ではなく、増えた機械の数**。

## 手順1: 範囲と reviewer を決める

`$ARGUMENTS` 未指定なら `git diff main...HEAD --stat` と `git status --porcelain`。
変更ファイルが30を超えるならサブシステム単位に割る。

範囲に含まれるものだけ走らせる。

| reviewer                | 走らせる条件                                                     |
| ----------------------- | ---------------------------------------------------------------- |
| `architecture-reviewer` | 常に                                                             |
| `comment-reviewer`      | 常に                                                             |
| `react-reviewer`        | `.tsx` / フック / Context                                        |
| `ui-reviewer`           | `.scss` / レイアウトを持つ component                             |
| `rust-reviewer`         | `src-tauri/`                                                     |
| `perf-reviewer`         | ループ / 変換 / 描画 / IO                                        |
| `robustness-reviewer`   | エラー処理 / IO / 外部入力 / パース                              |
| `oss-hygiene-reviewer`  | `README` / `CONTRIBUTING` / `docs/` / `.github/`、または明示指定 |

## 手順2: 走らせる

選んだ reviewer を**1つのメッセージで同時に**起動する。各プロンプトに含めるもの:

- 見るファイルの具体的な一覧
- この変更が何をしようとしているかの1〜2行
- **`.claude/knowledge/mechanization-backlog.md` の「機械では止まらないもの」の5類型。
  そこだけを見させる。** 機械が既に見ている範囲の所見は雑音

## 手順3: 振り分ける（この skill の中心）

**全部読んでから**、所見を3つに割る。1件目から直し始めない。

| 行き先         | 条件                                      | やること                                              |
| -------------- | ----------------------------------------- | ----------------------------------------------------- |
| **機械にする** | lint / 型 / ラチェット / テストで落とせる | **これを最優先で入れる。**同種を全部塞ぐ              |
| 直す           | 機械にできないが、いま直す                | 1所見1コミット                                        |
| 送る           | 範囲外・判断が要る                        | issue か `docs/IDEAS.md`（分類は `/implement` 手順7） |

振り分けで必ず問うこと。

- **その所見は `mechanization-backlog.md` に既にあるか。** あるなら回数を1つ増やして、**今回入れる**。
  「1件目だから two-strikes に達していない」を、**その表を見ずに書かない**
- **同種が他に何箇所あるか。** 1箇所だけ直すと不整合が増える
- 所見に納得できないなら直さない。報告書に反論を書く。レビュアーは間違えることがある

**所見が同じ機構に3件以上集まっているなら、個別に直す前にその機構を落とす案を1行書く。**
巨大なファイルは行単位の所見を無限に産むだけで分割されない（`session.rs` は4,817行のまま
35ラウンドを通過した）。

## 手順4: 直す

機械 → 直す、の順。機械を後に回すと同じ場所を二度触る。

直すもの1件ごとに1行書いてから直す。

> この直し方で壊しうるもの: ＿＿＿

書くのは「回帰の恐れ」ではなく**どの入力がどの経路を通って何になるか**。書けないなら直し方が決まっていない。

コミット前に検証を通す（`git commit` は `.claude/hooks/verify-gate.sh` が横取りする）。
**落ちたら直す。飛ばさない。**

### 走査を書くときの罠

`mechanization-backlog.md` の「既知の罠」を読む。要点は1つ。

**「見つけた件数が0」と「見たセルが0」を区別する。** 走査型のテストには件数の下限
（`toBeGreaterThan`）を必ず置く。無いと走査が壊れても緑になる。

## 手順5: 2巡目

**入れた機械が効いているかだけを見る。所見の再収集をしない。**

- 入れた検査を、直す前の状態に戻して**落ちることを確かめる**（落ちなければ別の理由で通っている）
- 手順4 で書いた「壊しうるもの」が壊れていないか
- 送ったものに行き先の番号が付いているか

ここで終わり。**新しい所見が出ても、それは次の PR の入力**であって、このループを延長する理由ではない。

## 報告書

`.claude/reviews/<YYYY-MM-DD>-<slug>.md` に**1本だけ**書く。ラウンドごとに増やさない。

```markdown
# レビュー <slug>

- 日付 / 範囲 / 走らせた reviewer / 対象コミット

## 入れた機械

（何を落とせるようになったか。変異を当てて落ちることを確かめたか）

## 直した所見

（1件1行。短ハッシュと1行の説明を併記する）

## 送ったもの

（行き先の issue 番号 / IDEAS の行）

## 機械にできなかったもの

（`mechanization-backlog.md` へ回数を書き戻したか）

## 見ていない範囲
```

## 禁止事項

- **所見が尽きるまで回す。** 尽きない
- **所見を全部読む前に直し始める**
- **機械化できる所見を、機械にせず個別に直して終える**
- 所見を黙って落とす。落とすなら行き先を書く
- 複数の所見を1コミットにまとめる
- 走査型のテストを件数の下限なしで入れる
- 検証を通さずに「完了」と報告する
