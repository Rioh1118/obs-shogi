**1ラウンド分の所見を全部読んでから**、次のラウンドまでの直し方を決める。
ここでは直さない。計画を報告書へ書いて `/review-fix` へ渡す。

`/implement` 手順5 のループの中で、`/review-round` と `/review-fix` の間に入る。

```
/review-round   → 所見を報告書に書く
/review-plan    → 所見を束ね、順を決め、壊しうるものを先に書く   ← ここ
/review-fix     → 計画の順に1所見1コミットで直す
/review-round   → 計画が書いた焦点を次の reviewer に渡す
```

## なぜ要るのか

`/review-fix` は**所見を1件ずつ**取る。1件ずつの判断としては正しい。
だが**そのラウンドの所見を全部並べたときに初めて見えるもの**が、誰の担当でもなくなる。

実測でそこが抜けている。

- `2026-09-02-harness-and-research` の r1〜r4 は、**4ラウンド全てで
  「前ラウンドの修正で入った新しい欠陥」**を出した（r4 の表に7件）。
  1件ずつ見れば正しい修正が、次のラウンドの所見を作っている
- `.claude/reviews/` で最も長いループは**15ラウンド**（`cursor-vocabulary`）

どちらも「その修正が何を壊しうるか」を**直す前に**書いていれば次のラウンドの焦点になっていた。
計画の段はそのために置く。**所見の消化計画ではない。次のラウンドへ渡す焦点を作る段。**

## 手順1: 読み切る

対象の報告書を読む。`$ARGUMENTS` が無ければ `.claude/reviews/` の最新。
**所見だけを読まない。** 「重複・矛盾した所見」「見ていない範囲」「lint / hook で強制できるもの」も読む。
束ねと順序の根拠はそちらに入っていることが多い。

前ラウンドの報告書があれば、その「次ラウンドの焦点」を読む。
**焦点に答えていない所見があるなら、それは今回のラウンドの穴**で、計画に書く対象になる。

**1件目から直し始めない。** 全部読む前に手が動いたら、この skill は仕事をしていない。

## 手順2: 束ねる

**同じ根から出ている所見**を1つの束にする。判定はこれだけ。

> A を直すと、B の指摘箇所は**消えるか、別物になるか**。

消えるなら B は A の後で「解消済み」になりうる（`/review-fix` 手順1 がそれを拾う）。
別物になるなら、B は A の後で**書き直してから**取る。

**束はコミットの単位ではない。** 1所見1コミットは崩さない（`/review-fix` 禁止事項）。
束は**順序の単位**であって、畳んでよいという意味ではない。

## 手順3: 順を決める

**BLOCK → HIGH → MEDIUM の並びをそのまま順序にしない。** 深刻度は「見つけた側の重さ」で、
直す順は「直す側の依存」で決まる。次を先に置く。

1. **機械で強制できるもの**（lint / hook / 型）。人の注意に頼る修正を先に入れると、
   後から機械を入れたときに同じ場所をもう一度触ることになる。
   `/review-fix` 手順2 は所見1件ごとにこれを問うが、**ラウンド全体で先に置けるのは計画だけ**
2. **他の所見の指摘箇所を消すもの**（手順2 の束の先頭）
3. **失敗経路と門番の向きを変えるもの**。修正が積み上がる前に入れる。
   後半に回すと、壊したときに何が原因かを切り分けられなくなる
4. 残り

## 手順4: 対象そのものを疑う

**所見が同じ機構に集まっていないか**を数える。集まっているなら、
個別に直す前に**その機構を落とす案を計画に1行載せる**。

**所見が減らないラウンドが3回続いたら、直し方ではなく対象を疑う。**
所見を1件ずつ見ている限りこの形は見えないので、疑えるのは計画の段だけになる。

- その機構は、いま直している issue が要求しているか。要求していないなら落として issue に出す
- 同じ判断をする場所を数える。2箇所以上あるなら、機構を足す前に集約する
- 判断を変えたら、その判断が正当化していた機構がまだ要るかを測り直す

載せずに個別修正へ入ると、次のラウンドでまた同じ機構に所見が出る。

## 手順5: 壊しうるものを、直す前に書く

**この skill の中心。** 直すと決めた所見それぞれに、1行書く。

> この直し方で壊しうるもの: ＿＿＿

書けないなら**直し方がまだ決まっていない**。決まっていないものを `/review-fix` へ渡さない。

書くのは「動かなくなるかもしれない」ではなく、**どの入力がどの経路を通って何になるか**。

- ✗「回帰の恐れがある」
- ○「`Err` で止まっていた入力が `Ok` で返るようになる。呼び先の `catch` が消える」

この一覧がそのまま**次ラウンドの焦点**になる。次の `/review-round` は、
これを reviewer へ渡すプロンプトに入れる（`/review-round` 手順3）。

## 手順6: 直さないものの行き先を決める

**計画から黙って落とさない。** 落とすなら行き先を書く。

行き先の分類は `/implement` 手順7 の表で決める（同じ PR / 別コミット / issue /
`docs/IDEAS.md`）。ここに二重に置かない。
所見そのものに納得できないなら、**報告書に反論を書いて見送る**（`/review-fix` 手順2-4）。

## 手順7: 検証のコストを見積もる

**`git commit` ごとに `.claude/hooks/verify-gate.sh` が走る。**
1所見1コミットなので、**このラウンドで直す件数がそのまま検証の回数**になる。

    見積り = 直す件数 × そのブランチで実際に走る検証の時間

所要時間の目安は `CLAUDE.md` の検証節。**どの検証が走るかを机上で決めない**
（判定の出典は `.claude/hooks/verify-gate.sh` そのもの）。

Rust の検証が走るブランチで10件を1ラウンドに積むと20分を超える。
**そのときは件数を減らして、残りを次のラウンドへ送る。** 送ったことは手順8 に書く。

## 手順8: 報告書へ書く

**別ファイルを作らない。** 対象のラウンドの報告書に追記する。
ラウンドをまたいで参照できないと、このループは成立しない。

`/review-round` が空欄で置いた「## 修正計画」を、次で埋める
（古い報告書には「## 次ラウンドの対象」という見出しで残っている。あればそれを置き換える）。

```markdown
## 修正計画（r<N> → r<N+1>）

### 束（同じ根から出ている所見）

- <束の名前>: E5-1 → E5-2（E5-1 を直すと E5-2 の指摘箇所が消える）

### このラウンドで直すもの

| 順  | 所見 | なぜこの順か | この直し方で壊しうるもの |
| --- | ---- | ------------ | ------------------------ |

### 直さないもの

| 所見 | 行き先 | 理由 |
| ---- | ------ | ---- |

### 対象そのものを疑ったか

（所見が同じ機構に集まっているか。件数で書く。落とす案があるなら1行）

### 次ラウンドの焦点

（上の「壊しうるもの」を統合した一覧。次の `/review-round` はこれを reviewer へ渡す）

### 検証の見積り

（件数 × 走る検証。減らしたなら、何を次ラウンドへ送ったか）
```

## 手順9: 次へ

**ここで止まらない。** そのまま `/review-fix` へ進む
（`/implement` 手順5「ループの途中で止まらない」）。

**計画をユーザーに承認させない。** 承認を待つと、計画を立てること自体が目的になる。
止まってよいのは `/implement` 手順5 が挙げる3つだけ。

単独で呼ばれたときだけ、計画を述べて委ねる。

## 禁止事項

- **所見を全部読む前に直し始める**
- **「壊しうるもの」を空欄のまま `/review-fix` へ渡す**（手順5）
- **所見を計画から黙って落とす。** 落とすなら行き先を書く（手順6）
- **複数の所見を1コミットに畳む計画を書く。** 束は順序の単位であってコミットの単位ではない
- **計画を報告書と別のファイルに書く**
- 計画の承認をユーザーに求めて止まる
- 深刻度の並びをそのまま順序として書き、なぜその順かを空欄にする
