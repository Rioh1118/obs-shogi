実装を**終わらせる**ための手順。前提は `CLAUDE.md`。ここには**順序と判断**だけを書く。

## 手順1: 着手前

- `main` に直接コミットしない。ブランチを切る
- **`main` が進んでいないか確認する。** `git fetch` して、離れているなら先に rebase する。
  古い基点で書くと、実測も行番号への参照も腐ったまま積み上がる
- 変更の**範囲を先に決める**。「ついでに直す」を混ぜない

## 手順2: 現物を読んでから書く

**推測で書き始めない。** 特に次は毎回外れる。

- 「この関数は失敗しないはず」→ 呼び先の `catch` を読む
- 「この state は誰かが読んでいるはず」→ `grep` で読み手を数える
- 「この行番号のコメントは合っているはず」→ 開いて確かめる

数えた結果は**数字で残す**。「多い」「ほとんど」ではなく件数で書く。

## 手順3: 刻んでコミットする

**1コミット = 1つの変更。** 何を1つと数えるかは「元に戻すときに一緒に戻したいか」で決める。
「ついでの整形」「ついでの改名」を混ぜない。混ぜると差分が読めなくなる。

`npm run verify` は**ビルドを含まない**。SCSS を触ったら `npm run build` も通す。
`Cargo.lock` だけの変更は gate の Rust 判定に掛からないので手で `npm run verify:rust`。

**verify を通してから `git commit` する。** コミットが gate で止まると lint-staged が
ワークツリーを復元し、**その巻き戻しで直前の編集が消える**。「直したはずの値が戻っている」
という形で出るので、原因に見えにくい。

## 手順4: レビューの厚さを決める

**全部に全観点を当てない。**

| 重さ   | 何が当てはまるか                                                        | やること                  |
| ------ | ----------------------------------------------------------------------- | ------------------------- |
| **軽** | docs のみ / コメント / トークンへの置換 / 1ファイル内で閉じた表示の調整 | レビュー不要。verify だけ |
| **中** | 1スライス内で閉じる。失敗経路・外部プロセス・状態機械に触れない         | `/review` を観点を絞って  |
| **重** | 下のどれか1つでも該当                                                   | `/review` を観点を絞らず  |

重に上げる条件:

- **失敗経路を触る**（`catch` / エラー表示 / 復帰導線）
- **外部プロセスと歩調を合わせる**（エンジン、Rust のセッション、ファイル監視）
- **状態機械を触る**（reducer、`useRef` で持つ内部状態、非同期の競合）
- `shared/` または `entities/` を触る
- レイヤをまたぐ import が増減する
- 触った箇所に**テストが1本も無い**

迷ったら重にする。

## 手順5: レビューを回す

`/review` を呼ぶ。**2巡で終わる**（所見が尽きるまで回さない。尽きない）。
振り分け・順序・機械化の判断はそちらが持っている。ここに二重に置かない。

**このループは一息に回す。** 途中で報告して指示を待たない。
止まってよいのは3つだけ。

- 手順7 の「直し方に判断が要る」に当たったとき
- 検証が通らず、原因が自分で解けないとき
- ユーザーが割り込んだとき

**「次に進んでよいか」は聞かない。** 進んでよい。

## 手順6: テストを足す

新しいロジックには実際にテストを足す。

**書いたテストは変異を当てて落ちることを確認する。** 直した箇所を元の壊れた実装に戻し、
テストが落ちるかを見る。落ちなければ、そのテストは別の理由で通っている。

`src-tauri/tests/` の大半は**ソースを走査するラチェット**で、振る舞いを見ていない。
`cargo test` の green を「Rust が壊れていない」と読まない。

状態や非同期が絡むなら `/state-transition-table` を先に使う。埋まっていないセルがテスト項目になる。

## 手順7: 途中で見つけた既存の問題

**まず再現を確かめる。** コードを読んだだけの推測なら、それは所見ではない。

| 状況                                     | どうするか                                                |
| ---------------------------------------- | --------------------------------------------------------- |
| いま触っている変更の**前提を壊している** | **同じ PR で直す。** 直さないと変更が成立しない           |
| 範囲の中にあり、**独立して直せる**       | **別コミットで直す。** メッセージで独立を書く             |
| 範囲の外、**6週間以内に着手する**        | **issue を立てる。** その場では直さない                   |
| 範囲の外、**6週間以内に着手しない**      | **`docs/IDEAS.md` に1行**（`docs/OPERATING-MODEL.md` §2） |
| 直し方に判断が要る（設計の選択）         | issue を立て、**ユーザーに選ばせる**                      |

**それ以外は聞かずに進める。** 立てるときは `/write-issue`。

## 手順8: 報告

**ループを抜けたときに1回。** 書くのは4つ。

- **入れた機械**（何を落とせるようになったか）
- 直した所見と、提案どおりに直さなかったものはその理由
- **自分が作った退行があれば、隠さず先に書く**
- 検証の結果。通していないなら「未検証」と明示する

## 手順9: コミットを並べ直す

`/tidy-commits` を呼ぶ。**既定は「触らない」**なので毎回並べ直すことにはならない。
**押した後は呼ばない。**

## 手順10: PR

- 本文には**何を変えたかではなく、なぜその直し方にしたか**を書く
- 決定を伴ったなら ADR（`docs/decisions/`）へのリンクを張る
- `gh pr edit --body` は Projects classic の deprecation で**黙って失敗する**。
  `gh api -X PATCH repos/OWNER/REPO/pulls/N -F body=@file` を使う

## 禁止事項

- **検証を通さずに「完了」と報告する**
- **機械化できる所見を、機械にせず個別に直して終える**
- テストを弱めて所見を消す
- 「テストが通ったので安全」と書く
- 範囲外の問題をその場で直す
