実装を**終わらせる**ための手順。書き始める前にここを読む。

前提は `CLAUDE.md`（検証コマンド・依存の方向・コメントの書き方）。ここには**順序と判断**だけを書く。

## 手順1: 着手前

- **着手中の issue は1件だけ。** `gh issue list --assignee @me` が2件以上返る状態を作らない
- `main` に直接コミットしない。ブランチを切る
- **`main` が進んでいないか確認する。** `git fetch` して、離れているなら先に rebase する。
  古い基点で書くと、実測も行番号への参照も腐ったまま積み上がる
- 変更の**範囲を先に決める**。「ついでに直す」を混ぜない

## 手順2: 現物を読んでから書く

**推測で書き始めない。** 特に次は毎回外れる。

- 「この関数は失敗しないはず」→ 呼び先の `catch` を読む
- 「この state は誰かが読んでいるはず」→ `grep` で読み手を数える
- 「この行番号のコメントは合っているはず」→ 開いて確かめる

数えた結果は**数字で残す**。「多い」「ほとんど」ではなく件数で書く。

## 手順3: 刻んでコミットする

**1コミット = 1つの変更。** 何を1つと数えるかは「元に戻すときに一緒に戻したいか」で決める。

- 型や設定の準備 → 本体 → テスト、が別々の関心事なら別コミット
- 「ついでの整形」「ついでの改名」を混ぜない。混ぜると差分が読めなくなる
- コミット前に検証を通す。`git commit` は `.claude/hooks/verify-gate.sh` が横取りして自動で走らせる。
  **落ちたら直す。飛ばさない**

`npm run verify` は**ビルドを含まない**。SCSS を触ったら `npm run build` も通す。
`Cargo.lock` だけの変更は gate の Rust 判定に掛からないので手で `npm run verify:rust`。

## 手順4: レビューの厚さを決める

**全部に全観点を当てない。** 変更の性質で決める。

| 重さ   | 何が当てはまるか                                                        | やること                                                         |
| ------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **軽** | docs のみ / コメント / トークンへの置換 / 1ファイル内で閉じた表示の調整 | レビュー不要。verify だけ                                        |
| **中** | 1スライス内で閉じる。失敗経路・外部プロセス・状態機械に触れない         | `/review-round` を**観点を絞って**1ラウンド                      |
| **重** | 次のどれか1つでも当てはまる                                             | `/review-round` を観点を絞らず、**指摘ゼロのラウンドが出るまで** |

重に上げる条件（1つでも該当したら重）:

- **失敗経路を触る**（`catch` / エラー表示 / 復帰導線）
- **外部プロセスと歩調を合わせる**（エンジン、Rust のセッション、ファイル監視）
- **状態機械を触る**（reducer、`useRef` で持つ内部状態、非同期の競合）
- `shared/` または `entities/` を触る（下の層ほど壊したときの範囲が広い）
- レイヤをまたぐ import が増減する
- 触った箇所に**テストが1本も無い**

迷ったら重にする。軽く見積もって漏らすほうが高くつく。

## 手順5: レビューと修正を回す

**指摘がゼロのラウンドが1回出るまで終わらない。** これは MUST。

```
/review-round   → 所見を .claude/reviews/ に書く（直さない）
/review-fix     → 1所見1コミットで直し、報告書に結果を書き戻す
/review-round   → 修正で新しい問題が入っていないか見る
...
```

打ち切ってよいのは**所見が0件のラウンドが出たとき**だけ。
BLOCK と HIGH が0でも、MEDIUM が残っているなら次を回す。

所見に納得できないなら直さずに**報告書へ反論を書く**。レビュアーが間違っていることはある。
ただし「面倒だから見送る」は書かない。見送る理由を読み手が検証できる形で残す。

### 4ラウンド続けて同じ故障が出たことがある

**「コメントに書いた理由が、実装している条件と違う」**（ADR-0003 のレビュー r1〜r4）。
機械では防げない。**コメントに「〜だから」と書いたら、その条件式がコードのどの行かを指せるか**を
1件ずつ確認する。

## 手順6: テストを足す

新しいロジックには実際にテストを足す。`cargo test` の green は何も保証しない（`#[test]` が0個）。

**書いたテストは変異を当てて落ちることを確認する。** 直した箇所を元の壊れた実装に戻し、
テストが落ちるかを見る。落ちなければ、そのテストは別の理由で通っている。

状態や非同期が絡むなら `/state-transition-table` を先に使う。
埋まっていないセルがテスト項目になる。

## 手順7: 途中で見つけた既存の問題

**まず再現を確かめる。** コードを読んだだけの推測なら、それは所見ではない。

確かめたうえで:

| 状況                                         | どうするか                                                                |
| -------------------------------------------- | ------------------------------------------------------------------------- |
| いま触っている変更の**前提を壊している**     | **同じ PR で直す。** 直さないと変更自体が成立しない                       |
| 触っている範囲の中にあり、**独立して直せる** | **別コミットで直す。** コミットメッセージで独立していることを書く         |
| 範囲の外にある                               | **issue を立てる。** その場では直さない。範囲を広げると PR が読めなくなる |
| 直し方に判断が要る（設計の選択が絡む）       | issue を立て、**ユーザーに選ばせる**。勝手に決めない                      |

issue を立てるときは**再現手順と、なぜ問題かを具体的な失敗の筋道で書く**。
「〜すべき」ではなく「〜という入力で〜になる」。

## 手順8: PR

- ブランチを push する前に**ユーザーに確認する**
- 本文には**何を変えたかではなく、なぜその直し方にしたか**を書く。差分は読めば分かる
- レビューを回したなら報告書のパスと、最終ラウンドで所見が0件だったことを書く
- 決定を伴ったなら ADR（`docs/decisions/`）へのリンクを張る
- `gh pr edit --body` は Projects classic の deprecation で**黙って失敗する**。
  `gh api -X PATCH repos/OWNER/REPO/pulls/N -F body=@file` を使う

## 禁止事項

- **検証を通さずに「完了」と報告する。** 通していないなら「未検証」と明示する
- **レビューを1ラウンドで打ち切る。** 所見0のラウンドが出るまで終わらない
- テストを弱めて所見を消す
- 複数の所見を1コミットにまとめる
- 「テストが通ったので安全」と書く
- 範囲外の問題をその場で直す
