テストケースを思いついた順に足すのをやめ、**状態 × イベント**を先に列挙する。
**空のセルが、そのまま未検証の経路。**

## いつ使うか

- 非同期の完了と外部からの変化が競合する（送信中に設定が変わる、待機中に停止される）
- プロセスやサーバなど**外部の状態機械**と歩調を合わせている
- 既に不具合が出た箇所。**同じ場所で2度目が出たら必ず使う**

逆に、純関数と単純な入出力には要らない。表を作るコストが上回る。

## 手順1: 状態を列挙する

内部の状態変数の**組み合わせ**を、意味のある単位にまとめて記号を振る。
変数を全部掛け合わせない。到達可能で、振る舞いが変わるものだけを残す。

各状態には**判定条件を式で書く**。「送信中」ではなく `inFlightRef !== null` と書く。
書けないなら、その状態はまだ言葉になっていない。

## 手順2: イベントを列挙する

状態を変えうる入力を、**発生源つき**で並べる。

漏れやすいもの:

- **否定方向の遷移**（ready になる、だけでなく ready でなくなる）
- **同じ値のままの再初期化**（識別子が変わらないエンジンの再起動など）
- **利用者による中断**（停止ボタン、モーダルを閉じる、棋譜を閉じる）
- **失敗**（成功だけ書いて失敗を書かない、が最頻）

## 手順3: 外部の状態を列に入れる

**このプロジェクトで実際にやらかした失敗がここ。**
React の state だけで表を作り、Rust 側のセッションを列に入れ忘れたため、
「フロントは停止、エンジンは動作中」という表に無い状態が生まれ、
以降すべての解析開始が弾かれる行き止まりになった（issue #120 / ラウンド3 BLOCK）。

境界をまたぐ状態は、**自分の側の状態と並べて1つの表に載せる。**
別の表に分けるなら、両方に「相手側の状態」を列として持たせる。

## 手順4: セルを埋める

各セルに**そのイベントが起きたときの期待挙動**を書く。
「起きない」「状態が変わらない」も明示する（`—`）。空欄のまま残さない。

## 手順5: 不変条件を書く

表の下に、**どのセルでも破ってはいけない性質**を3つ前後で挙げる。
セルごとの期待挙動より、こちらの方が寿命が長い。

例（`docs/state-transitions/engine-position-sync.md`）:

> 1. `syncedSfen` が非 null なら、その SFEN は現在のエンジンに実際に送れている
> 2. キューに積まれた局面は、必ずいつか送られるか、より新しい局面に置き換わる
> 3. 記録を捨てる操作は必ず世代を上げる

## 手順6: 既存のテストと照合し、埋まっていないセルを明記する

テストが踏んでいるセルに印を付ける。**印の無いセルが成果物。**

**埋まっていないセルを表に残すこと。** 消すと「表を作った」だけで安心してしまう。
「実装上は同じ経路に落ちるが、テストは無い」と書く。

## 手順7: 埋めたテストが本物か確かめる

書いたテストは、**そのセルの挙動を壊す変異を当てて落ちること**を確認する。
落ちなければ、そのテストは別の理由で通っている。

このプロジェクトで実例がある。`(ready待ち, 局面変化)` のテストを書いたが、
変異を当てると**別のテストが落ちて、書いたテスト自身は落ちなかった。**
調べると、コメントが主張していた区別が実際には起こりえないことが分かった。
テスト名を実際に検証している内容に直し、コメントを実態に合わせた。

## 置き場

`docs/state-transitions/<スライス名>.md`。

## 禁止事項

- 埋まっていないセルを消して表を完成に見せる
- 判定条件を書かずに状態名だけ並べる
- 外部プロセスの状態を「自分の管轄外」として表から外す
- 変異を当てずに「テストを足した」と報告する
