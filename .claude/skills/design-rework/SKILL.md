AI が測り、案を作り、別の目に批評させて直す。**人が判断するのは2回だけ**: 並べた完成案から選ぶときと、PR。
途中の判断は `/decide` で決めて `direction.md` の判断ログに残す。**どれが良く見えるか**だけは AI が確定しない。推奨を1つ言うところまで。
性格・値・語は `obs-shogi-design-system` スキル（モード A）を読んでから始める。案の中の値は、モード A の「直書きしない」の外。選ばれた後に DS へ入れる。

止まって聞くのは `docs/rules/decisions.md` にあるものと、完成案の承認、`locked.json` の固定値、DS の画像の基準の更新と `ds:eval`（実費）、plugin・hook、同じ所を3周直しても良くならないとき。

- 作業フォルダは根の `.claude/plans/<slug>/`。**コマンドには絶対パスで渡す**（`design-system` から走るので、相対では別の場所にできる）
- `audit.md`（点検）、`direction.md`（方向と判断ログ）、`critique.md`（批評）、`feedback/<周>.json`（感想）、`now/`・`proto/`・`compare.html`（道具が作る）
- 窓は 1600×1000（起動時の上限）、1464×917（利用者の画面での起動時）、1280×720、1024×640（窓の下限）

## 手順1: 現物を測る

製品の部品を見本データで描いて撮り、崩れを数える。**手で起動して撮らない。** 空・失敗・長い文字を同じ条件で出せない。

```bash
npx vite --port 5199 --strictPort --host 127.0.0.1     # 根で、裏で動かす。作業が終わったら止める
cd design-system
npm run ds:screens -- --url http://127.0.0.1:5199 --sizes 1600x1000,1464x917,1280x720,1024x640 --out <作業フォルダ>/current
```

- 数は、崩れ（文字が読めない・押せない）、形の癖（入れ子の箱・背景のグラデーション・片側の棒）、固定値の違反（コントラスト・文字の下限）の3つに分けて出る。種類は `design-system/screens/kinds.mjs`
- 足りない場面は `screens/scenarios.mjs` に、足りない値は `screens/fixtures.mjs` に足す。見本に実在の人名と手元のパスを入れない。状態は `docs/spec/screens/` の表から取る。製品に無い状態を描かない
- 数だけで終えず、画像を開いて重い順に並べる。[点検表](references/checklist.md) と [AI の癖](references/ai-tells.md) を当てる。**検査を全部通っても良いとは限らない**（#652 の帯いっぱいのボタンは、前後の画像に写っていた）
- 利用者の言葉は直さずに写し、どの部品かだけを当てる。見立てと違う所を書く（言葉が無ければ「無し」）
- 崩れの行き先だけを書く。基準からの逸脱は手順7で直す、基準が無いものは決めて足す、基準が悪いものは基準を直す案にする。「今の寸法は意図」という原則は、利用者が名指した画面には当てない

完了: `audit.md` に、種類ごとの数・目で見た所見・見立てと違う所がある。描けなかった場面が無い。

## 手順2: 方向を1枚に書く

方向の下書きを [AI の癖](references/ai-tells.md) に当て、型どおりの所を直してから作る。`direction.md` に、ブランドから取るもの、直した所、外の資料と DS の原則が食い違う所と採った側を書く。

- 額縁と素材の2層、記録係の性格は既定で残す。崩すなら、崩す語を書く
- ブランドは、色・書体・密度・印になる形1つに絞る。**部品の使い方（タブ・表・ボタン・フォーカス）は道具の標準のまま**、並べ方・配分・密度は変えてよい
- 外の資料や別の製品は考え方を借りる。値・コード・文章を持ち込まない

完了: 食い違いの1件ずつに、採った側と理由がある（無ければ「無し」）。

## 手順3: 実物で3案以上を作る

`design-system/explorations/<日付>-<slug>/` に `cases.mjs` を置く。出すものと、案の画面が守る約束は `design-system/compare/build.mjs` の冒頭にある。手本は `explorations/2026-11-22-rework/`。

- **構成・密度・重みを変える。** 色や角丸だけの違いを案に数えない。今の決定を当て切った形も1案に入れる
- 文言・データ・画像は実物。その画面の状態を、全部の案で描く
- 利用者が気に入っている所（brief の「寄せる先」を含む）は、**変えない形を必ず1案に入れる**。消す案は、消す理由を書く（検討のドックを全部の案で作り替え、「今の方がカッコ良い」と直された）
- 押すものを今より小さくするなら、代わりの操作を同じ案に入れる。数が増える一覧は、件数の多い見本でも描く
- 色の帯・枠・下敷きを外す前に、その下で何が背景を持つかを読む（局面ナビは自前の背景を外して器ごと透明になった）
- 案ごとに、諦めるものを1行書く。推奨を1つ決めて理由を書く

```bash
npm run ds:compare -- explorations/<日付>-<slug> --work <作業フォルダ> --now --url http://127.0.0.1:5199   # 最初の1回
npm run ds:compare -- explorations/<日付>-<slug> --work <作業フォルダ>                                     # 2回目から
```

完了: 案に崩れと固定値の違反が1件も無く（コマンドが成功で終わる）、`compare.html` がある。

## 手順4: 別の目に批評させて直す

文脈を持たない agent 1本に、**画像と brief だけ**を渡す。見る画像を別のフォルダに写し（今と各案、代表の状態。40枚まで）、その絶対パスだけを伝える。案の狙い・推奨・自分の採点・崩れの数を渡さない。渡す brief は、利用者・使う場面・守ること・性格・アプリのアイコンで組む。

- 見るもの: 読む順と重み、盤の扱い、密度、箱と枠の数、AI の癖、状態ごとの崩れ、名前を隠したときに分かるか、画面をまたぐ揃い
- 指摘は場所・問題・直し方・重さの形で、確信度80以上だけ（コードを見ないので review-protocol の形式は使わない）。**返答は全体で 4,000 字以内**と頼み、届いた全文をメインが作業フォルダに写す（サブエージェントは報告のファイルを書けない。長い返答は通信の途中で切れ、1時間戻らなかった）
- 1件ずつ「直した」「一部」「従わない」と理由を `critique.md` に書く。**直す前に落ちる検査を足せないかを先に見る**（読める幅が無い知らせ、接した欄、見えないいまの行は、崩れ 0 件のまま批評で見つかった）。足したら `npm run ds:screens:selftest`
- 直した画像を同じ agent に見せる。**批評は2周で終える。** 2周目の残りは確認事項に書く。同じ所が3周直しても良くならなければ止めて聞く

完了: 全ての指摘に行き先があり、直した後の画像で確かめてある。

## 手順5: 人に1回で選んでもらう

```bash
npm run ds:compare:serve -- --work <作業フォルダ> --open     # 止めるまで戻らないので、裏で動かす
```

今と案が同じ窓の大きさで並ぶ。見る人は状態・窓・明るさを切り替え、判定と「どこが、どう感じた」を残す。感想はそのまま `feedback/<周>.json` に入る。

- 渡すものは、開いた状態の1枚、推奨1つと理由、聞きたいこと3つまで、AI が決めて驚かれそうな判断、確認していないこと
- 言葉で好みを聞かない。足りなければ案を増やす。待つ間に次の案を作らない
- 感想を受け取ったら、サーバを止める

完了: 判定か混ぜ方が `feedback/` か会話にある。

## 手順6: 次の周か、規則へ

「これにする」が無いか、「混ぜる」がある（混ぜた画面はまだ描かれていない）なら、`cases.mjs` の周の名前（英数字とハイフン）を上げて手順3へ戻る。`ds:compare` が前の周の感想を `feedback/previous.json` に写すので、1件ずつ `done` に直したこと（従わないなら理由）を書く。空のままでは次の1枚を作れない。書いたものは、次の1枚の右の列に出る。

1案が選ばれたら、DS に入れる（モード C。ここで選ばれた案は、密度が変わってもモード B へ戻さない）。

- 値・部品・パターン・語を入れる。案の CSS を製品へ写さない
- 感想から残る決まりは、次の画面が同じ水準で作れる形（役割の表と、してよいこと・いけないこと）で書く
- 見た目の決定は `design-system/decisions/`、製品の構造の決定は `docs/decisions/` に ADR を書く
- 画面ごとの反映の順を決め、1画面1 PR にする

完了: 選ばれた案の全ての決まりに、DS の行き先か、入れない理由がある。

## 手順7: 渡す

操作が変わるなら `/intake` から、見た目だけなら `/implement` へ。

- 直した画面から `npm run ds:screens -- --only <場面> --strict` を通し、`--record` で基準（`screens/baseline.json`）を下げる。下げた後は `--check` が増えたぶんを止める
- PR には前後の実アプリの画面と、撮影の崩れの数を付ける
- 実装後に直されたら `.claude/rules/skill-care.md` に従う

完了: `npm run verify`・`npm run verify:ds` と、触った場面の `--strict` が通っている。
