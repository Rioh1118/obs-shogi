見た目の良し悪しは**人が決める**。AI の仕事は、違和感を測れる形にし、選べる形で見せ、決まったことを規則へ落とすこと。
この工程の判定だけは `/decide` で決めない。トンマナと語は `docs/spec/design-language.md` を読んでから始める。

**検査を通っても良いとは限らない。** プリセット編集は3巡の後に人が不可と判定し、#652 では帯いっぱいに伸びたボタンが
前後の画像に写っていたのに、差分だけを見て見落とした。

## 手順1: 違和感をそのまま集める

実画面を見せ、利用者の言葉を直さず1行ずつ書く。`.claude/plans/design-<画面>/feedback.md` に置く。

| 画面 | 利用者の言葉 | 指している部品 | 測った値 |
| ---- | ------------ | -------------- | -------- |

- 見せるのは実物。`/run` か、DOM と本番の CSS を並べた台帳を使う。描き直した画面で聞かない
- 「ダサい」を言い換えない。どの部品かだけを聞く
- 空・失敗・長い文字列・値が多い状態も見せる

完了: 全行に部品の名前がある。

## 手順2: 測って3つに分ける

各行を実測し、分ける。

| 種類           | 例                                 | 次にすること             |
| -------------- | ---------------------------------- | ------------------------ |
| 基準からの逸脱 | 面の角丸が基準の 8px に対して 14px | 手順5で基準へ寄せる      |
| 基準が無い     | ボタンの幅                         | 手順3〜4で決めて基準に足す |
| 基準が悪い     | 基準どおりなのにダサい             | 手順3へ。基準を直す案を出す |

[点検表](references/checklist.md) を当て、利用者が言っていない候補は別の表に分けて見せる。**候補は言葉と混ぜない。**

完了: 全行の種類と実測があり、利用者が表を見た。

## 手順3: 目指す姿を例で合わせる

言葉だけで合意しない。**好きな実物と嫌いな実物**を利用者から2〜3個ずつもらい、どこが良いのかを部品の単位で書く。
無ければ、こちらが性格の近い製品を3つ挙げ、1つごとに「取り入れる点／取り入れない点」を書いて選んでもらう。

**額縁と素材の2層、記録係の性格は既定で残す**（§0）。崩すなら、崩す語を明示して合意する。
例はそのまま真似ない。

完了: 「この画面は〈例〉の〈点〉に寄せ、〈点〉は寄せない」が1文ある。

## 手順4: ワイヤーを2〜3案

色と質感を入れず、**面の分け方・並び・主な操作**だけを見せる。文言は実物を使う。

- 案は見比べられるほど違うものにする（値の違いだけの案を出さない）
- 案ごとに、諦めるものを1行書く
- 推奨を1つ言い、理由を書く
- 階層が変わらないなら省き、省いたことを書く

完了: 利用者が1案を選んだか、混ぜ方を言った。

## 手順5: モックを1軸ずつ

選んだ案を、実トークン・実文言・実データで作る。`Artifact` の HTML に今の画面と並べる。

- **1回に動かす軸は1つ。** 角丸 → 階層 → 密度 → 色 の順。軸を混ぜると何が効いたか分からない
- トークンに無い値を使うときは、新しいトークンの案として名前を付ける
- 状態を全部並べる（既定 / 値が多い / 空 / 読み込み中 / 失敗 / 無効）
- 差分だけでなく、**写っている部品が基準に合うか**も自分で見てから出す
- 面を外す前に、その下で何が面を持つかを読む。局面ナビは自前の面を外して器ごと透明になった

判定は `feedback.md` に1行ずつ残す。

| 軸 | 見せたもの | 判定 | 利用者の言葉 |
| -- | ---------- | ---- | ------------ |

**同じ軸で3往復したら止める。** モックを増やさず手順3へ戻り、例を合わせ直す。

完了: 全ての軸に採用か却下があり、却下にも理由がある。

## 手順6: 規則へ落とす

- 値はトークンへ。役割の表は `docs/spec/design-language.md`。基準を変えるなら理由に利用者の言葉を添える
- 別の画面にも効く決定は ADR
- 機械で落とせるものはラチェットか走査にする（`/implement` の「機械化できる所見」）
- 他の画面への影響を一覧にし、一度に直すか画面単位にするかを利用者に聞く

完了: 合意した全行に行き先がある。

## 手順7: 渡す

操作や状態が変わるなら `/spec-draft`、見た目だけなら `/implement` へ渡す。見た目が動く PR は分け、前後の実画面を付ける。
実装後に実アプリで見てもらい、直されたら `.claude/rules/skill-care.md` に従う。

完了: `feedback.md` の行が全部、採用・却下・保留のどれかで閉じている。
