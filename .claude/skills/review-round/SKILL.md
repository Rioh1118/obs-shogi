レビューを**1ラウンド**走らせる。直すのはこの skill の仕事ではない。所見を出して止まる。

## 手順1: 範囲を確定する

`$ARGUMENTS` を読む。

- 未指定 → `git diff main...HEAD --stat` と `git status --porcelain` を見て、変更されたファイルを範囲にする
- `--all` → `src/` と `src-tauri/` 全体
- パス → そのパス配下
- 観点名（`ui` `perf` など） → その reviewer だけを走らせる

**範囲が広すぎると所見が薄くなる。** 変更ファイルが 30 を超えるなら、サブシステム単位に割って
複数ラウンドにする。実装の一部として回しているなら**どれから見るかは自分で決めて進む**
（`/implement` 手順5）。単独で呼ばれたときだけユーザーに確認する。

## 手順2: 走らせる reviewer を選ぶ

範囲に含まれるものだけを選ぶ。関係ない reviewer を走らせない。

| reviewer                | 走らせる条件                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------- |
| `architecture-reviewer` | 常に（ファイルの追加・移動・import の変更があれば必ず）                                 |
| `react-reviewer`        | `.tsx` またはフック・Context の変更                                                     |
| `ui-reviewer`           | `.scss` またはレイアウトを持つコンポーネントの変更                                      |
| `rust-reviewer`         | `src-tauri/` の変更                                                                     |
| `perf-reviewer`         | ループ・データ変換・描画・IO を含む変更                                                 |
| `robustness-reviewer`   | エラー処理・IO・外部入力・パースを含む変更                                              |
| `comment-reviewer`      | 常に（コメントと命名は全ての変更に付いてくる）                                          |
| `oss-hygiene-reviewer`  | `README` / `CONTRIBUTING` / `docs/` / `.github/` / ライセンス周りの変更、または明示指定 |

## 手順3: 並列で起動する

選んだ reviewer を**1つのメッセージの中で同時に**起動する。逐次にしない。

各 reviewer に渡すプロンプトには必ず次を含める:

- 見るファイルの具体的な一覧（「変更点を見て」で済ませない）
- この変更が**何をしようとしているか**の1〜2行
- 直前のラウンドがある場合は、その報告書のパスと「同じ所見を再掲しないこと」

## 手順4: 報告書を書く

`.claude/reviews/<YYYY-MM-DD>-<slug>-r<N>.md` に書く。`<N>` はこの範囲での何ラウンド目か。
同じ範囲の既存ファイルを見て番号を決める。

```markdown
# レビュー <slug> ラウンド<N>

- 日付 / 範囲 / 走らせた reviewer / 対象コミット（`git rev-parse --short HEAD`）

## 所見

（深刻度順。BLOCK → HIGH → MEDIUM。各所見に reviewer 名を添える）

## 重複・矛盾した所見

（複数の reviewer が同じ箇所を別の理由で指摘した場合、統合してここに書く。
互いに矛盾する提案があれば両論を残し、判断が要ることを明示する）

## 見ていない範囲

（各 reviewer の申告を統合）

## lint / hook で強制できるもの

（人の注意ではなく機械で防げるもの。ここが増えるほどレビューは軽くなる）

## 次ラウンドの対象

（今回直すもの / 見送るもの と、その理由）
```

## 手順5: まとめる

BLOCK と HIGH の件数、最も重い所見3件、そして
「lint / hook で強制できるもの」に何が挙がったかを述べる。

**実装の一部として回しているなら、ここで止まらない。** そのまま `/review-fix` へ進む
（`/implement` 手順5「ループの途中で止まらない」）。順序は報告書の「次ラウンドの対象」で決める。

単独で呼ばれたときだけ、何から直すかをユーザーに委ねる。

## 禁止事項

- 所見の水増し。LOW を並べて件数を作らない
- 読んでいないファイルについて書く
- 「テストが通っているので問題ない」と書く（TS も Rust もテストは薄い。現在値は `npm run test` と `cargo test` の末尾）
- 報告書を書かずに口頭で済ませる。ラウンドをまたいで参照できないと、このループは成立しない
