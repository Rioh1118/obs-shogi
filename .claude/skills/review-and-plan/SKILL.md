レビューは**2周で打ち切る**。ルールは `docs/rules/`。エージェントの使い方は `.claude/rules/agents.md`。
出力形式と確信度は `.claude/skills/review-protocol/SKILL.md`。

## なぜ2周か

**LLM のレビューは収束しない。** 実測は報告書275本で最長46ラウンド。うち13ラウンドは
「新しく挙がったものは無い」と書きながら続いた。**0件は状態ではなく偶然**なので停止条件に使えない。

減らないのは所見を1件ずつ潰しているから。**同じ穴を機械で塞ぐまで、別の綴りで再出現する。**
だから成果物は直した指摘の数ではなく、**増えた機械の数**（`.claude/knowledge/mechanization-backlog.md`）。

## 手順0: ハーネスの版を確かめる

**worktree でも agent と skill は主チェックアウトから読まれる。** `.claude/` をブランチで直しても、
そのブランチのレビューには届かない。差のあるファイルを出す。

```bash
MAIN="$(git rev-parse --path-format=absolute --git-common-dir)/.."
git ls-tree -r --name-only HEAD -- .claude/agents .claude/skills |
  while read -r f; do
    diff -q <(git show "HEAD:$f") "$MAIN/$f" >/dev/null 2>&1 || echo "差あり: $f"
  done
```

効かせたい規約は、reviewer へのプロンプトに本文ごと書く。

## 手順1: 指摘を集める

`$ARGUMENTS` 未指定なら `git diff main...HEAD --stat` と `git status --porcelain`。

**メインが見る。** 差分が大きいときだけ範囲で割る。

| 範囲                     | reviewer               |
| ------------------------ | ---------------------- |
| `src-tauri/`（crate 別） | `rust-reviewer`        |
| `src/`（レイヤ別）       | `react-reviewer`       |
| `docs/`、`.github/`      | `oss-hygiene-reviewer` |

プロンプトに含めるもの: 見るファイルの一覧と見ない範囲、変更の目的、仕様のパス、
`mechanization-backlog.md` の「機械では止まらないもの」。**会話の経緯は渡さない。**

指摘は差分の中だけ。既存の問題は指摘しない。`機械` の列に名前があるルールも指摘しない。

全部読んだら、**「見ていない範囲」に変更の中心が入っていないか**を確かめる。入っていたら、そこだけ見る。

## 手順2: 修正計画を作る

**指摘には必ず修正計画を添える。** 計画の無い指摘は報告しない。全部読んでから作る。

| 順  | ファイル:行 | ルール ID | 確信度 | 行き先 | 修正案 | 壊しうるもの |
| --- | ----------- | --------- | ------ | ------ | ------ | ------------ |

**行き先**: 機械にする / 直す / 送る。**機械 → 直す、の順**に並べる。

- **機械にする**: lint、型、ラチェット、テストで落とせる。同種を全部塞ぐ。これを最優先にする
- **直す**: 機械にできないが、いま直す。手順4の fixup にする
- **送る**: 範囲外。Issue か `docs/IDEAS.md`（分類は `/implement` 手順7）

計画で必ず問うこと。

- `mechanization-backlog.md` に既にあるか。あるなら回数を増やして今回入れる
- 同種が他に何箇所あるか
- 状態を触る直しは、変わるセルと同じ行の他のセルを見たか
- 画面の欄や文言を足すなら、`/spec-draft` の骨格のどこに置くか
- 同じ機構に3件以上集まるなら、個別に直す前に機構を落とす案を1行書く
- 当たるルールが無い本物の指摘は `R-新規` と書き、ルール案を添える

## 手順3: 1回だけ承認を取る

計画の表を出し、`AskUserQuestion` で1問だけ聞く。「全部進める（推奨）」と「進めない」の2択。
番号を外す指示は Other で受ける。**指示どおりに計画を確定し、聞き直さない。**
指摘が0件なら聞かずに終える。

## 手順4: 直す

計画の順に直す。コミット前に検証を通す（`.claude/hooks/verify-gate.sh` が横取りする）。
**落ちたら直す。飛ばさない。**

**指摘の修正は、対象のコミットへの `fixup!` として積む。** 畳むのは `/organize-commits`。

- `git absorb --base <基点>` があれば使う。**`--and-rebase` は付けない**。対象が見つからない差分は index に残るので、手で `git commit --fixup=<sha>` にする
- `git absorb` は `git commit` を通らず検証ゲートが走らないので、後で `npm run verify` を通す。取り消しは `git reset --soft PRE_ABSORB_HEAD`
- 無ければ `git commit --fixup=<sha>`。1指摘1コミット
- **新しいコミットにするのは、レビューで新要件が出たときと、対象のコミットが無い検査の追加だけ**

走査を書くときは `mechanization-backlog.md` の「既知の罠」を読む。
**「見つけた件数が0」と「見たセルが0」を区別する。** 走査型のテストには件数の下限を置く。

## 手順5: 2周目

**手順4の差分だけを見る。** 新しい範囲へ広げない。

- 入れた検査を、直す前の状態に戻して落ちることを確かめる
- 計画の「壊しうるもの」が壊れていないか
- 差分が新しく作った確信度80以上の問題だけを直す。承認は取り直さない

ここで終わり。差分の外の新しい指摘は次の PR の入力で、周回を延ばす理由にしない。

## 報告書

`.claude/reviews/<YYYY-MM-DD>-<slug>.md` に**1本だけ**書く。

```markdown
# レビュー <slug>

- 日付 / 範囲 / 割り方 / 対象コミット

## 修正計画

## 入れた機械

## 直した指摘（短ハッシュ）

## 送ったもの（行き先の番号）

## 見ていない範囲
```

## やること

- 2周で止める。全部読んでから直す
- 機械にできる指摘は機械にする
- 指摘を落とすときは行き先を書く
- 走査型のテストには件数の下限を置く
- 検証を通してから完了と報告する
