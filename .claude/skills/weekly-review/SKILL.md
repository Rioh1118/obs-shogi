`docs/OPERATING-MODEL.md` の §3 に従って週次レビューを進行する。**あなたが決めるのではなく、ユーザーが決めるのを補助する。**

## 最初に読むもの

1. `docs/PREMISES.md`
2. `docs/OPEN-QUESTIONS.md`
3. `docs/decisions/LOG.md`（前回の行）
4. `gh issue list --assignee @me --state open`（Now）

## 進行

### 手順1: 前提の点検（最重要。飛ばさない）

`PREMISES.md` で `次回確認` が今日より前の前提をすべて挙げる。各々についてユーザーに問う:
「まだ成り立っているか / 確認する手段はあるか / 覆っていないか」

- 覆っていれば ❌ にし、**依存する決定（ADR）を書き直すところまでやる**。前提だけ直して方針を放置しない
- 確認できたら `確認日` を今日に更新する
- 確認する手段が無いなら、そう書く（「未確認のまま使っている」と明示することに意味がある）

期限切れが1つも無ければ「点検対象なし」と言って手順2へ。

### 手順2: 決定を1件だけ確定させる

`OPEN-QUESTIONS.md` の最上位（🔴 が優先）を1つ取る。

- 「決めるのに要るもの」が揃っているか確認する。揃っていなければ**決めさせない**。代わりにその項目を更新して次週に送る
- 揃っていれば決める。決まったら `docs/decisions/NNNN-<slug>.md` に ADR を書き、`OPEN-QUESTIONS.md` から削除する
- **2件目に進まない。** 決定のバッチサイズを1に保つのがこのループの目的

ADR の形式:

```markdown
# ADR-NNNN: <決定の要約>

- 日付 / 状態（採用 | 廃止 | ADR-XXXX により置換）

## 文脈 / 決定 / 理由 / 結果（何を諦めたか含む） / 依存する前提（P-XXX）
```

### 手順3: Now の確認

現在 assignee が自分の issue を確認する。続けるか差し替えるか。
差し替えるなら**理由を1行残す**。差し替え頻度そのものが指標なので、黙って差し替えない。
assignee が2件以上あれば WIP 違反なので指摘する。

### 手順4: 摩擦の集計

ドッグフーディング記録をユーザーに出してもらう。**3回以上出た摩擦だけ**を issue 化候補にする。1〜2回は雑音として扱う。
新規 issue は「6週間以内に着手するもの」だけ。それ以外は `docs/IDEAS.md` に1行追記。

## 最後に

`docs/decisions/LOG.md` に1行追記する:

```
YYYY-MM-DD | 決定: <ADR番号と要約 または 「なし（理由）」> | Now: <#番号 継続/差替> | 前提: <点検結果>
```

そのうえで、変更した docs をコミットするか確認する。

## 禁止事項

- ユーザーの代わりに方針を決めない。選択肢と根拠を出すところまで
- 1サイクルで2件以上の決定を確定させない
- 「進んでいる感じ」を進捗の根拠にしない。マージされた成果と変わった決定だけを数える
- 前提の点検（手順1）を時間が無いからと飛ばさない。それを飛ばすと、この仕組み全体が意味を失う
