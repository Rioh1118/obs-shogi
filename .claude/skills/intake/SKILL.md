**与件台帳**を作る。解決策を考える工程ではない。「何が問題で、何を守り、何をしないか」を、
出典つきで1行ずつにする。

## 仕様ができるまで

前の工程の成果物を次の工程が読んで始める。**工程の中の判断は `/decide` が決める。** 人は成果物と判断ログを見る。

| 工程         | skill                     | 渡すもの                                       | 決めること               |
| ------------ | ------------------------- | ---------------------------------------------- | ------------------------ |
| 与件整理     | `/intake`                 | `.claude/plans/<slug>/ledger.md`               | 与件と非ゴール           |
| 調査と裏取り | `/survey`                 | `research/` の事実と `<slug>/survey.md`        | 標準に寄せる／独自を保つ |
| トンマナ     | `/tone-manner`            | `docs/spec/design-language.md` と `index.scss` | 方向（3案から）          |
| 画面の作り直し | `/design-rework`        | `design-<画面>/feedback.md` と見本             | 人が判定する見た目       |
| 叩き台と仕様 | `/spec-draft`             | `docs/spec/` の仕様と見本                      | 見本と受入条件           |
| 状態遷移     | `/state-transition-table` | `docs/state-transitions/<slug>.md`             | 表が出した新しい論点     |
| 起票         | `/spec-to-issues`         | Issue と仕様への番号の書き戻し                 | 起票の一覧               |
| 実装         | `/implement`              | PR                                             | 動くものが良いか         |

- **戻る。** どの工程でも、考えていない論点が出たら台帳に足し、そこから下をやり直す
- **整える。** 工程の終わりごとに台帳の `文書の状態` を見直し、その工程の決定が古くした文書を足す。
  実装の PR までに行き先どおり片付ける
- **省く。** 外の標準に関わらないなら調査を、画面の見た目が既存の規則で足りるならトンマナを、
  状態も非同期も無いなら状態遷移を省く。省いたことと理由を台帳に1行書く
- 台帳は作業の記録。残る事実は `research/`、決定は ADR、未決は `docs/OPEN-QUESTIONS.md`、
  仮定は `docs/PREMISES.md` へ移す

## 手順0: 手持ちを棚卸しする

問う前に読む。**読んだものを台帳の冒頭の `文書の状態` に1行ずつ書く。**

| 文書 | 何の正本か | 状態 | 行き先 |
| ---- | ---------- | ---- | ------ |

**状態**は 現役 / 古い / 他と食い違う。**行き先**は、古い・食い違うものをどこで直すか。

- `docs/proposals/` の案も読む。`次回確認` を過ぎた前提は「古い」として扱い、手順4で確かめる
- どちらが正本かは `docs/OPERATING-MODEL.md` §1 の置き場で決める
- 文書が現物と違えば、現物を事実として文書を直す
- 決定どうしの食い違いは手順4で `/decide` が解く。ADR は書き換えず supersede する
- 見るのはこの作業に関わる文書だけ。全文書の棚卸しはしない

`docs/spec/`（該当の screens / features）、`docs/state-transitions/`、`docs/PREMISES.md`、
`docs/OPEN-QUESTIONS.md`、`docs/decisions/`、`research/`、`.claude/plans/`、関連 issue。
基準は `origin/main`。コミットハッシュを書く。

## 手順1: 分解する

発言を1行1件に割り、下の表にする。

| ID  | 種別 | 与件 | 出典 | 確度 | 状態 |
| --- | ---- | ---- | ---- | ---- | ---- |

- **種別**: 問題 / 目的 / 要望 / 制約 / 非ゴール / 前提 / 問い
- **出典**: 発言（日付）/ `path:line` / issue 番号
- **確度**: 言明（人が言った）/ 確認（現物を開いた）/ 推定（根拠を併記）
- **状態**: 確定 / 要調査 / 要決定 / 保留（何が要るかを併記）

解決策の形で来た要望は、**言葉をそのまま残し**、解いている問題を別の行に書く。
「スライダーが要る」なら、要望と「範囲のある数を手早く変えたい」の2行になる。

完了: 発言の全文がどれかの行に対応している。

## 手順2: 現物と突き合わせる

各行を手順0の文書とコードに当て、**衝突**の節に書く。

- 既に済んでいる（どのコミットで）
- 現物と合わない
- 過去の決定・前提と矛盾する（ADR の番号、P-NNN、Q-NNN）

**矛盾はここで解決しない。** 手順4へ送る。決定を覆すなら新しい ADR になる。

完了: 全行に「衝突なし」か衝突の中身がある。

## 手順3: 抜けを走査する

次の軸を **明確 / 一部 / 無い** で埋める。無い軸は「問い」の行にする。

誰が使うか ／ 成功した状態（何が通れば画面を出してよいか）／ 非ゴール ／ データと後方互換 ／ 外部との境界（プロセス・規格）／
失敗と復帰 ／ 空・読み込み中 ／ 性能の目安 ／ 語彙 ／ 見た目と言葉 ／ テストをどこで掛けるか

**「標準」「普通」「他もそう」と書かれた与件は全部 `要調査`** にする。裏取りが済むまで確定にしない。

## 手順4: 判断する

衝突と問いのうち、**答えで作るものが変わるものだけ**を `/decide` に渡す。事実は調べ、
人しか知らないことは前提を置いて判断ログに書く。範囲を変える判断は `/decide` の止まる条件に従う。

## 手順5: 渡す

台帳の末尾に **一文の目的**、**次の工程で答える問い**、**判断ログ** を書く。

完了:

- 全行に種別・出典・確度・状態がある
- `文書の状態` の古い・食い違う行に行き先がある
- `要決定` が0件（残すなら保留に落として理由がある）
- 非ゴールが1行以上ある
- 手順3の軸が全部埋まっている
