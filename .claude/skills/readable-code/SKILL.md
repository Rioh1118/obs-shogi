読み手はコードジャンプで追い、**置き場 → 名前 → 型 → コメント**の順に推測する。
どこかの段で推測が外れたら、その段を直す。下の段で埋めない。名前で言えることをコメントに書かない。

## どの skill を呼ぶか

| 場面                         | 呼ぶ skill                                         |
| ---------------------------- | -------------------------------------------------- |
| 新しいコードを書く           | この skill の「書くとき」                          |
| 書いたコードや差分を確かめる | この skill の「確かめるとき」                      |
| 既存コードを整理する         | `/tidy-code`（1ディレクトリか1スライス）           |
| リポジトリ全体を棚卸しする   | `/cross-cutting-audit`（コードを変えない）         |
| 判定の後に修正まで回す       | `/review-and-plan`（ルール ID と計画つき）         |
| 名前を決める、見直す         | `/naming`                                          |

設計の判断は `docs/rules/`、語は `CONTEXT.md`、コメントの規則は `CONTRIBUTING.md`「コメントの書き方」が正本。
ここには**読み手の問いと、このリポジトリで起きた形**だけを置く。実測は `references/evidence.md`、
コメントの判定の型は `references/comments.md`、出典は `references/sources.md`。
判定が割れたら `/decide` で決める。**人の確認を待たない。**

## 読み手の問い

上から順に問う。1つでも「いいえ」なら直す。ルール ID があるものは `docs/rules/` で判定する。

### 1. 探せるか

| 問い                                                         | 判定                                                                                                                 |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| 責務の語で grep して実装に着くか                             | 公開の名前と内部の名前を揃える。コマンドと実装で語が違うと名前で辿れない（`mechanization-backlog.md` の Tauri コマンドの行）                     |
| ファイルの役割を1文で言えるか                                | 言えて「と」が要らない（R-RES-2）。`utils` `common` `misc` は役割が無い                                               |
| 同じ名前のファイルはパスで役割が分かるか                     | `types.ts` `provider.tsx` はスライスの決まった役割なので良い                                                          |
| ファイルが大きいとき、責務が複数か                           | **行数は調べる入口で、割る理由ではない**（ADR-0009）。テストを除いた行数を見て、冒頭の1文が書けるかで決める           |

### 2. 名前から推測できるか

- **決めるときは `/naming` を通す。** ここでは読んで推測できるかだけを問う
- 関数は**動詞＋目的語**、真偽は問いの形（R-NAM-5）。読む名前の関数は書き換えない（R-EFF-2）
- 同じ役割に同じ動詞。`settings` crate は3モジュールが `read_or_default` / `write`、1モジュールが `load` / `save` と割れている（R-NAM-4）
- 違いを修飾語で言う。`eqMoveFull` / `eqMoveMinimal` は何の完全さかが分からず、`eqMove` が別名として3つ目に居る
- 比喩より実物の語。`口` `門` `札` の代わりに関数・経路・引数と書く（`references/comments.md`）

### 3. 型から推測できるか

| 対象             | 判定                                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| 取りえない状態   | 判別できる union と enum で消す（R-TST-1、R-CHG-2）                                                                   |
| 意味の違う値     | 別の型にする（R-TST-2、R-RSA-7）。`KifuCursor` と `CursorKey` が見本                                                  |
| 真偽の位置引数   | 呼び手の行で意味が読めないなら enum か名前つきの引数にする（R-RSA-7）。真偽の組が取りうる値を余らせるなら union にする |
| trait            | 差し替えが実在するときだけ（R-RST-1）。`BlobStore` は `DiskStore` と `InMemory` の2実装で、テストの差し替えも実在に数える |
| interface と type | 使い分けは決まっていない（`mechanization-backlog.md`）。**触ったファイルの形に揃え**、書き換えで差分を増やさない       |
| ジェネリクス     | 呼び手が別の型を実際に渡すときだけ。`cloneJkf<T extends …>` のように型引数が目印でしかないなら、そう書く              |
| 構造体           | 同じ欄を束で渡し続けるなら型にする（R-RES-5）。Rust の総称の境界は `impl` に書く（R-RST-5）                            |

### 4. コメントで補えるか

**名前と型で言えないことだけを書く。** 規則は `CONTRIBUTING.md`、判定は `references/comments.md` の順で行う。
最初に問うのは1つ。**そのコメントを消して、第三者が何を誤解するか。** 答えられないなら消す。

### 5. 同じものか、違うものか

- **同名異処理**: 名前が同じで意味が違うなら改名する。`reducer` のように役割が同じなら残す（R-NAM-3）
- **異名同処理**: 本体を読み比べる。`deepClone`（`features/settings/lib/presetDialog.ts`）と `clonePreset`（`entities/engine-presets/lib/normalize.ts`）は同じ本体の写し
- **まとめる**: 「片方の仕様が変わったら、もう片方も必ず変わるか」が「はい」のとき（R-DUP-1）。判定、形式、上限の写しは数によらず1つにする（R-DUP-3）
- **まとめない**: 形が同じだけのもの。`cloneJkf` は `undefined` のキーを保つ理由があり、`JSON` の退路を持つ上の2つに寄せてはいけない。`docs/rules/common.md` の R-DUP-2、R-DUP-4 で判定する
- 共通の関数に呼び手ごとの旗が増えたら、呼び手へ戻す（R-DUP-4）。置き場の名前に困るなら概念がまだ無い（R-DUP-5）

## 書くとき

1. 読む人が最初に開く場所を決める。責務の1文を書き、既存のどのスライスに入るかを決める
2. 公開する関数と型の**名前と型だけ**を先に書く。本体を読まずに使い方が分かるかを問う
3. 説明しにくければ、説明を足さず設計を直す。doc の要約が「〜と〜」になるなら割る
4. 本体を書く。途中で説明の行が要るなら、その塊を名前のある関数にできないかを問う
5. 最後にコメントを書く。名前と型で言えなかった制約、理由、順序だけを残す
6. 新しい語は先に `CONTEXT.md` へ足す

完了: 上の5つの問いに「いいえ」が無い。`npm run verify`（Rust を触ったら `npm run verify:rust`）が通る。

## 確かめるとき

1. 範囲を決める。指定が無ければ `git diff main...HEAD`
2. 差分の宣言を、**本体を読む前に**名前と型だけで読み、処理を推測して書き留める
3. 本体を読み、推測との差を見る。外れた箇所がそのまま所見になる
4. 次にコメントを読み、`references/comments.md` の順で判定する
5. 異名同処理の候補を探す。`inventory.mjs` は `/cross-cutting-audit` のものを範囲つきで使う

出力は `.claude/skills/review-protocol/SKILL.md` の形式。確信度80未満と好みは出さない。
機械が見ているもの（`docs/rules/` の `機械` の列、`CONTRIBUTING.md`「機械で止めているもの」）は指摘しない。
**指摘の前に、機械にできないかを問う。** できるなら検査にするか `.claude/knowledge/mechanization-backlog.md` に回数を足す。

完了: 差分の全ての宣言に推測を当てた。所見にルール ID か「R-新規」が付いている。
