**語はドメインから、形は言語から取る。** 語の出どころを調べずに名前を発明しない。
読み手が初めて見る語は、推測の材料にならない。判断は `/decide` で決める。

正本は語が `CONTEXT.md`、規則が `docs/rules/` の R-NAM-*、R-RSA-1、R-RSA-2。対応表と慣習は `references/vocabulary.md`。

## 手順1: 概念を1文で書く

**名前を考える前に**、次を埋める。埋まらないなら設計が先。

| 項目   | 関数                     | 型・値                 |
| ------ | ------------------------ | ---------------------- |
| 何か   | 何を返すか、何を起こすか | 1つの値が何を表すか    |
| 境界   | 外へ出るか（線の名前か） | 同左                   |
| 作用   | 読むだけか、書き換えるか | 書き換えられるか       |
| 寿命   | 同期か、失敗するか       | どこで生まれ、どこで死ぬか |

**線の名前は別に扱う。** Tauri コマンド、serde の欄、イベント名、保存形式は変えると外が壊れる。

完了: 1文があり、「と」で繋がっていない。繋がるなら割る。

## 手順2: 内側の語を調べる

同じ意味の語が既にあるかを、**類語まで**機械で調べる。

```bash
N=.claude/skills/naming/scripts/word-usage.mjs
node $N word <候補> <類語> <類語>   # 語を含む宣言を場所つきで並べる
node $N verbs <範囲>                # その範囲の動詞の表
```

1. `CONTEXT.md`、`docs/decisions/`、`docs/spec/design-language.md` の語を引く
2. 類語を3つ以上挙げて走らせる。読む系なら `get read load fetch find lookup resolve`
3. **0件は「無い」の証拠にならない。** 宣言を拾えていない場合があるので `grep` で確かめる

完了: 類語ごとの件数と、代表の宣言の場所がある。

## 手順3: 既存の語が妥当かを確かめる

**数が多い語が正しいとは限らない。** 本体を読み、同じ語の宣言が同じ契約かを見る。

| 見えたもの                                 | 判定                                                         |
| ------------------------------------------ | ------------------------------------------------------------ |
| 同じ語が同じ契約                           | **揃える。** その語を使う                                    |
| 同じ語が別の契約                           | 語を分ける（R-NAM-3）。新しい名前に同じ語を足さない          |
| 別の語が同じ契約                           | どちらかへ寄せる（R-NAM-4）。寄せる先を手順4で決める         |
| 語が概念からずれている（`aiName` など）    | 正しい語を決め、`CONTEXT.md` の「揺れが残っているもの」へ    |

契約として比べるのは、戻り値、副作用、失敗の形、コスト。`read_or_default` と `load` が同じ契約かは本体でしか分からない。

完了: 判定と、読んだ本体の場所がある。

## 手順4: 外の語を調べる

上から順に当てる。**上の層に語があれば、下の層で言い換えない。**

| 順 | 層                 | 見るもの                                 | 例                                             |
| -- | ------------------ | ---------------------------------------- | ---------------------------------------------- |
| 1  | 外部仕様           | USI、SFEN、CSA、KIF、JKF、Tauri の API   | `bestmove`、`multipv`、`forks`                 |
| 2  | 共同体の語         | 将棋の語、将棋ソフトと GUI の語          | 局面は `position`、持ち駒は `hand`             |
| 3  | 言語と枠組みの慣習 | Rust API Guidelines、React、TSDoc        | `to_` `into_` `as_`、`use`、`on` と `handle`   |
| 4  | 依存の語           | 標準ライブラリ、`tsshogi`、`tokio`       | `Iterator` の `map`、`AbortController`         |
| 5  | 一般の語           | 辞書で英語の語義を確かめる               | 語義の広さ、別の分野での意味                   |

- **一次情報で確かめる。** 記憶で語を決めない。読めた出典を判断ログに書く
- **確立した意味を外さない。** USI の `mate` は `go mate` と `score mate` で別の意味を持つ。専門家を驚かせる使い方をしない
- **略語は検索で意味が出るものだけ。** `sfen`、`usi`、`pv` は良い。`cstmr` の形は作らない
- **日本語の語**: 英語に定まった語があれば英語。無ければローマ字を1つに決める。外部仕様の綴りは残す（`tesuu`）
- **TS と Rust で語を揃える。** 違うのは大文字小文字だけ（R-TST-5）

完了: 1〜4 の層を見た結果があり、語が無い層は「無し」と書いてある。

## 手順5: 候補を比べて決める

候補を2つ以上出し、`/decide` で決める。問いは次の順。

1. **誤解**: 呼び出しの行だけを読んだ第三者が、別の処理を想像しないか
2. **衝突**: `word-usage.mjs word <語>` で別の意味が既に居ないか
3. **探索**: 責務の語で grep して着くか。公開の名前と内部の名前が揃うか
4. **形**: 動詞＋目的語か、問いの形か、語順が周りと同じか（`references/vocabulary.md`）
5. **長さ**: 使う範囲が広いほど長く。10行で消える変数は短くてよい
6. **型の重複**: 型が言うことを名前で繰り返さない

名前に「と」や `And` が要るなら手順1へ戻る。素直な名前が付かないなら設計を疑う（R-NAM-1、R-DUP-5）。

## 手順6: 残す

- 新しい語は、コードより先に `CONTEXT.md` へ足す。列は `UI の表記`、`コードの名前`、`意味`、`使わない語`
- 外部の語との対応が増えたら `references/vocabulary.md` の表に足す
- 既存の宣言の改名は、`/tidy-code` の「改名」の1コミットで行う。線の名前は変えない
- 判断ログを残す。利用者が見る価値のある判断は、`/decide` の手順で PR の確認事項へ載せる

完了: 判断ログに候補、選んだ語、調べた層、読んだ出典がある。
