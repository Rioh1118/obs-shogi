**外向けのテンプレート（`.github/ISSUE_TEMPLATE/`）とは別の型。**
あちらは「コードを読んでいない人が症状を伝える」ため。こちらは
**「コードを読んで再現を確かめた人が、判断に足る材料を残す」**ため。

規約の案は `docs/proposals/issue-and-label-conventions.md`（**まだ未採用**）。
ここには**いま実際に打てる書き方**だけを置く。

## 立てる前に

`/implement` 手順7 の分類を先に通す。**表はあちらが唯一の出典。ここに写さない。**

issue にするのは次の2つだけ。

- **範囲の外にあり、かつ6週間以内に着手する**もの
- **直し方に判断が要る**もの（ユーザーに選ばせる）

根拠は `docs/IDEAS.md` の運用ルール。

> issue を新規に立ててよいのは **6週間以内に着手するもの**だけ。それ以外は `IDEAS.md` に1行。

**6週間以内に着手しないなら issue にしない。**

## 立てる前に確かめること

**推測を issue にしない。** コードを読んだだけの見立ては所見ではない。

- [ ] **再現を確かめた**（実際に踏んだ / テストで再現した / 該当行を開いて論理を追い切った）
- [ ] **数えた。**「多い」「ほとんど」でなく件数
- [ ] **既存の issue を検索した**（`gh issue list --search "<語>"`）
- [ ] 触った箇所のファイル名と行番号を控えた

## タイトル

**症状を書く。原因や対策を書かない。**

|     | 例                                                                         |
| --- | -------------------------------------------------------------------------- |
| ✅  | `検索に出るのに開けない棋譜がある`                                         |
| ✅  | `保存できない理由が英語のまま出る。しかも一番起きる経路では誰にも見えない` |
| ✅  | `write_new_file だけ atomic でなく、書き込み途中で壊れたファイルが残る`    |
| ❌  | `read_text_portable をリファクタする`（対策が主語）                        |
| ❌  | `文字コードの扱いを改善すべき`（「〜すべき」を使わない）                   |
| ❌  | `エンコーディングのバグ`（何が起きるか分からない）                         |

**数えたなら括弧で数字を入れる。**
`（5経路のうち塞がっているのは1つ）` / `（直近6本中1本）` / `（レビュー7ラウンドで毎回出た）`

## 本文の型

見出しは固定しない。**次の5つを、この順で、必要なものだけ書く。**

### 1. 事実

**表にできるなら表にする。** 経路・場所・実際の挙動を並べる。
場所は `ファイル:行` で書く。開けば確かめられる形にする。

```markdown
| 経路                  | 試すもの                                            | 場所                        |
| --------------------- | --------------------------------------------------- | --------------------------- |
| 索引作り（KIF / KI2） | クレート + UTF-16LE/BE、EUC-JP、...                 | `search/kifu_reader.rs`     |
| 画面で開く            | UTF-8 → だめなら Shift_JIS を**必ず成功として返す** | `file_system/operations.rs` |
```

### 2. 何が起きるか

**利用者から見た症状を書く。** ここが本文の核。

```markdown
- **EUC-JP の `.kif`**: 索引には入るが、ツリーから開くと化けた文字列を
  「成功」で返し、TS のパーサが落ちる。利用者から見ると**「検索では出るのに開けない」**
```

内部の話しか書けないなら、**それは本当に issue にする価値があるか**を疑う。

### 3. 付随（任意）

同じ場所で見つかったが直接の原因ではないもの。**混ぜずに節を分ける。**

### 4. 直し方の案（任意）

**断定しない。** 判断が要る点を明示する。
決めきれないなら「**決めること**: A にするか B にするか」の形で書く。

### 5. 出どころ

**必ず書く。** どこから出てきたかが分かると、後から重み付けできる。

```markdown
#318 のレビュー `.claude/reviews/2026-08-31-skc-v040-r1.md`（architecture）。
```

## ラベル

**実在するラベルから選ぶ。存在しないラベルを指定すると `gh` は issue を作らずに落ちる。**

```bash
gh label list --limit 60      # 打つ前に必ず見る
```

2026-09-02 時点で実在する `area:` は **`area:engine` / `area:book` /
`area:analysis` / `area:ui` の4つだけ**。`area:kifu` / `area:search` /
`area:game` / `area:build` は `docs/proposals/issue-and-label-conventions.md` が
足そうとしている案で、**まだ作られていない**。

- **種類**を1つ: `bug` / `enhancement` / `documentation`
- **領域**を1つ以上: 実在するものから。**該当が無ければ領域は付けずに立て、
  足りないラベルを提案へ書き足す**（立てられない方が損）

```bash
gh issue create --title "..." --body-file <scratchpad>/issue.md \
  --label bug --label area:engine
```

## epic を立てるとき

**両方を満たすときだけ。**

- 束ねる issue が**同じ判断を共有している**（判断1回で PR が1本になる）
- 吸収する issue を**close する**（open のまま束ねない）

本文の型（#290 の形）。

```markdown
<一段落で、何がずれているか>

## なぜ1つにまとめるか

<判断を1回にまとめられる理由>

## 吸収した issue（close 済み。実測は各 issue の本文に残っている）

- [ ] #201 <一行要約>。**決めること**: A にするか B にするか
- [x] #260 <一行要約>

## 独立して残している issue

- #258 <理由つきで>

## 関連

<先に埋めないと踏めない依存があれば>
```

**進捗管理のために epic を立てない。** それは `docs/OPERATING-MODEL.md` の週次レビューの仕事。

## 禁止事項

- **再現を確かめずに立てる**
- **「〜すべき」で書く**（`〜という入力で〜になる` にする）
- **件数を「多い」で書く**
- **6週間以内に着手しないものを issue にする**（`docs/IDEAS.md` へ1行）
- **実在しないラベルを指定する**（`gh` が落ちて issue が作られない）
- 対策をタイトルにする
- 出どころを書かない
