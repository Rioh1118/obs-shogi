`/implement` で積んだコミットを、**読み手が知りたい単位**へ並べ直す。

`/implement` の手順5（レビューのループ）を抜けた後、手順10（PR）の前に使う。
`/review-round` `/review-fix` と同じ粒度の道具で、単独でも呼べる。

## なぜ要るのか

`/implement` の手順3 は「1コミット = 1つの変更」で刻ませ、
`/review-fix` は「1所見 = 1コミット」で直させる。**どちらも正しい。**
その結果、ブランチにはこういう並びが残る。

```
feat: 対局の Player 抽象を足す
fix: レビュー B1-1 — null の扱いを直す
fix: レビュー B1-2 — 型を絞る
docs: レビュー B1-3 — コメントの断言を直す
fix: レビュー B2-1 — 前のラウンドで入れた退行を戻す
...
```

**これは「レビューの往復の履歴」であって「変更の履歴」ではない。**
PR のレビュアーも、半年後に `git log` を読む人も、
「どの指摘で何を直したか」ではなく「**何をどう変えたか**」を知りたい。

`CLAUDE.md` は「経緯は git log と PR に残す。コードには現在どうあるべきかだけを書く」と決めている。
**その git log がレビューの往復で埋まっていると、決めた置き場が仕事をしていない。**

## 並べ直さない方がよい場合

先に判定する。**既定は「触らない」。**

| 状況                                                     | どうするか                                 |
| -------------------------------------------------------- | ------------------------------------------ |
| **作業ツリーが汚れている**（未コミット・未追跡がある）   | **触らない。**手順4 が巻き込む             |
| コミットが3つ以下                                        | **触らない。**読める                       |
| 各コミットが独立して意味を持ち、レビュー由来のものが無い | **触らない**                               |
| **push 済み**                                            | **触らない。**履歴を書き換えない           |
| レビューのラウンドが1回で、所見が2〜3件                  | **触らない。**得るものが少ない             |
| **畳まないと決めたコミットが本体と同じファイルを触る**   | **触らない。**方法A では境界を復元できない |
| コミットが6つ以上あり、うち半分以上がレビュー由来        | 並べ直す                                   |
| 「ついで」が混ざってしまった（手順3 の禁止を破った）     | 並べ直す                                   |

## 目標の形

**1コミット = 元に戻すときに一緒に戻したい塊。** これは手順3 と同じ基準で、
違うのは**レビューで直した分を、それが直した本体へ畳む**こと。

```
feat: 対局の Player 抽象を足す          ← B1-1 / B1-2 / B2-1 を畳んだ
docs: 状態遷移表に対局セッションを足す   ← B1-3 を畳んだ
test: Player の差し替えを固定する
```

**畳んではいけないもの**は次。別コミットのまま残す。

- **本体と独立して意味を持つ修正**（ついでに見つけた既存バグの修正など）。
  `/implement` 手順7 が「別コミットで直す。独立していることを書く」と決めている
- **退行の修正**が、退行を入れたコミットと別の関心事に属する場合
- docs だけの変更と、コードの変更

## 手順

### 1. 範囲を確定する

**シェル変数を使わない。** Bash ツールの状態（環境変数）は呼び出しを跨いで持続せず、
検証ゲートは `git commit` を単独の呼び出しにすることを強制する（`cd` も複合も deny）。
`BASE=...` は次の呼び出しで空になり、**`git reset --soft`（引数なし）は
HEAD へのリセット＝成功する no-op になる。** 積み直しが起きていないのに手順6 が必ず一致する。

作業用のファイルに落として `$(cat ...)` で引く。置き場はセッションの scratchpad
（`/tmp` 直下は、ワークツリーが2つ動いていると衝突する）。

**`W=<scratchpad>` のような変数に入れない。** それも呼び出しを跨がないので、
同じ故障が一段ずれて再発する。**scratchpad の絶対パスを毎回そのまま書く。**
以下では `<W>` と書くが、実際には展開済みの絶対パスを打つこと。

```bash
git merge-base HEAD main > <W>/tidy-base.txt
git log --oneline $(cat <W>/tidy-base.txt)..HEAD
git diff --stat $(cat <W>/tidy-base.txt)..HEAD
```

**作業ツリーが汚れていないことを先に確かめる。**

```bash
git status --porcelain -uall
```

**非空ならここで止める。** 手順2 が記録する安全網は `git diff base..HEAD` で
**未コミットの変更を含まない**のに、手順4 の `git add -A` はそれを群へ巻き込む。
結果、手順6 の比較は必ず不一致になり、指示どおり `git reset --hard` を打つと
**未コミットの変更ごと消える**（reflog の宙に浮いたコミットにしか残らない）。

**押していないことを確かめる。**

```bash
git log --oneline @{u}..HEAD 2>/dev/null || echo "上流なし（未 push）"
```

上流があって、その先に出ているコミットが範囲に入っているなら**そこで止める**。

### 2. 差分の合計を記録する（これが唯一の安全網）

**並べ直しは差分の合計を変えてはいけない。** 前後で一致することを機械で確かめる。

```bash
git diff $(cat <W>/tidy-base.txt)..HEAD > <W>/tidy-before.diff
test -s <W>/tidy-before.diff            # ← 非空であること。空なら基点の取り違え
git rev-parse HEAD > <W>/tidy-head.txt   # 戻れるように
```

### 3. 群に割る

各コミットを読んで、どの群に属するかを決める。**推測で割らない。**
レビュー由来のコミットは、**どのファイルのどの行を直したか**を見て、
それが本体のどのコミットの範囲かで決める。

```bash
git show --stat <sha>
```

**先に「畳まない」と決めたコミットを見る。** それが他の群と同じファイルを触っていたら、
方法A では境界を復元できない。**その時点で並べ直しを中止する**（上の判定表へ戻る）。

### 4. 積み直す

**このリポジトリでは `git rebase -i` が使えない**（対話フラグが通らない）。
2つの方法があり、既定は A。

#### 方法A: soft reset で作り直す（既定）

```bash
git reset --soft $(cat <W>/tidy-base.txt)
git status --short                       # 全ての変更がステージに載っている
git rev-parse HEAD                       # ← tidy-base.txt の中身と一致すること
git diff --cached --stat                 # ← 非空であること
```

**この2つの確認を飛ばさない。** `<W>` を展開し忘れる、あるいは `tidy-base.txt` が無いと
`$(cat ...)` が空になり、`git reset --soft`（引数なし）は
**成功したまま何もしない**。ここで気づかないと最後まで気づけない。

ここから群ごとに `git add` して commit する。

**`git commit` は必ず `-m` を付ける。** メッセージ無しだと `$EDITOR` が開き、
非対話のシェルでは戻ってこない。**1呼び出しにつき1つだけ**（ゲートが2つ以上を deny する）。

```bash
git restore --staged .                       # 一度全部降ろす
git add <群1 のパス...>
git commit -m "<type>: <群1 の要約>"          # ← 別の呼び出しで。ゲートが走る
git add <群2 のパス...>
git commit -m "<type>: <群2 の要約>"
...
git add -A
git commit -m "<type>: <残りの要約>"
```

**群がファイル単位で割れないときは、並べ直しを中止する。**

方法A は全コミットを1つのワークツリー状態に潰すので、**同じファイルの中の
コミット境界は復元できない**。`git add -p` は対話フラグが通らないので使えない。
そこで無理に進めると、**畳んではいけないもの**（上の3つ）を本体へ畳むことになり、
禁止事項に当たる。**手順3 で気づいて「触らない」へ戻るのが正しい。**

#### 方法B（非対話 rebase）は使えない

`GIT_SEQUENCE_EDITOR=... git rebase` も `GIT_EDITOR=true git rebase` も、
**環境変数を前置した綴りは通らない**（ゲートか `.claude/settings.json` の
`permissions.allow` のどちらかで止まる。どちらで止まるかは版による）。
`git rebase -i` そのものもこの環境では通らない。**選択肢として数えない。**

### 5. 検証のコストを見積もる

**`git commit` ごとに `.claude/hooks/verify-gate.sh` が走る。**

**どの種類の変更がどの検証を呼ぶかをここに写さない。** 唯一の出典は
`.claude/hooks/verify-gate.sh` そのもの。**関数名も判定も版で変わる**ので、
関数名すら書かない（実際に、ブランチによって判定の実装が別物になっている）。
走るのは `.claude/settings.json` が指す版（`${CLAUDE_PROJECT_DIR}` 側）であって、
チェックアウトしているワークツリーの版とは限らない。
所要時間の目安は `CLAUDE.md` の検証節（`npm run verify` 約8秒 /
`npm run verify:rust` 約2分15秒）。

    見積り = 群の数 × （そのブランチで実際に走る検証の時間）

**どの検証が走るかは机上で決めない。1群目を積んで測る。**
版によっては、ゲートが**別のディレクトリ**（`${CLAUDE_PROJECT_DIR}` 側）の
`git status` を読んで種類を決めるものがある。ワークツリーで回すと、
手元のブランチが `.rs` を含まなくても Rust の検証が走りうる（逆も然り）。

Rust の検証が走るブランチを10群に割ると20分を超える。**群の数はここを見て決める。**

途中で検証が落ちたら、そこで積み直しが止まる。
`git reflog` と `<W>/tidy-head.txt` から元の HEAD へ戻れる。

### 6. 差分が変わっていないことを確かめる

**これを飛ばさない。** 積み直しの唯一の不変条件。

```bash
git diff $(cat <W>/tidy-base.txt)..HEAD > <W>/tidy-after.diff
test -s <W>/tidy-after.diff             # ← 空同士の一致を「OK」と読まない
diff <W>/tidy-before.diff <W>/tidy-after.diff && echo "OK: 差分の合計は同じ"
```

**一致しなければ元に戻す。**

```bash
git reset --hard $(cat <W>/tidy-head.txt)
```

### 7. 報告書の sha を書き戻す

**`/review-fix` は所見ごとに短ハッシュを報告書へ書いている**（`review-fix` 手順5）。
積み直すとその sha は**1つ残らず到達不能になる**。報告書の存在を守るだけでは足りない。

畳んだ対応が1対1なら旧 sha → 新 sha を報告書へ書き戻す。
1対1でないなら、報告書の sha 欄を **`畳み込み済み`** に一括で置換する。
どちらにせよ、**到達できない sha を報告書に残さない。**

### 8. 報告

- 何コミットから何コミットになったか
- **畳まずに残したものと、その理由**
- 差分の合計が一致したことを明示する
- 検証を通したか（通していないなら「未検証」と明示する）

## レビュー報告書はどうするか

`.claude/reviews/` の報告書は**消さない**。
コミットを畳んでも、**どの所見をどう直したかは報告書が持っている**。
`/review-fix` が結果を書き戻す先はそこで、git log ではない。

PR 本文には報告書のパスと、最終ラウンドで所見が0件だったことを書く（`/implement` 手順10）。
**ただし報告書の中の sha は、手順7 で書き戻すまで信用できない。**

## 禁止事項

- **push 済みのコミットを書き換える**
- **差分の合計を変える。** 並べ直しのついでに直さない。直したいものが出てきたら、
  並べ直しを終えてから別のコミットにする
- **手順6 の確認を飛ばす**
- **到達できなくなった sha を報告書に残す**（このスキルの手順7）
- **検証を飛ばして「整理した」と報告する**
- 独立して意味を持つ修正を本体へ畳む（`/implement` 手順7 の分類を無視しない）
- レビューで直した事実を隠すために報告書を消す
