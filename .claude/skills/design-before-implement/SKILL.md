読むもの: 仕様か Issue、`docs/rules/common.md`、触る言語のルール、`CONTEXT.md`、関わる ADR。
エージェントの使い方は `.claude/rules/agents.md`。この skill はメインだけで足りる。

## 手順1: 現物を数える

変更に関わる識別子を検索し、呼び手、読み手、書き手を**件数で**書く。既存の同じ形を探す。

完了: 「推測」と付く行が残っていない。

## 手順2: 置き場所を決める

ルール `R-RES-*` で決める。

- この変更の責任は誰が持つか。候補が2つあるなら両方を書き、選ばなかった理由を添える
- 新しいファイルを足すなら、既存のどこにも入らない理由を書く
- 依存の向きが下向きのままか。層を跨ぐ import が増えないか

## 手順3: 触るファイルを並べる

ファイルごとに、変える理由を1行書く。**理由を書けないファイルは範囲から外す。**
コミットの切れ目もここで決める。

## 手順4: 共通化を判断する

同じ形の処理ごとに、`R-DUP-*` で判定する。**同じ形というだけでまとめない。**

| 問い                                         | 判定                         |
| -------------------------------------------- | ---------------------------- |
| 判定、丸め、形式、上限など同じ規則の写しか   | まとめる（1か所目でも）      |
| 片方の仕様が変わると、もう片方も必ず変わるか | はい: まとめる／いいえ: 下へ |
| 3か所以上あり、共通点と差分が見えているか    | まとめる案を出す             |
| それ以外                                     | 別のまま。理由を1行書く      |

まとめるなら、名前を先に書く。素直な名前が付かないなら別のままにする。
既存の共通関数に引数や分岐を足す案は、呼び手へ戻す案と比べる。

## 手順5: 副作用と壊しうるものを書く

`R-EFF-*` と `R-ERR-*` に当てる。**どの入力がどの経路を通って何になるか**で書く。
状態か非同期があるなら `/state-transition-table` の表のどのセルを変えるかを書く。

## 手順6: 出力する

重い変更は `.claude/plans/<slug>/design.md` に、中の変更は会話に、次の形で書く。

```markdown
## 設計: <変更の名前>

- 責務の置き場所: <場所と理由>。選ばなかった案: <案>
- 触るファイル:
  | ファイル | 変える理由 | コミット |
- 共通化の判断:
  | 対象 | 判定 | 理由（ルール ID） |
- 語: <CONTEXT.md に足す語。無ければ「なし」>
- 壊しうるもの: <入力 → 経路 → 結果>
- テストを掛ける所: <既存の継ぎ目。できるだけ高い層で1つ>
```

設計の選択に人の判断が要るときだけ、`AskUserQuestion` で1問聞く。それ以外は止まらず実装へ進む。

完了: 全ての欄が埋まり、次の人がこの出力だけで実装を始められる。
