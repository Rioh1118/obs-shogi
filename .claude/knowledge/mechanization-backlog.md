## 走査を書くときの既知の罠

**「見つけた件数が0」と「見たセルが0」を必ず区別する。** この repo で最も繰り返し踏まれている形。
走査型のテストには**件数の下限**（`toBeGreaterThan`）を必須にする。無いと、走査が壊れて
0件を返しても緑になる。`state_transition_cells.rs` は `table_source()` が
`game-session.md` 決め打ちで、他の表を1つも見ていないのにずっと緑だった。

**走査器そのものにテストを置く。** `scssScaleRatchet` はリポジトリ全体の件数しか主張しておらず、
合成 SCSS を食わせる検査が無かった。**そのラウンドの robustness 所見は全て、
走査器に文字列を食わせるだけで再現した。**

**既存の警告が0でないものは `-D` で入れない。** 件数ラチェット（増える方向にだけ落とす）なら
片付けを待たずに今日から張れる。`rustdoc-ratchet.sh`（基準29）と
`knip-ratchet.sh`（基準150）がどちらもこの形。**入れたら変異を当てて落ちることを確かめる**
——`knip` は死んだ `export type` を1つ足して 151 になることで確かめた。

**外部コマンドの人間向け出力を正規表現で数えない。** JSON など形の決まった出力を使う。
`knip-ratchet.sh` は最初 `grep | grep | awk` で見出しを数えていて、
knip が見出しを1行も出さない状況（自分が壊れた・指摘が0件）で最初の `grep` が 1 を返し、
`pipefail` + `set -e` が**何のメッセージも出さずに終了**した。CI がそれで落ちた。
**「数えていない」と「基準と違う」を区別できない検査は、この罠そのもの。**

**stderr を stdout へ混ぜない。** `npx` は `npm warn ...` を stderr に出すので、
`2>&1` で受けると JSON の手前に1行載って解析が必ず落ちる。
診断には要るので、捨てずに別へ受けて失敗時に出す。

## 検証の所要時間（2026-09-08 に段ごとに実測）

**`verify` は 6分02秒だった。段ごとに測ったら8割が1段に集まっていた。**

| 段                                  | 実測        |
| ----------------------------------- | ----------- |
| `test:hooks`（門番自身の検査）      | **4分52秒** |
| `typecheck`（`tsc -b`、冷えた状態） | 35.7秒      |
| `test`（vitest 99ファイル）         | 13.6秒      |
| `ratchet:knip`                      | 12.7秒      |
| `lint`                              | 1.2秒       |

`test:hooks` が重いのは**プロセス起動律速**だから。この機械で `git` の起動は
1回あたり約46ms、`bash -c` が約39ms（`/usr/bin/true` は7.7ms）。
判定を1件ずつ当て、`probe_is_readonly` が動詞ごとに repo を複製するので
数千プロセスが立つ。**内部を最適化する話ではない。**

→ **`verify` から外した。** 守っている不変条件は門番を触ったときしか動かないので、
`.claude/hooks/*.sh` を触ったコミットでゲート自身が走らせる（種類 `hooks`）。
CI に控えを置いた。**`verify` は 6分02秒 → 1分08秒。**

### テストのスコープを絞ってはいけない

vitest はファイル単位で並列化するので wall clock は**最長の1ファイル**が決める。
内訳は走査ラチェット26ファイル/10.4秒、振る舞いテスト73ファイル/45.5秒で、
最長は `features/settings/ui/tabs/__tests__/AiLibraryTab.test.tsx` の16.8秒（30テスト）。

**`vitest --changed` / `related` で絞ってはいけない。** 選択は import グラフで行われるが、
`src/__tests__/` のラチェットは走査対象を `fs` で読むので**import 辺が無い**。
絞るとラチェットだけが黙って走らなくなる——「見つけた件数が0」と同じ失敗の形。

**速くしたいなら最長の1本を割る**（`AiLibraryTab.test.tsx`）。
`entities/analysis/model/__tests__/provider.test.tsx` は `advance()` で
**7,750ms を実時間で待って**いるので、そちらは偽タイマーに寄せられる。どちらも未着手。

## 機械では止まらないもの（＝人／LLM のレビューが見るべき唯一の場所）

全トピックで繰り返し「防げない」と申告された類型。ここ以外を人が見るのは無駄。

1. **コメントが主張する条件と、実装している条件式のずれ。** 全275本を通じて最多。
   `commentHistory` は**経緯**の語しか見ないので、**理由の嘘**には効かない。
   → 対処は1つだけ: **「〜だから」と書いてあったら、その条件式がコードのどの行かを指す。**
2. **文脈を前提にしたコメント。** そのコメントだけを読んで意味が通るか。
   読み手は issue も会話も差分も見ていない。
   → **一部は機械化できる**（下の「新しく機械にできるもの」）が、
   「上と同じ理由で」が指す理由が本当にその上にあるかは読まないと分からない。
3. **`await` を跨いだときに何が古くなるか。** 成立条件が広すぎて走査にできない。テストでしか固定できない。
4. **一意性の断言**（「ここだけ」「〜しか」「N箇所」）。実在検査は通るが、数と範囲は見ていない。
5. **1つの題材で測った結果を一般則として doc に書き、別の題材で崩れる形。**
6. **責務の置き場・命名の割れ・段の割り当て。** 構造の判断そのもの。
   ADR-0009 §6 が「**行数では割らない**」と決めているので、サイズでは代替できない。
   合図は「1ファイルに段を跨ぐ責務が同居」「冒頭の `//!` が『と』で繋がって1行で言えない」。

## 新しく機械にできるもの（この見直しで出た）

- **文脈を前提にした指示語の検出 —— 測ったうえで「入れない」と判断した。**
  `commentHistory` は経緯の語しか見ていない。そこで
  「上と同じ / 同様の理由 / 例の / 先ほど / 後述 / 前述 / 上記の理由」を
  `src/` と `src-tauri/src/` で数えた（2026-09-08）。**該当は「上と同じ」の5件のみ、他は0件。**

  うち**3件は同一の doc ブロック内で直前の行を指していて正当**
  （`src-tauri/src/engine/game/session.rs:335`、`src-tauri/src/engine/utils.rs:133`、
  `src/__tests__/sourceText.test.ts:121`）。
  残り2件（`src/entities/file-tree/model/provider.tsx:627`、
  `src/features/kifu-comment-note/ui/__tests__/KifuCommentNote.test.tsx:160`）は
  別の分岐を指していて書き直す価値がある。

  **語で禁じると3件の正当な用法を誤検知する。** 判定に要るのは
  「『上』が同じブロック内か」で、それは走査の主題が語ではなくブロック境界になるということ。
  **本体より誤検知の抑え方のほうが大きい**ので入れない。再提案するなら、この測定を覆すこと。
