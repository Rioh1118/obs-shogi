# verify-gate の判定

`.claude/hooks/verify-gate.sh` は PreToolUse で `git commit` を横取りし、必要な検証を走らせる。
**素通し（deny も検証もされずに通る）が唯一の致命的な失敗**で、R2 から R11 まで毎ラウンド出た
（G-09 / H-01 / H-02 / I-01 / J-01 / K-01 / L-01 / L-02 / M-02 / N-01 / N-02 / O-02 / P-03）。

毎回「新しい綴り」として1件ずつ潰してきたが、**段が複数あり、どの段で落ちても結果が
「素通し」になる**ことを表にしていなかった。綴りではなく段で見る。

## 段（状態）

| 記号 | 判定条件（式）                                                                                       | 通らなかったときの行き先                                                  |
| ---- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| S1   | `gate_matches_commit "$command"` — コミットを作る git 呼び出しとして切り出せる                       | S2 へ                                                                     |
| S2   | `gate_mentions_commit "$command"` — `git` とコミット動詞が語として現れる                             | **exit 0（素通し）**                                                      |
| S3   | `gate_target_dir "$command" "$cwd"` が非空 — 宛先が自明                                              | deny                                                                      |
| S3'  | `gate_in_project "$project_dir" "$GATE_HOME"` — 宛先の `--git-common-dir` がゲート自身のツリーと一致 | **exit 0（このプロジェクト以外は対象外）**                                |
| S4   | `gate_kinds_for_path` × `git status --porcelain -z --untracked-files=no` — 種類が1つ以上             | exit 0（見えた変更のどれも種類に当たらないとき。1つも見えない場合を含む） |
| S5   | `run_gate` — 選ばれた検証が通る                                                                      | deny                                                                      |

S1 を通れば S3 へ、S1 を落ちて S2 に当たれば deny、S2 も落ちれば**素通し**。

**段の外に免除がある。** 積んだ操作を畳む呼び出し（`gate_is_teardown`）は、
S4 の分類に関わらず `needs_*` を 0 にする（不変条件3）。**数を名乗らない** ——
免除が増えたときに、この行だけが古くなる。

## コマンドの形（イベント）

| 記号 | 形                                                                                           |
| ---- | -------------------------------------------------------------------------------------------- |
| A    | `git commit -m x`（起点の作業ディレクトリで、ディレクトリ指定なし）                          |
| B    | `git status && git commit -m x`（手前が**読むだけ**の git 呼び出し）                         |
| C    | ディレクトリを付け替える（`-C` / `--git-dir` / `cd X &&` / `pushd` / `env -C` / `GIT_DIR=`） |
| D    | コミットを作る別の動詞（`revert` / `cherry-pick` / `merge` / `rebase` / `am` / `pull`）      |
| E    | alias（`git ci`）、alias の合成（`git acp`）                                                 |
| F1   | `git` の綴りにパス修飾や引用が付く（`/usr/bin/git` / `'git'` / `\git`）                      |
| F2   | `git` の綴りが展開でしか決まらない（`$(which git)` / `$x`）                                  |
| G    | 行を跨ぐ（`git \` + 改行 + `commit`）                                                        |
| H    | 引用の中に動詞が出るだけ（`git commit -m "fix: git commit の話"`）                           |
| I    | commit ではなく、`git` と動詞が**同じコマンドに並ばない**（`git add` / `git log`）           |
| J    | commit ではないが、`git` と動詞が**同じコマンドに並ぶ**（`gh pr create --title` の本文など） |

### 埋まっていないセル

- **(D, S4)**: `git rebase main` は S1 を通るが、作業ツリーが clean なら S4 で
  `needs_*=0` になり素通しする。**これは PreToolUse の構造上どうにもならない**
  （コマンドの前に、そのツリーは存在しない）。表に残す
- **(B, S4)**: 手前に**ツリーを変える** git（`add` / `rm` / `mv` / `stash` /
  `checkout` / `restore` / `reset`）を置いた形は、**S1 で deny する。**
  PreToolUse はコマンドが走る前に判定するので、手前で変えると**その前の状態を見る** ——
  `git rm X && git commit` は X がまだ在る状態を走査して「変更なし」と読み、
  検証も deny もせずに素通ししていた。
  **走査の仕方を変えても閉じない**（消される側・これから現れる側は原理的に見えない）ので、
  手前に置ける動詞を列挙する側で塞いである（`GATE_READ_ONLY_VERBS_BASE`）。
  2回の呼び出しに分ければ従来どおり打てる
- **S4 の分類**: `expect_kinds` があるのは `gate_kinds_for_path` 単体で、
  **`git status -z` の出力を食わせる end-to-end のケースは無い**（リネーム2レコード、
  引用符付きパス）

## 不変条件

1. **コミットを作りうるコマンドが、S2 まで落ちて素通しすることは無い。**
   S1 で切り出せない綴りは、S2 が deny 側へ落とす
2. **検証するツリーは、コミットされるツリーと同じ。** 判別できないなら deny（S3）
3. **誤発火は許容する。** 余分な検証が走るだけで、素通しより危険が小さい。
   **ただし S2 の誤発火は例外** —— そこでの誤発火は検証ではなく**無条件の deny** で、
   案内はコミットの打ち方を指示する。**コミットしようとしていない利用者には
   従える操作が1つも無い。** 止まったら `git` と動詞を同じコマンドに書かないこと。
   **ただし積んだ操作を畳む綴りは対象にしない。** `--abort` / `--quit` / `--edit-todo` は
   コミットを1つも作らない。`--skip` は残りを当てるので作りうるが、**その中身は積んである
   patch で、手元のツリーではない。** そして手元のツリーで検証が落ちるなら、
   畳む手段そのものを取り上げることになる。
   ここでは「余分な検証が走るだけ」が成り立たない。
   `--continue` を入れないのは、**あれが作るコミットの中身が手元のツリーそのもの**で、
   1つ目が当たらないから（「途中のツリーでしか打てるか」では区別できない。
   `--continue` にも当たる）。
   **この免除を足した `42a050f2`（PR #237）のメッセージは、訂正前の根拠2つを持ったまま** ——
   「`--skip` はコミットを1つも作らない」と「競合を抱えたツリーでは検証が必ず落ちる」。
   どちらも偽で、上の文がいま持っているのが正しい根拠。
   reword しないのは、以降のハッシュが全て変わって `.claude/reviews/` の参照が空を指すため

## 照合

- 不変条件 1: `expect_mentions` の表が担っている ✓（S1 で切り出せない綴りを S2 が拾う）。
  語彙の取りこぼし側は `expect_alias_resolution` ✓（値に生の改行を含む形を含む）。
  **語彙側だけでは、`$(which git)` のような切り出せない綴りは守られない**
- 不変条件 2: S3 の表（`expect_dir`）が担っている ✓。宛先が別リポジトリのときに
  検証を当てない側（S3'）は `expect_project` の表 ✓
- 不変条件 3: 意図した挙動として R6 で確定。deny 側のケースを表に並べてある ✓。
  畳む操作を除く側は `expect_teardown` の表 ✓（`--continue` と、コミットを作る
  呼び出しを混ぜた綴りが免除に入らないことも並べてある）
