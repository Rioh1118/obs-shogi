# 状態遷移表: updater

対象: `entities/updater/model/provider.tsx`（状態機械）/
`features/updater/ui/UpdaterScreen.tsx`（カード）/
`features/settings/ui/tabs/WorkspaceTab.tsx`（設定の「更新」の節）

**ディスク上の実体を列に持つ。** 更新は「フロントが何を描いているか」だけでは決まらない。
取得が終わった時点ではまだ何も入れ替わっておらず、**入れ替わったかどうかは
`downloadAndInstall` が返る瞬間にしか変わらない。** 片方だけで表を作ると、
その区別がそもそも書けない。

引く plugin は tauri-plugin-updater。**他リポジトリの行番号はすべて `v2.10.1` 時点**
（`src-tauri/Cargo.lock` が固定している版）。リンクはタグで留めてある。

表は 8状態 × 18事象。`✓` は踏んでいるテスト
（`entities/updater/model/__tests__/provider.test.tsx`）。

## ディスク上の実体

**フロントからは観測できない。** `downloadAndInstall` が返す promise が解決するまで、
どこに居るかを知る手立てが無い。**段の側でその区別を持つ**のがこの表の主眼。

| 記号   | 実体                                         | いつ                              |
| ------ | -------------------------------------------- | --------------------------------- |
| **D0** | 触っていない                                 | 取得の前と最中                    |
| **D1** | 検証と入替が進行中                           | 取得の完了から promise の解決まで |
| **D2** | 入れ替わった。走っているプロセスだけが古い   | promise の解決の後                |
| **D3** | 旧バンドルが消え、新しいものが置かれていない | macOS の入替が途中で落ちた後      |

D1 が在るのは、取得の完了を伝える合図が[署名の検証とインストールより前][plugins-workspace-download]に
送られるため。**取得が終わった時点では、まだ何も検証していないし何も入れ替えていない。**

D3 が在るのは、macOS の入替が[旧バンドルを一時ディレクトリへ移してから][plugins-workspace-macos-backup]
[新しいものを所定の位置へ移す][plugins-workspace-macos-place]ため。後半が落ちると、
退避先の一時ディレクトリは関数を抜けるときに破棄される。後半が落ちる条件は
ボリュームをまたぐ移動で、**アプリを外付けディスクに置いた場合**に当たる。

Windows に D2 は無い。インストーラを起動した直後に
[プロセスを終了させる][plugins-workspace-windows-exit]ので、promise は解決も棄却もしない。

## 状態

| 記号   | フロント                       | 実体     | 判定                                        |
| ------ | ------------------------------ | -------- | ------------------------------------------- |
| **S0** | 何も描かない                   | D0       | `phase === "idle"`                          |
| **S1** | 何も描かない                   | D0       | `phase === "checking"`                      |
| **S2** | 告知のカード                   | D0       | `phase === "available"`                     |
| **S3** | 進捗のカード                   | D0       | `phase === "downloading"`                   |
| **S4** | 「更新を適用しています…」      | D1       | `phase === "installing"`                    |
| **S5** | 「更新の準備ができました」     | D2       | `phase === "ready"`                         |
| **S6** | 「更新を取得できませんでした」 | D0       | `phase === "error"`、`stage === "download"` |
| **S7** | 「更新を適用できませんでした」 | D0 か D3 | `phase === "error"`、`stage === "install"`  |

**S7 の実体は決まらない。** 落ちたのが署名の検証なら D0、入替の途中なら D3 で、
plugin はどちらも同じ文字列で返す。だから S7 の文言は「終了すると起動できなくなる
ことがある」と**ことがある**で書いてある——断定すると、検証で落ちただけの回に
入れ直しを強いることになる。

**S0 が4つの意味を兼ねる。** 「まだ確認していない」「確認して更新が無かった」
「カードを閉じた」「飛ばす版だった」が、どれも同じ状態に落ちる。設定の
「最後に確認できた」と「飛ばす設定になっています」が、外からその4つを分ける。

カードだけに任せると、押した本人には何も返らない。

## この表が満たすべき不変条件

1. **「準備ができました」を出してよいのは、実体が入れ替わり終えた後だけ。**
   S4 と S5 を分けているのはこのため。合図（E8）で S5 へ進めると、
   (S5, E12) と (S5, E13) が入替の最中に起きるようになる。
2. **取得を始めてから終わるまで、走る経路は1本。**
   関門を「押した時点の `status`」に置くと破れる（E7 まで動かないため）。
3. **確認しなかったことと、確認して更新が無かったことを、記憶の側で分ける。**
   段はどちらも S0。分けているのは `lastCheckedMs` だけで、**失敗した確認では
   動かさない**ことがその区別を成り立たせている。
4. **閉じられる状態は、閉じた後に復帰の口が在ること。**
   S2 を閉じても次の起動で出る。E16 で消したものは E18 で戻せる。
   **S7 だけはこれを満たさない**——閉じると、実体を失ったことを伝える面が二度と出ない。

## 埋まっていないセル

**フロントの語彙で書けるセルは踏んだ。** 残るのは、実プロセスか plugin の内側が要るもの。

| セル                  | いま起きること                    | なぜ固定できないか                           |
| --------------------- | --------------------------------- | -------------------------------------------- |
| (S4, E15)             | Windows でプロセスが消える        | 実プロセスと Windows が要る                  |
| (S5, E12)             | 新しい版で開き直す                | 実プロセスが要る                             |
| (S5, E13)             | 次の起動が新しい版になる          | 実プロセスが要る                             |
| (S7, E13)             | D3 だった場合、二度と起動できない | 入替の途中で落とす経路が plugin の内側にある |
| (S3, E13) / (S4, E13) | 取得と入替の最中に終了する        | 同上                                         |
| (S0, E14)             | 新しい版に気づかない              | 定期の確認が無いので、踏むセルが存在しない   |

**(S0, E14) だけは性質が違う。** 他の5つは「踏めない」だが、これは
**踏む経路を作っていない**。定期の再確認を足せば埋まる → #432。

## この表が決めていないこと

- **定期の再確認を入れるか。** 入れれば (S0, E14) が埋まる
- **リリースノートを見せるか。** plugin は本文を返すが、どの段にも出していない
- **告知を通知の基盤へ載せ替えるか。** 基盤は失敗のための語彙で、S2〜S5 の4つは
  失敗ではない（ADR-0004 決定5・やらないこと）
