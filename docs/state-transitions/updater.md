# 状態遷移表: updater

対象: `features/updater/lib/useUpdater.ts` / `features/updater/ui/UpdaterScreen.tsx`

**ディスク上の実体を列に持つ。** 更新は「フロントが何を描いているか」だけでは決まらない。
同じ「準備ができました」の1枚が、アプリの実体が**まだ古い**場合と**もう新しい**場合の
両方で出る。片方だけで表を作ると、その区別がそもそも書けない。

引く plugin は tauri-plugin-updater。**他リポジトリの行番号はすべて `v2.10.1` 時点**
（`src-tauri/Cargo.lock` が固定している版）。リンクはタグで留めてある。

表は 8状態 × 15事象。

## ディスク上の実体

**フロントからは観測できない。** `downloadAndInstall` が返す promise が解決するまで、
どこに居るかを知る手立てがコードに無い。

| 記号   | 実体                                         | いつ                              |
| ------ | -------------------------------------------- | --------------------------------- |
| **D0** | 触っていない                                 | 取得の前と最中                    |
| **D1** | 検証と入替が進行中                           | 取得の完了から promise の解決まで |
| **D2** | 入れ替わった。走っているプロセスだけが古い   | promise の解決の後                |
| **D3** | 旧バンドルが消え、新しいものが置かれていない | macOS の入替が途中で落ちた後      |

D1 が在るのは、取得の完了を伝える合図が[署名の検証とインストールより前][plugins-workspace-download]に
送られるため。**取得が終わった時点では、まだ何も検証していないし何も入れ替えていない。**

D3 が在るのは、macOS の入替が[旧バンドルを一時ディレクトリへ移してから][plugins-workspace-macos-backup]
[新しいものを所定の位置へ移す][plugins-workspace-macos-place]ため。後半が落ちると、
退避先の一時ディレクトリは関数を抜けるときに破棄される。後半が落ちる条件は
ボリュームをまたぐ移動で、**アプリを外付けディスクに置いた場合**に当たる。

Windows に D1 と D2 は無い。インストーラを起動した直後に
[プロセスを終了させる][plugins-workspace-windows-exit]ので、promise は解決も棄却もしない。

## 状態

| 記号   | フロント                   | 実体 | 判定                                               |
| ------ | -------------------------- | ---- | -------------------------------------------------- |
| **S0** | 何も描かない               | D0   | `status.phase === "idle"`                          |
| **S1** | 何も描かない               | D0   | `status.phase === "checking"`                      |
| **S2** | 告知のカード               | D0   | `status.phase === "available"`                     |
| **S3** | 進捗のカード               | D0   | `status.phase === "downloading"`                   |
| **S4** | 「更新の準備ができました」 | D1   | `status.phase === "ready"` かつ promise が未解決   |
| **S5** | 「更新の準備ができました」 | D2   | `status.phase === "ready"` かつ promise が解決済み |
| **S6** | 「更新に失敗しました」     | D0   | `status.phase === "error"`                         |
| **S7** | 「更新に失敗しました」     | D3   | `status.phase === "error"`                         |

**S4 と S5、S6 と S7 は、フロントから区別できない。** `UpdaterStatus` に欄が無い。
判定の右端に書いた「promise が未解決」は表の側で立てた条件で、**対応する値がコードに無い。**

**S0 が4つの意味を兼ねる。** 「まだ確認していない」「確認して更新が無かった」
「告知を閉じた」「失敗の知らせを閉じた」が、どれも同じ状態に落ちる。

## この表が満たすべき不変条件

1. **「準備ができました」を出してよいのは、実体が入れ替わり終えた後だけ。**
   いまは取得の完了で出しているので、S4 に居る間ずっと嘘をついている。
   (S4, E12) と (S4, E13) の危うさは、どちらもこの1つから出ている。
2. **取得を始めてから終わるまで、走る経路は1本。**
   2本走ると、同じ宛先への入替が重なる。関門を「押した時点の状態」に置く限り破れる。
3. **確認しなかったことと、確認して更新が無かったことを、同じ状態で表さない。**
   いまは E4 の失敗まで同じ S0 に落ちるので、配布先が壊れていても区別が付かない。
4. **閉じられる状態は、閉じた後に復帰の口が在ること。**
   S7 で閉じると、アプリが実体を失ったことを伝える面が二度と出ない。

## 埋まっていないセル

**全部。** `useUpdater` と `UpdaterScreen` を検証するテストは1件も無い。
`app/__tests__/rootErrorBoundary.test.tsx` は `UpdaterScreen` を丸ごと差し替えていて、
境界の振る舞いだけを見ている。

そのうえで、**書けば潰せるもの**と**いまの型では書けないもの**に分かれる。

| セル                 | いま起きること             | 固定できるか                                       |
| -------------------- | -------------------------- | -------------------------------------------------- |
| (S1, E4)             | 確認の失敗が消える         | できる                                             |
| (S1, E5)             | S1 に固定される            | 上限を渡す形に変えたうえで、できる                 |
| (S2, E6) を2回       | 取得と入替が2本走る        | できる                                             |
| (S2, E11) → 次の起動 | 同じ版の告知がもう一度出る | 永続の置き場を決めたうえで、できる                 |
| (S0, E14)            | 新しい版に気づかない       | 定期の確認を足したうえで、できる                   |
| (S4, E9)             | 画面が1文字も変わらない    | **できない。** D1 と D2 を分ける値がフロントに無い |
| (S4, E12)            | 入替の最中に再起動する     | **できない**（同上）                               |
| (S4, E15)            | プロセスが消える           | できない。実プロセスと Windows が要る              |
| (S5, E13)            | 次の起動が新しい版になる   | できない。実プロセスが要る                         |
| (S7, E13)            | 起動できなくなる           | できない。plugin の中で起きる                      |

**「できない」が5件あるのは、表がフロントの語彙で書けない状態を持っているから。**
`UpdaterStatus` を実体の段まで分けない限り、この列は埋まらない。
下の3件は分けても埋まらない —— 実プロセスを要する経路は、このリポジトリに
固定されているものが1つも無い。

## この表が決めていないこと

- 告知をどこに出すか（専用のカードのままか、通知の基盤へ載せるか）。
  基盤の語彙は失敗のためのもので、S2〜S5 の4つは失敗ではない
- 「後で」と「この版を飛ばす」を分けるか。分けるなら永続の置き場
- 確認の失敗（E4）を利用者へ出すか。出さないなら、代わりに何を見せるか
