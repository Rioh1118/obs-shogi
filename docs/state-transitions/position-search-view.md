# 状態遷移: 局面検索の画面

対象は `src/features/position-search/ui/`。**画面の側**だけを扱う。
索引と検索そのもの（Rust 側、ディスクのキャッシュ、`stale` の意味）は
[search.md](search.md) が持つ。失敗の行き先は
[failure-surfacing.md](failure-surfacing.md)。

## なぜ表にするか

この画面には「いまどの行か」を指すものが**3つ**ある——選択（`activeIndex`）、
ホバー、DOM のフォーカス。加えて結果がチャンクで届くので、
「検索中」と「結果がある」が**同時に真であるのが通常の姿**になる。

表にする前は、この3つが噛み合っていない組み合わせが4つ残っていた。
どれも「エラーも出ないのに操作が効かない/効く先が違う」形なので、
コードを読むだけでは気づけない。

## 状態

### 一覧そのもの

| 記号        | 判定条件（実際の式）                                                  | 画面                                                       |
| ----------- | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| **L-idle**  | `queryKey == null`                                                    | 「検索する局面がありません」                               |
| **L-load**  | `isLaunching \|\| isSearchingRequest(rid)` かつ `hits.length === 0`   | 「検索結果を受信中…」                                      |
| **L-strm**  | 同上 かつ `hits.length > 0`                                           | 行が出る。**押せる**（下の「不変条件4」）                  |
| **L-hits**  | `!isSearching && hits.length > 0`                                     | 行が出る                                                   |
| **L-empty** | `!isSearching && !error && hits.length === 0` かつ `queryKey != null` | 「一致する棋譜がありません」。`stale` なら増えうる旨を併記 |
| **L-err**   | `error != null`                                                       | 0件なら理由つきの箱。1件でも届いていれば**行を残して**注記 |

`queryKey` は `params.sfen ?? currentSfen ?? null`。棋譜を開いていなければ null になる。

**`stale` は上の6つと直交する。** `indexState ∈ {Restoring, Building, Updating} || session.stale`
で決まり、どの状態にも重なって出る。意味は [search.md](search.md) が持つ。

**`L-strm` が通常の姿。** `chunkSize: 300` で届くので、`isSearching` は
一覧が育っているあいだずっと真。「検索中だから触らせない」を選ぶと、
利用者から見て**ずっと触れない**になる。

### 行1つ

| 軸           | 判定条件                                          |
| ------------ | ------------------------------------------------- |
| **selected** | `index === activeIndex`（`hits > 0` なら必ず1つ） |
| **hover**    | ポインタが乗っている                              |
| **focus**    | `document.activeElement === その行`               |

**focus は selected に従属する。** 独立した軸ではない（不変条件1）。
`tabIndex` は選択している行だけが `0`、他は `-1`。

## 事象

| 記号         | 発生源                      | 備考                                    |
| ------------ | --------------------------- | --------------------------------------- |
| **chunk**    | Rust（検索結果の分割到着）  | 並べ直す。選択は `hitKey` で追う        |
| **done**     | Rust（検索完了）            |                                         |
| **fail**     | Rust / `invoke` の失敗      |                                         |
| **requery**  | `queryKey` が変わる         | 前の rid を `cancelSearch` して投げ直す |
| **close**    | 利用者（Escape / 外を押す） | `cancelSearch` して全部 reset           |
| **click**    | 利用者                      | 選択（開かない）                        |
| **dblclick** | 利用者                      | 開いて閉じる                            |
| **arrow**    | 利用者（↑ / ↓ / j / k）     | 選択が動く。焦点も追う                  |
| **enter**    | 利用者                      | 開いて閉じる                            |
| **offscr**   | 仮想リスト（行が外れる）    | 選択している行が焦点を持ったまま消える  |

**`offscr` を事象として立てているのは、これが「利用者の操作でない状態変化」だから。**
書き忘れると焦点が `<body>` へ落ち、`Modal` の引き戻しが**選択していない行**を掴む。

### 行の見た目（selected × hover × focus）

|                          | 面                   | 帯（左 2px） | outline |
| ------------------------ | -------------------- | ------------ | ------- |
| 素                       | 無し                 | 無し         | 無し    |
| hover                    | `white .04`          | 無し         | 無し    |
| selected                 | `secondary-dark .18` | あり         | 無し    |
| selected + hover         | `secondary-dark .24` | あり         | 無し    |
| selected + focus         | `secondary-dark .18` | あり         | あり    |
| selected + hover + focus | `secondary-dark .24` | あり         | あり    |

**`hover` は必ず「足す」側。** CSS の詳細度で `:hover` (0,2,0) は
`--active` (0,1,0) に勝つので、`:not(.pos-hit--active)` で除外しないと
**選択している行にポインタを乗せた瞬間に選択の面が消える**。

**素 + focus は起こらない。** 焦点は選択に従属するため（不変条件1）。

## 不変条件

1. **「いまどの行か」を指すものは1つ。** 選択・ホバー・フォーカスが同時に立っても、
   「次に Enter を押したら開く行」は1行に定まる。
   実装上は**焦点を選択に追従させる**ことで満たしている
2. **ホバーは、より強い状態を消さない。** ホバーは常に足す側で、選択の表現を置き換えない
3. **行の描画は自分のスロットの外に出ない。** 文字サイズ・余白・行数をどう変えても隣を覆わない。
   行の高さを数値で決め打たず実測に任せることで、ずれる状態自体を作らない
4. **押せないと見えるものは、キーボードからも動かない。** 逆も同じ

## 埋まっていないセル（テスト項目）

`src/features/position-search/ui/__tests__/PositionSearchHitList.test.tsx` が
踏んでいるのは上の `✓` と、行の高さ・`listbox`/`option` の親子・
`tabIndex` の配り方・焦点の追従。**残りは1つも見ていない。**

| 何を見ていないか                                         | どうなるか（未確認）                                                                  |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `arrow` で選択と焦点が一緒に動くこと                     | キーの受け口は `PositionSearchModal` 側なので、一覧だけを描くテストでは踏めない       |
| `offscr`（選択した行が画面外へ出て消える）               | 焦点が listbox へ預けられるはず。happy-dom はレイアウトを持たないので仮想化が動かない |
| `L-strm` の最中に `requery`                              | 前の rid の `cancelSearch` と、届き続けるチャンクが競合する                           |
| `close` の直後に chunk が届く                            | `requestId` を null にしてから届く経路                                                |
| `enter` が「焦点のある行」でなく「選択した行」を開くこと | 両者が一致するようにしたので**同じはず**だが、突き合わせるテストは無い                |

**`offscr` と `requery` は実機で確かめていない。** 仮想化とスクロールを動かせる
土台（レイアウトを持つ DOM）をこのリポジトリはまだ持っていない。

## この表が拾ったもの

- **焦点と選択が別の行を指す**こと。行3に焦点を置いて↓を押すと、リングは3・
  選択の面は4を指し、Enter で開くのは4、読み上げは3を読んでいた
- **開いた直後は矢印も Enter も死んでいる**こと。このモーダルで焦点を取れるのは
  ヒットの行だけなので、行が0件のあいだ `Modal` の引き戻しが器そのものを掴む。
  その器はキーの受け口より**上**にあるので、イベントが受け口まで下りてこない
- **検索中は矢印だけが効く**こと。行は `disabled` なのに矢印は `isSearching` を
  見ていなかった（不変条件4が破れていた）
- **状態行と一覧が違うことを言う**こと。`L-idle` で状態行は「待機中」、
  一覧は「一致する棋譜がありません」と出していた
