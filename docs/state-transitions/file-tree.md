# 状態遷移表: file-tree（L1）

対象: `src/entities/file-tree/model/provider.tsx` と `src/widgets/file-tree/ui/FileTree.tsx`。

上位は [app.md](app.md)。棋譜そのものの読み込みは `game.md`（未作成）が持つ。

ツリーとファイル操作に関わるものだけ。選択・展開・メニューは失敗経路に関わらないので省く。

| 記号   | 状態               | 判定                                                            |

### 注

※1 ツリーが残っているかどうかで見せ方が分かれる。残っているならモーダル、まだ無ければその場。

**出すボタンは2つの軸で決まる。混ぜない。**

| ボタン                   | 何が決めるか     | 条件                                                     |
| ------------------------ | ---------------- | -------------------------------------------------------- |
| 再読み込み               | **段**           | `fsErrorTier` が `warning` のとき                        |
| ワークスペースを選び直す | **ツリーの有無** | ツリーが1本も無いとき（`FileTree` が `fallback` を渡す） |

読み直しても直らない失敗に再読み込みを出すと、押しても何も起きないので利用者は押し続ける。
逆に、逃げ道を段で切ると**ルートが消えたとき**（`not_found` は `warning`）だけ行き止まりになる。
読み直す先が消えているので、再読み込みは何度押しても同じ失敗に戻る。
→ `FileTreeErrorNotice`

読み直しを始めると reducer が `error` を落とすので、表示側は引き金になった失敗を
自分で持つ。持たないと押した瞬間に通知が消える。
→ [failure-surfacing.md](failure-surfacing.md) F-3

※2 失敗をどこへ出すかは、**その操作を起こした場所が失敗を出す場所を持っているか**で
決まる。名前がその行き先を表す。`provider.tsx` に5経路ある。

| 経路                    | 使う操作                                 | 何をするか                                                              |
| ----------------------- | ---------------------------------------- | ----------------------------------------------------------------------- |
| `failWithNotice`        | 移動（ドラッグ&ドロップ）                | 衝突は S4 へ、それ以外は `state.error` に積む（S3）                     |
| `failToCaller`          | 作成・取り込み（モーダルの中）           | 衝突は S4 へ、それ以外は呼び出し元へ返す。フォームが自分の中に出す      |
| `failToNameInput`       | リネーム・フォルダ作成（インライン編集） | 衝突は S4 へ、`invalid_name_*` は呼び出し元へ返す、残りは `state.error` |
| `pushError` の直呼び    | 削除、衝突の解決を中断するとき           | 常に `state.error` に積む（S3）                                         |
| `loadFileTree` の直積み | ツリーの読み直し                         | `state.error` に積む。**操作の戻り値には載せない**                      |

**`state.error` に積むと reducer が編集行とメニューを畳む。** 名前の訂正で直る失敗を
そこへ流すと、直すための入力欄が一緒に消える。だから入力欄を持つ経路は
`invalid_name_*` を返す側に回す。→ ADR-0004 の F-14

**読み直しの失敗は操作の失敗ではない。** 変更は成功しているので、`Err` として返すと
「作成に失敗した」という嘘が同じ画面に2つ出る。`loadFileTree` が積む1箇所だけに任せる。

**S4 の間は積まない。** `conflict` が立っているとき reducer は `error` を落とす。
衝突を解決しようとして起きた失敗は `FileConflictDialog` の中で伝える
（モーダルが2枚重なるのを避けるため）。`(S4, E9)` のセルはこれ。

※3 S3 からは読み直し（`refreshTree`）で戻る。ルートそのものが読めない場合は
読み直しても同じ場所を見にいくだけなので、ワークスペースを選び直す導線を並べる

※4 S3（ツリーあり）と S5 の出口はモーダルで、オーバーレイが全面を覆いフォーカスも
閉じ込める。**閉じるまでツリーの操作は起こせない。** 「実行できる」ではない

## この表が満たすべき不変条件

1. **ツリーが表示されているなら、それはディスクの現在の状態と一致している。**
   ファイル監視が無いので、外部からの変更に対してはこれを守れていない
2. **どの失敗からも、利用者の操作で S2 に戻れる。**
3. **`error` と `kifuError` は独立。** 棋譜が開けなくてもツリーは操作できる（S5 の行）

- **外部でのファイル変更**（機能自体が無い）
