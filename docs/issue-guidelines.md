# Issue の運用

**Issue は「やると決まった作業」の札。** 中身の正本はリポジトリのファイルに置き、Issue はそこを指す。

Issue は git の外にあるので、レビューも走査も届かない。詳細を書くと、コードが動いた時点から古くなる。
2026-10-31 に数えた open 225件では、183件が本文でソースのパスを指し、そのうち54件が
消えたパスか存在しない行を指していた（別リポジトリのパスも少数含む）。本文の中央値は1,322字。
#196 は本文の書き換え中に結論が変わり、#110 は本文の丸ごと差し替えが要った。

## 書くこと／書かないこと

本文は**800字以内**。超えるなら詳細が混ざっている。

| 書くこと                                       | 書かないこと（置き場は次の節）                |
| ---------------------------------------------- | --------------------------------------------- |
| 何が起きているか、または何ができるようになるか | 直し方の設計、案の比較                        |
| 利用者から見た結果                             | `ファイル:行`、コード片、関数名の列挙         |
| 完了条件（観測できる形で）                     | 実測の表、調査の経過、レビューの所見の全文    |
| 正本へのリンク（仕様の節、AC の ID）           | 仕様の写し                                    |
| 先に終わる Issue（`Blocked by #N`）            | 着手順の説明。順番は親 Issue のチェックリスト |
| 出どころ（レビュー報告、仕様、発見した PR）    | 未決の論点、相談                              |

- **指すのは振る舞いと型の名前まで。** コードの場所は着手する人が今のコードで探す
- **タイトルは症状か、できるようになること。** 60字以内。対策を主語にしない。「〜すべき」を使わない
- **1 Issue 1 作業。** 別の問題は別の Issue にする
- **事実と推測を分ける。** 推測は「推測」と書く
- **起票の前に再現を確かめる。** コードを読んだだけの見立ては Issue にしない

### バグの必須項目

再現手順、期待結果、実際の結果、再現の頻度、環境。報告者が原因を知る必要は無い。
再現手順が本文にあるので、バグは正本のリンクが無くてもよい。

### 本文を直してよいとき

**本文を育てない。** 中身が動くなら正本を直す。本文を直すのは、正本へのリンク、完了条件、ブロックが
変わったときだけ。経過はコメントに1行で書く。

## 置き場

| もの                                | 置き場                                                           |
| ----------------------------------- | ---------------------------------------------------------------- |
| やると決まった作業                  | **Issue**                                                        |
| 仕様、受入条件                      | `docs/spec/`                                                     |
| いま足りていないことの詳細          | `docs/spec/screens/` の「いま満たしていないこと」                |
| 状態とイベント                      | `docs/state-transitions/`                                        |
| 決めていないこと                    | 仕様の「決まっていないこと」から `docs/OPEN-QUESTIONS.md` へ     |
| いつかやる（6週間以内に着手しない） | `docs/IDEAS.md`                                                  |
| 決めたこと、直し方の設計判断        | `docs/decisions/`                                                |
| 仮定                                | `docs/PREMISES.md`                                               |
| 他の実装の事実                      | `research/`                                                      |
| レビューの所見と実測                | `.claude/reviews/`                                               |
| 実装の中で決めた細部                | PR の本文                                                        |
| 質問、相談、まだ作業でない話        | [Discussions](https://github.com/Rioh1118/obs-shogi/discussions) |

Issue を立ててよい条件は `docs/OPERATING-MODEL.md` §2（6週間以内に着手するものだけ）。

## ラベル

実在するラベルだけを使う。**増やす前にこの表を直す。** 付けるのは次の3軸で、他は新規に使わない。

| 軸     | 値                                                                                                                   | 必須            |
| ------ | -------------------------------------------------------------------------------------------------------------------- | --------------- |
| 種別   | `bug` / `enhancement` / `documentation`。親 Issue は `epic`                                                          | 1つ             |
| エリア | `area:engine` / `area:analysis` / `area:book` / `area:kifu` / `area:search` / `area:game` / `area:ui` / `area:build` | 1つ以上         |
| 優先度 | `priority:high` / `priority:medium` / `priority:low`（意味はラベルの説明）                                           | 受理した時に1つ |

## ライフサイクル

状態のためのラベルは足さない。**優先度が付いているかで分かる。**

| 状態     | 判定                                     | 次                                                           |
| -------- | ---------------------------------------- | ------------------------------------------------------------ |
| 受付     | open で `priority:*` が無い              | `/issue-triage` で受理か閉じるかを決める                     |
| 受理     | open で `priority:*` がある              | やると決まった。そのまま作業できる                           |
| 情報待ち | 受付のまま、報告者への質問が最新コメント | 7日返事が無ければ閉じる候補                                  |
| 着手     | 自分が assignee                          | PR の本文に `Closes #N`                                      |
| 完了     | closed                                   | 正本（仕様の「いま満たしていないこと」など）も同じ PR で直す |

`/spec-to-issues` が立てる Issue は人の承認を通っているので、最初から受理の状態にする。

**受理のまま60日動かないものは、`/issue-triage` の一覧に必ず載せる。** 自動では閉じない。
起点は最後の作業の動き（紐づいた PR、コミット、経過のコメント）で、本文やラベルの編集は数えない。
閉じるなら「閉じる基準」のどれかに当てる。当たらなければ残し、着手するかを人が決める。

## 親 Issue

依存のある作業が2件以上あるときに、順番と進み具合を見せるために立てる（型は `.github/ISSUE_TEMPLATE/tracking.yml`）。

**議論の場にしない。** 中身は正本へのリンクとチェックリストだけ。論点は子の Issue か
`docs/OPEN-QUESTIONS.md` へ。子の詳細を写さない。親は子が全部閉じたら閉じる。

## 閉じる基準

閉じるときは**理由と行き先をコメントに1行**書く。

| 理由         | 条件                              | `--reason`    | 行き先                 |
| ------------ | --------------------------------- | ------------- | ---------------------- |
| 完了         | 完了条件を満たす PR が入った      | `completed`   | PR                     |
| 実装済み     | 現物で確かめた                    | `completed`   | コミットか PR          |
| 仕様へ移した | 未決、相談、詳細の置き場の誤り    | `not planned` | 移した先のファイル     |
| いつかやる   | 6週間以内に着手しない             | `not planned` | `docs/IDEAS.md` の行   |
| 範囲外       | `docs/PREMISES.md` の軸に乗らない | `not planned` | 理由。ADR があれば番号 |
| 重複         | 同じ作業の Issue がある           | `not planned` | 残す Issue の番号      |
| 再現しない   | 手順で再現できず、情報も来ない    | `not planned` | 試した環境             |

## 関係する skill

- `/spec-to-issues` — 仕様から起票する
- `/issue-triage` — 既存の Issue を整理する
- `/write-issue` — 作業の途中で見つけたものを1件起票する
