# 画面仕様: 局面検索

対象: `src/features/position-search/` `src/entities/search/` `src-tauri/src/search/`
`modal=position-search`

状態遷移: 画面の側は [`position-search-view.md`](../../state-transitions/position-search-view.md)、
索引と検索そのものは [`search.md`](../../state-transitions/search.md)。
**この仕様書に状態の表を置かない。**

## 目的

**同じ局面を含む棋譜を、ワークスペース全体から探して開く。**
これが `docs/PREMISES.md` P-002 の言う「保守されたクロスプラットフォームの
棋譜ライブラリ層」の中心にある機能。

## 出入口

| 入口                                               | 出口                                                     |
| -------------------------------------------------- | -------------------------------------------------------- |
| 解析ペインの 🔍（現在局面を検索）                  | Enter／ダブルクリック → その棋譜のその局面を開いて閉じる |
| 課題局面の一覧の「検索」または `s`（`sfen=` 付き） | Esc・オーバーレイ → `returnTo` があれば一覧へ戻る        |

確定して閉じるときは `closeModal({ skipReturn: true })`。
**確定操作では `returnTo` を辿らない。**

## 検索対象の局面

`queryKey = params.sfen ?? currentSfen ?? null`

- `sfen=` があればその局面（課題局面から来た場合）
- 無ければ盤の現在局面
- どちらも無ければ「検索する局面がありません」

**`queryKey` が変わると検索し直す。** 前の検索は `cancelSearch` で取り下げる。
取り下げは `requestId` を `ref` で追いかけて行う（`setRequestId` の反映を待たないため）。

## 画面構成

```
┌ 局面検索 ───────────────────────────────────────────────────┐
│ 12件  検索中…  [結果が古い可能性]                            │
├──────────────────────────────┬──────────────────────────────┤
│ ヒット一覧（仮想スクロール） │ 検索対象の局面 / 現在の局面   │
│  ▸ 45角戦法.kif   32手目     │  ┌──────────────┐            │
│    棋譜A.kif      28手目     │  │  盤プレビュー │            │
│    …                         │  └──────────────┘            │
│                              │  この先の手（5手）           │
│                              │  行き先: <パス>              │
└──────────────────────────────┴──────────────────────────────┘
```

- 右上の見出しは、`sfen=` で来たときだけ「検索対象の局面」。通常は「現在の局面」
- `PositionSearchContinuation` は、選んでいるヒットの**そこから先5手**を出す。
  読みに行くのは**選択が止まってから**（150ms）。矢印で駆け抜けた行は読まない。
  読み込み済みの棋譜なら待たずに出る
- **選んでいない棋譜も読む。** 選択が止まってから 300ms 経つと、
  直前に動いた向きの**次の1行**の棋譜を先に読んでおく（中身は出さない）。
  矢印で降りている間の待ちはこれで消える。抱えておく上限は件数でなく
  **量**（`MAX_CACHED_BYTES`）で、超えたら古い順に落ちる
- `PositionSearchDestinationCard` は、いま開いている棋譜と行き先を並べる

### 並び順

`useOrderedPositionHits` が、**いま開いている棋譜のヒットを先頭に寄せる**。
残りは Rust から届いた順。

寄せるかどうかは、**そのヒットが届いた時点で索引がパスを返したか**で決まる。
届いた時点で引けなかったヒットは、後から索引にパスが入っても寄せ直さない。

## 操作と結果

| 操作               | 結果                                     |
| ------------------ | ---------------------------------------- |
| `↓` / `j`          | 次のヒットへ                             |
| `↑` / `k`          | 前のヒットへ                             |
| `Enter`            | そのヒットを開く（**検索中でも押せる**） |
| 行をクリック       | 選択                                     |
| 行をダブルクリック | 開く                                     |
| `Esc`              | 閉じる（`Modal` が受ける）               |

**検索中でも開ける。** 結果は `chunkSize: 300` のチャンクで届くので
`isSearching` は一覧が育っている間ずっと真。ここで弾くと
事実上「全件届くまで何も押せない」になる。届いたヒットは行き先を決めるのに足りる。

焦点は選択している行が持つ。この節自体は焦点を取らない。

### 開く経路

`usePositionHitNavigation` が持つ。

1. 同じファイルが既に開いていれば、その場で `applyCursor`
2. 別のファイルなら `selectNodeByAbsPath` でツリーを切り替え、
   読み込みが終わって `view.player` が立ってから `applyCursor`

**移動を始められたときだけ閉じる。** `startNavigationToHit` が返すのは
`NavigationOutcome` の3値で、`"started"` 以外はモーダルを開いたまま断りを出す。
ツリーにその棋譜が無ければ `"not-in-tree"`、ツリー自体をまだ読めていなければ
`"tree-unavailable"`。

**下の表が3行に割れている根拠は `RefusalReason`**（`PositionSearchModal`）で、
`NavigationOutcome` の失敗2値に `"no-path"` を足したもの。あちらは
`startNavigationToHit` を呼ぶ前——索引が行き先のパスを返さなかった回。

**返すのは「始められたか」で、「開けたか」ではない**——ツリーに在って盤に
載せられない棋譜（#434）は `"started"` が返るので、いまも黙って閉じる。**着いた局面が要求どおりかも
見ていない**（`reachedCursor` を通していない → #443）。
索引に在る棋譜がツリーに無いのは**正常運転で起こる**。ツリーは即座に読み直されるのに、
索引の更新は watcher と静穏 800ms のデバウンス越しに来るので、遅れる窓が常にある。
走査そのものが失敗した回と watcher の起動に失敗した回は、削除が一度も取り込まれない
（→ [`search.md`](../../state-transitions/search.md) の「走査が失敗しても `Y` に上がる」）。

## 失敗の見せ方

| 失敗                                       | どこに出るか                                                                                      |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 検索の起動が落ちた                         | 状況バーに「エラー」＋理由                                                                        |
| 検索の途中で落ちた                         | 同上。**届いているヒットは残す**                                                                  |
| ヒットの棋譜がツリーに無い                 | 一覧の上に `InlineNotice`（`danger`）。**閉じない**（F-32）                                       |
| ヒットの行き先のパスを索引が返さない       | 同じ場所に `InlineNotice`（`danger`）。**閉じない**（F-32）                                       |
| ツリーをまだ読み込めていない               | 同じ場所に `InlineNotice`（`warning`）。読み込めれば同じ操作で開ける（F-32）                      |
| 索引が作成中・更新中                       | 状況バーに「索引の更新待ち」／0件なら「増える場合があります」                                     |
| 索引を作れなかった                         | 「索引を作れませんでした」／0件なら理由と次にすることを言う                                       |
| 走査が失敗（索引は残る）                   | 「索引を更新できていません」／0件なら「最近の追加は反映されていません」                           |
| 読めなかった場所があった                   | 「読めなかった場所があります」／0件なら「そこの棋譜は検索に出ないか、最新でない可能性があります」 |
| 索引に入れられなかった棋譜があった         | 「一部を索引に入れられていません」／0件なら「そこには当たりません」                               |
| 読めない場所と、入れられなかった棋譜の両方 | 「読めない場所と、入れられなかった棋譜があります」                                                |
| 更新できず、入れられなかった棋譜もある     | 「更新できず、入れられなかった棋譜もあります」                                                    |
| 索引がまだ無い                             | 「索引がありません」／0件なら「まだ作られていません」                                             |
| 続きの棋譜が読めない・解析できない         | **どこにも出ない。**「（続きなし）」になり、終局と区別が付かない → #421                           |
| 続きが要求した局面に着けない               | **どこにも出ない。** 別の線の続きが印無しで出る（`reachedCursor` を通していない → #443）          |

→ [`failure-surfacing.md`](../../state-transitions/failure-surfacing.md) F-32

### 状況バーの進み具合

索引の具合とは別に、**この検索がどこまで進んだか**を1語で出す。

| いつ               | 文言    |
| ------------------ | ------- |
| 起動待ちか受信中   | 検索中… |
| 起動か途中で落ちた | エラー  |
| 最後まで受け取った | 完了    |
| まだ投げていない   | 待機中  |

### 0件のときに出る文言

**実文で載せる。** 要約で書くと、画面を触った人が仕様書を開かないまま
文言を変えられる（`src/__tests__/screenSpecCoverage.test.ts` が突き合わせる）。

| 具合                              | 文言                                                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `ok`（索引は健全）                | 一致する棋譜がありません                                                                                           |
| `ok`＋検索中に索引が動いた        | 一致する棋譜がありません（検索中に索引が動いたので、取り直すと変わる場合があります）                               |
| `building`                        | 一致する棋譜がありません（索引の更新中なので、増える場合があります）                                               |
| `notStarted`                      | 一致する棋譜がありません（索引がまだ作られていません）                                                             |
| `buildFailed`                     | 索引を作れなかったので検索できません（ワークスペースを読めるか確かめてください）                                   |
| `notRefreshed`                    | 一致する棋譜がありません（索引を更新できていないので、最近の追加は反映されていません）                             |
| `partiallyIndexed`                | 一致する棋譜がありません（索引に入れられなかった棋譜があるので、そこには当たりません）                             |
| `partiallyUnreadable`             | 一致する棋譜がありません（読み取れなかった場所があるので、そこの棋譜は検索に出ないか、最新でない可能性があります） |
| `partiallyUnreadableAndIndexed`   | 一致する棋譜がありません（読めなかった場所と、索引に入れられなかった棋譜の両方があります）                         |
| `notRefreshedAndPartiallyIndexed` | 一致する棋譜がありません（索引を更新できておらず、入れられなかった棋譜もあります）                                 |

**0件以外にも一覧が出す文言が2つある。** どちらも `indexHealth` の分岐ではないので、
`screenSpecCoverage` の走査には掛からない（入れ子三項と JSX の地の文）。

| いつ                         | 文言                                                 |
| ---------------------------- | ---------------------------------------------------- |
| 受信中で、まだ0件            | 検索結果を受信中…                                    |
| 途中で失敗し、届いた分は残す | 途中で失敗したので、これで全部とは限りません: {理由} |

**0件の理由は具合ごとに言い分ける。** 分岐を持つのは `indexHealth`
（`entities/search/lib/indexHealth.ts`）1つで、画面はそれを読むだけ
——画面ごとに旗を並べ直すと、見る順が割れる。

**残っている欠陥は `stale` のほう。** `query_service` が見るのは
`state != Ready` だけなので、Rust から来る `SearchBeginPayload.stale` は
`indexHealth` の値を区別しない。区別を作っているのは `EVT_INDEX_STATE` の段と旗で、
**検索セッション側の `stale` は依然として4状態を畳んでいる**。→ #350

## いま満たしていないこと

- **索引が壊れていることは、いまも何も出ない**（旗が立つのは走査の失敗と
  読めなかった場所だけ。ビット化けした索引は「正常」に見える）→ #350（エピック）
- **「続き5手」が読めなかった理由が消える。** 権限拒否・ファイル消失・壊れた KIF が
  どれも「（続きなし）」になり、本当に終局まで指された棋譜と区別が付かない → #421
- **「続き5手」が要求した局面に着けたかを見ていない。** 索引を作った後に棋譜が
  編集されていると、別の線の続きが**正しい顔をして**出る → #443
- **セッションの `stale` が4状態を畳んでいる**（上記）
- **走査の失敗から自力で復帰する導線が無い。** ワークスペースを開き直すしかなく、
  次に `fs-event` が来るまで再走査もされない
- **文字コードの判定が3層に散っていて、検索に出るのに開けない棋譜がある** → #325
- **空の変化の `forkIndex` が Rust と TS で食い違う** → #199
- **`book` と `search` で SFEN の受理集合が2つある** → #236
- **局面検索・局面ナビの非同期と effect にまとまった問題がある** → #288
- **検索条件が「完全一致の局面」1つだけ。** 手番無視・左右反転・部分一致・
  手数の範囲・メタデータでの絞り込みは**無い**

## これからの要件

`docs/PREMISES.md` P-001 は「横断検索そのものは差別化にならない」と判定している
（棋譜エクスプローラーが2022年に完全一致・部分一致・左右反転・手番無視・
手数制限・メタデータフィルタ・タグを実装済み）。したがって

- **条件を増やすことは目的ではない。** 増やすなら「保守された唯一の
  クロスプラットフォーム実装」という軸（P-002）に効く順で選ぶ
- 索引の状態を利用者に伝えること（#350）のほうが先。**条件を増やす前にこちら**
