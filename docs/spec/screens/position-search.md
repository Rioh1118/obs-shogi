# 画面仕様: 局面検索

対象: `src/features/position-search/` `src/entities/search/` `src-tauri/src/search/`
`modal=position-search`

状態遷移: 画面の側は [`position-search-view.md`](../../state-transitions/position-search-view.md)、
索引と検索そのものは [`search.md`](../../state-transitions/search.md)。
**この仕様書に状態の表を置かない。**

## 目的

**同じ局面を含む棋譜を、ワークスペース全体から探して開く。**
これが `docs/PREMISES.md` P-002 の言う「保守されたクロスプラットフォームの
棋譜ライブラリ層」の中心にある機能。

## 出入口

| 入口                                               | 出口                                                     |
| -------------------------------------------------- | -------------------------------------------------------- |
| 解析ペインの 🔍（現在局面を検索）                  | Enter／ダブルクリック → その棋譜のその局面を開いて閉じる |
| 課題局面の一覧の「検索」または `s`（`sfen=` 付き） | Esc・オーバーレイ → `returnTo` があれば一覧へ戻る        |

確定して閉じるときは `closeModal({ skipReturn: true })`。
**確定操作では `returnTo` を辿らない。**

## 検索対象の局面

`queryKey = params.sfen ?? currentSfen ?? null`

- `sfen=` があればその局面（課題局面から来た場合）
- 無ければ盤の現在局面
- どちらも無ければ「検索する局面がありません」

**`queryKey` が変わると検索し直す。** 前の検索は `cancelSearch` で取り下げる。
取り下げは `requestId` を `ref` で追いかけて行う（`setRequestId` の反映を待たないため）。

## 画面構成

```
┌ 局面検索 ───────────────────────────────────────────────────┐
│ 12件  検索中…  [結果が古い可能性]                            │
├──────────────────────────────┬──────────────────────────────┤
│ ヒット一覧（仮想スクロール） │ 検索対象の局面 / 現在の局面   │
│  ▸ 45角戦法.kif   32手目     │  ┌──────────────┐            │
│    棋譜A.kif      28手目     │  │  盤プレビュー │            │
│    …                         │  └──────────────┘            │
│                              │  この先の手（5手）           │
│                              │  行き先: <パス>              │
└──────────────────────────────┴──────────────────────────────┘
```

- 右上の見出しは、`sfen=` で来たときだけ「検索対象の局面」。通常は「現在の局面」
- `PositionSearchContinuation` は、選んでいるヒットの**そこから先5手**を出す
- `PositionSearchDestinationCard` は、いま開いている棋譜と行き先を並べる

### 並び順

`orderPositionHits` が、**いま開いている棋譜のヒットを先頭に寄せる**。
残りは Rust から届いた順。

## 操作と結果

| 操作               | 結果                                     |
| ------------------ | ---------------------------------------- |
| `↓` / `j`          | 次のヒットへ                             |
| `↑` / `k`          | 前のヒットへ                             |
| `Enter`            | そのヒットを開く（**検索中でも押せる**） |
| 行をクリック       | 選択                                     |
| 行をダブルクリック | 開く                                     |
| `Esc`              | 閉じる（`Modal` が受ける）               |

**検索中でも開ける。** 結果は `chunkSize: 300` のチャンクで届くので
`isSearching` は一覧が育っている間ずっと真。ここで弾くと
事実上「全件届くまで何も押せない」になる。届いたヒットは行き先を決めるのに足りる。

焦点は選択している行が持つ。この節自体は焦点を取らない。

### 開く経路

`usePositionHitNavigation` が持つ。

1. 同じファイルが既に開いていれば、その場で `applyCursor`
2. 別のファイルなら `selectNodeByAbsPath` でツリーを切り替え、
   読み込みが終わって `view.player` が立ってから `applyCursor`

## 失敗の見せ方

| 失敗                     | どこに出るか                                                                |
| ------------------------ | --------------------------------------------------------------------------- |
| 検索の起動が落ちた       | 状況バーに「エラー」＋理由                                                  |
| 検索の途中で落ちた       | 同上。**届いているヒットは残す**                                            |
| 索引が作成中・更新中     | 状況バーに「索引の更新待ち」／0件なら「増える場合があります」               |
| 索引を作れなかった       | 「索引を作れませんでした」／0件なら理由と次にすることを言う                 |
| 走査が失敗（索引は残る） | 「索引を更新できていません」／0件なら「最近の追加は反映されていません」     |
| 読めなかった場所があった | 「読めなかった場所があります」／0件なら「索引に入っていない棋譜があります」 |
| 索引がまだ無い           | 「索引がありません」／0件なら「まだ作られていません」                       |

**0件の理由は具合ごとに言い分ける。** 分岐を持つのは `indexHealth`
（`entities/search/lib/indexHealth.ts`）1つで、画面はそれを読むだけ
——画面ごとに旗を並べ直すと、見る順が割れる。

**残っている欠陥は `stale` のほう。** `query_service` が見るのは
`state != Ready` だけなので、Rust から来る `SearchBeginPayload.stale` は
上の6つを区別しない。区別を作っているのは `EVT_INDEX_STATE` の段と旗で、
**検索セッション側の `stale` は依然として4状態を畳んでいる**。→ #350

## いま満たしていないこと

- **索引が壊れていることは、いまも何も出ない**（旗が立つのは走査の失敗と
  読めなかった場所だけ。ビット化けした索引は「正常」に見える）→ #350（エピック）
- **セッションの `stale` が4状態を畳んでいる**（上記）
- **走査の失敗から自力で復帰する導線が無い。** ワークスペースを開き直すしかなく、
  次に `fs-event` が来るまで再走査もされない
- **文字コードの判定が3層に散っていて、検索に出るのに開けない棋譜がある** → #325
- **空の変化の `forkIndex` が Rust と TS で食い違う** → #199
- **`book` と `search` で SFEN の受理集合が2つある** → #236
- **局面検索・局面ナビの非同期と effect にまとまった問題がある** → #288
- **検索条件が「完全一致の局面」1つだけ。** 手番無視・左右反転・部分一致・
  手数の範囲・メタデータでの絞り込みは**無い**

## これからの要件

`docs/PREMISES.md` P-001 は「横断検索そのものは差別化にならない」と判定している
（棋譜エクスプローラーが2022年に完全一致・部分一致・左右反転・手番無視・
手数制限・メタデータフィルタ・タグを実装済み）。したがって

- **条件を増やすことは目的ではない。** 増やすなら「保守された唯一の
  クロスプラットフォーム実装」という軸（P-002）に効く順で選ぶ
- 索引の状態を利用者に伝えること（#350）のほうが先。**条件を増やす前にこちら**
