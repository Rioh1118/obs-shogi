# ADR-0010: ドックをタブの器にし、置けるものを「ビュー / 表示モード / ウィジェット」で分ける

- 状態: 採用
- 日付: 2026-09-13

## 背景

ドックには解析ペインが1枚だけ直に置かれている（`src/pages/AppLayout.tsx`）。
入れ替える仕組みが無いので、**面を1つ足すたびに `AppLayout` を書き換えることになる。**

そのため置き場が決まらないまま止まっている面が4つある。

- #95 定跡の中身を見る画面 ／ #96 現局面が定跡内かを出す
- 評価値の推移
- 対局の進行（#284）

`docs/spec/screens/app-layout.md` と `docs/spec/features/book.md` は、どちらも
「サイドバーの2本目にするか、ドックのタブにするか」で止まっていた。

同時に、解析ペインそのものの見せ方にも決めが要る状態だった。候補手の並べ方に
3つの案（行 / 表 / 一覧＋詳細）が出て、**どれも捨てたくない**という結論になった。
これを「3つの面」として持つのか「1つの面の3つの見せ方」として持つのかが決まらないと、
タブの一覧に何が並ぶのかも決まらない。

## 決定

### 1. ドックはタブの器にする。サイドバーの2本目にしない

これから増える面は**どれも「いまの局面」に従属する**（定跡・評価値推移・対局・
エンジンログ）。局面に従属しないもの（ファイルツリー）だけがサイドバーに居ればいい。

**解析タブは一覧から外せない。** 全部外せると「空のドック」という状態が生まれ、
そこに出す案内を設計することになる。

### 2. 置けるものを3語で分ける

| 語               | 定義                                                                        | 選ぶ基準                   |
| ---------------- | --------------------------------------------------------------------------- | -------------------------- |
| **ビュー**       | タブになれるもの。**何を出すかで区別する**。自分の操作列と URL の綴りを持つ | 2つを同時に開きたいか      |
| **表示モード**   | 1つのビューの中の並べ方。**出すデータは同じ**。状態は共有する               | 同じデータの別の並べ方か   |
| **ウィジェット** | ビューの中の部品。**単体では置き場を持たない**。出す・出さないだけ選べる    | それ単体でタブになりうるか |

判定に迷ったときの問いは **「2つを同時に開きたいか」**。
同時に開きたいならビュー、片方でいいなら表示モード。

これにより、候補手の3案は**表示モード**になる（ビューにしない）。

### 3. 状態の置き場を分ける

| 持つもの                           | 置き場                                        |
| ---------------------------------- | --------------------------------------------- |
| 選択中のタブ                       | **URL**（`modal` / `tab` / `pov` と同じ）     |
| 表示モード・タブの構成・脚注の項目 | **`AppConfig`**（設定の置き場を2つにしない）  |
| 解析の候補とキャッシュ             | **`entities/analysis`**（ビューに持たせない） |

### 4. 設定は4枚目のタブ「表示」を持つ

原則は **「その場で変わるものはその場に、恒久的な構成は設定に」**。
表示モードは両方に出る —— その場（タブの操作列）で切り替えられて、
選んだ結果が設定の既定として残る。

**エンジンログは既定でタブ一覧に出さない。** 通常の利用では要らない。

**評価値バーは既定で出さないが、実装は残す。** 設定から出せる形にする。

## 理由

### ドックを選んだ理由

サイドバーは「いま何を開くか」を選ぶ面で、ツリーがその役を持っている。
局面に従属する面をそこへ入れると、**選択と観察が同じ列に混ざる。**
ドックは既に「いまの局面について何か言う場所」なので、増える面はここに属する。

### ビューではなく表示モードにした理由

3案は同じデータを同じ操作で見せていて、違うのは並べ方だけ。
ビューにすると **今後1つ列を足すたびに3回設計することになる** し、
タブ一覧がほとんど同じ名前で埋まる。

逆に「評価値推移」は出すデータが違う（局面ごとの候補ではなく棋譜全体の系列）ので、
これはビュー。

### 選択中のタブを URL に置き、表示モードを置かない理由

タブは**どこを見ているか**なので、リロードで戻るべきで、人に渡す意味がある。
表示モードは**好み**なので、局面を人に見せるための URL に混ざらないほうがいい。

### タブの構成を `AppConfig` に置く理由

設定の置き場を2つにしない。`last_preset_id` という UI 寄りの値を
既に入れた前例がある。払うコストは Rust 側 `config.rs` と serde の既定値で、
**古い設定ファイルが読めること**が条件になる。

## 結果

### 得られるもの

- 面を足す作業が「ビューを1つ書いてタブ一覧に足す」で閉じる。`AppLayout` を書き換えない
- #95 #96 と対局の置き場が決まる。止まっていた4つが動かせる
- 盤の道具（向き・ナビ・検索・課題局面）を解析ペインのヘッダから追い出す口実になる
  （`docs/spec/screens/analysis-pane.md` が挙げている欠陥）
- 表モードの表と定跡ビューの表が同じ形になり、**列の定義を差し替えられる部品1つ**で両方に乗る

### 諦めたもの

- **2つのビューを同時に見ること。** ドックは1度に1枚。
  複数エンジンの比較のように「並べて見たい」要求が出たら、
  タブではなく**表の列**か、ドックを割る話として別に決める
- 表示モードを URL で人に渡すこと

### 依存する前提

- ドックの高さが1つであること。ビューごとに必要な高さが大きく違うなら、
  `--dock-h` の決め方から見直しが要る
- **解析の状態がビューの外にあること。** いまはキャッシュが widget の `useRef` に
  あるので（#561）、これを下げるまでタブ化は退行を生む
