# ADR-0004: 通知は「復帰に何が要るか」で4段に分け、見せ方を段から独立させる

- 日付: 2026-08-29
- 状態: 採用
- 関連: `docs/OPEN-QUESTIONS.md` Q-005 / ADR-0003（意味色をここに委ねていた）

## 文脈

失敗が利用者に届かない。実測（`main` `bb29884`）の内訳は
`docs/state-transitions/failure-surfacing.md` にある。要点は2つ。

### 1. `error` の置き場が6つあり、読み手がほとんど居ない

| スライス                  | `set_error` 相当の発火元 | UI の読み手                     |
| ------------------------- | ------------------------ | ------------------------------- |
| `game`                    | **9箇所**                | **0**                           |
| `analysis`                | 4箇所                    | **0**                           |
| `study-positions`         | 2箇所                    | **0**                           |
| `search`                  | 1箇所                    | **0**                           |
| `file-tree` (`error`)     | **9箇所**                | 1（**ツリーを消す**）           |
| `file-tree` (`kifuError`) | 1箇所                    | 1（モーダル）                   |
| `engine`                  | 1箇所                    | 1（設定タブを開いている間だけ） |

`clearError` は6スライスすべてが context に公開しているが、**UI 側の呼び出し元が1つも無い**。
置き場だけが作られ、表示する場所と消す導線がどちらも作られていない。

### 2. 「再試行すれば直る」は成り立たない失敗が6件ある

分類を決める過程で、18件それぞれについて**再試行ボタンを押したら実際に直るのか**を
コードから判定した。結果、次の6件は直らない。

| #     | 失敗                   | 押しても直らない理由                                                                                                                                  |
| ----- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-1   | 設定の読み込み         | `serde_json::from_str` の失敗＝設定 JSON が壊れている（`config_dir.rs:29`）。ファイルが無い場合は default を返すので、失敗＝壊れている                |
| F-9   | エンジン初期化         | 原因はパスや評価関数の不備。加えて実装が「同じ runtime では再トライしない」（`entities/engine/model/provider.tsx:92-96`）ので**押しても何も起きない** |
| F-6   | 解析の開始             | Rust に `is_active` なセッションが残る間は `ensure_no_active_session` が必ず弾く（`src-tauri/src/engine/bridge.rs:105-112`）                          |
| F-7   | `stop_analysis`        | 停止が通らなければ F-6 の状態に固定される                                                                                                             |
| F-5   | プリセットの保存       | 変更が全て楽観的更新（`dispatch` → `await persist`）で、失敗しても画面は保存済みの表示。「もう一度作成」は**重複を生む**                              |
| F-12b | 棋譜の操作（9箇所中8） | 移動・分岐入替・分岐削除・盤面選択の失敗は同じ入力で同じ結果になる                                                                                    |

**直らないものに「再試行」を出すと、通知が無いより悪い。** 利用者は押し続ける。
この判定が、下の決定1と決定3を決めている。

## 決定

### 1. 段は「復帰に何が要るか」で4つに切る

深刻度でも「次の操作が必要か」でもない。**利用者が何をすれば直るか**で切る。

| 段        | 色             | 件数 | 意味                                               |
| --------- | -------------- | ---- | -------------------------------------------------- |
| `info`    | 伝えるだけ     | 2    | 利用者は何もしなくてよい                           |
| `warning` | 再試行で直る   | 6    | 一時的な失敗。同じ操作をもう一度で直る見込みがある |
| `danger`  | 別の操作が要る | 6    | 繰り返しでは直らない。何をすべきかは失敗ごとに違う |
| `fatal`   | アプリ再起動   | 3    | アプリの中では直せない                             |

**`info` / `warn` / `error` の3段を採らない理由**は件数にある。3段だと `error` に14件が落ち、
「再試行すれば直る」と「エンジンを再起動するまで直らない」が同じ見た目になる。
PR #73 が3段だけを残して close された経路がこれだった。

### 2. `silent` を段として持つ

出してはいけない失敗がある。`cancelSearch` の失敗（F-16）は**意図的なベストエフォート**で、
既に終了した `requestId` への cancel は no-op として通る仕様
（`entities/search/model/provider.tsx:137`）。

`silent` を型に持つことで、**握り潰しとの区別がコードに残る**。
後で「やはり出す」に変えるときも、段を差し替えるだけで済む。

### 3. ボタンは段に紐づけない。`{ label, run }` を持ち回る

`danger` の6件は、要る操作が**それぞれ違う**。

| #               | 出すボタン                         |
| --------------- | ---------------------------------- |
| F-1             | 設定を初期化                       |
| F-9             | 設定を開く                         |
| F-2 / F-6 / F-7 | エンジンを再起動（再試行と並べる） |
| F-5             | 再保存                             |
| F-12b           | 無し（再試行に意味がない）         |

固定の「再試行」ボタンでは足りない。**通知は動作を値として受け取る。**

```ts
type NotifyAction = { label: string; run: () => void | Promise<void> };
```

### 4. 見せ方は段から独立させる

同じ段の中で置き場が割れる。`warning` の6件は toast / banner / modal /
モーダル内インラインに散る。分けているのは深刻度ではなく**利用者が対処できる場所**。

段が見せ方も決める形にすると、12件それぞれに置き場を手で決めることになり、
**いま6スライスに `error` が散っているのと同じ経路をたどる**。

経路は2つに分ける。**共通なのは段（色）と動作だけ。**

| 経路       | 描くもの                                              | 誰が描くか                                   |
| ---------- | ----------------------------------------------------- | -------------------------------------------- |
| グローバル | `toast`（自動で消える／消えない）/ `banner` / `modal` | 通知基盤が1箇所で描く                        |
| インライン | 解析ペイン内・検索モーダル内・設定タブ内・入力欄の下  | そのコンポーネントが `<InlineNotice>` で描く |

**インラインを基盤に載せない理由**は、置き場がコンポーネントの中にあるため
基盤からは描けないこと。そして保存モーダルの失敗を画面隅の toast に出すと
**直すべき入力から目が離れる**こと。

この形は既に1つ main にある。`PositionNavigationModal` は、盤上で再生できない手を含む
棋譜に対して「この手目を盤上で再現できません。ここから先へは進めません」を
**モーダルの中に**出している。通知基盤を通していないが、置き場としては正しい。

### 5. 意味色は段と同数の4つ

アプリのパレット（深緑 `#3f4e4f` `#2c3639` / 生成り `#dcd7c9` / 銅 `#a27b5c`）と
同じ温度で、彩度を落として作る。

| 段        | 色        |
| --------- | --------- |
| `info`    | `#7d93a3` |
| `warning` | `#c8955a` |
| `danger`  | `#b5645c` |
| `fatal`   | `#8c4a44` |

`success` は置かない。**成功を通知する場面が現物に1件も無い**ため。必要になったら足す。

いま `KifuReadErrorDialog` が使っている `rgba(255,140,60)` 系のオレンジは、
パレットと無関係に選ばれているため浮いている。これらは上の4色に寄せる。

通知の面は**暗い側を既定にする**。浮かせるために面を明るくすると本文が沈み、
`$color-primary-light` の上に置いた本文は 3.76:1 でコントラストの基準（4.5:1）を割る。
`$color-primary-black` に落として境界と影で分離すると 7.6:1 になる。
明暗はテーマとして受け取れる形にしておき、既定を暗い側にする。

### 6. 通知は集約する。ただし `state.error` は残す

6箇所に表示・消す導線・再試行を手書きすると、**表示を6回書くことになる**。
手書きは既に1回失敗していて、唯一の読み手（`FileTree.tsx:133`）が
ツリーごと消す実装になっている。

残すものが2つある。

- **`state.error` は各スライスに残す。** 通知は「利用者に伝える」ためのもので、
  **状態としてのエラー**（解析が止まっている、ツリーが読めていない）は別物。
  通知を消しても状態は消えない
- **インラインは集約しない**（決定4のとおり）

### 7. 更新方式は「失敗が後から観測できるか」で切る

決定3の F-5 は、楽観的更新のまま失敗を握り潰したことで
**画面が保存済みを表示しながらディスクは古いまま**になる。利用者が気づくのは次回起動時。

- **悲観的更新**（成功が返るまで UI を変えない）
  - 外部プロセスと歩調を合わせる操作。解析の開始・停止、エンジンの起動・停止。
    ズレると以降の解析が全て弾かれる（issue #120）
  - **`state` が唯一の正になる永続化**。プリセット・設定の保存。
    書けたかどうかを後から読み直す経路が無く、ズレても誰も気づかない
- **楽観的更新**（先に変えて、失敗したら戻す）
  - ディスクを触る操作のうち、**結果を読み直せるもの**。ファイルの作成・改名・削除・移動。
    失敗してもツリーを再読込すればディスクの真の状態が取れる

つまり「ディスクを触るかどうか」ではなく、**失敗を後から観測できるかどうか**で切る。
F-5 がディスク操作でありながら悲観側に来るのはこのため。

### 8. 危険な操作は確認ダイアログに統一する

いま4通りに割れている。

| 操作                         | いまの確認                                                 |
| ---------------------------- | ---------------------------------------------------------- |
| ファイル／ディレクトリの削除 | `ConfirmDialog`                                            |
| 研究局面の削除（2箇所）      | `ConfirmDialog`                                            |
| エンジンプリセットの削除     | **`window.confirm()`** — OS のダイアログでテーマの外に出る |
| ワークスペースの変更         | タブ内インライン ＋ `CHANGE` と入力                        |
| **棋譜の分岐削除**           | **確認なし。押した瞬間に消える**                           |

`ConfirmDialog` 自身にも `danger` の見た目が無く、`variant="ghost"` のボタンに
赤い `span` を入れているだけなので、**「削除する」と「キャンセル」が同じ形**になっている。

- 取り消せない操作は `ConfirmDialog` に統一する。`window.confirm()` はやめる
- `ConfirmDialog` に `danger` を足す。色は決定5の `danger`
- 影響が広い操作（ワークスペース変更）の「文字を打たせる」形は**段として認める**
- **「元に戻す」による取り消しは採らない。** 履歴を持つ話になるのでエンハンスとして分ける

## 割り当て

18件の行き先。段は決定1、見せ方は決定4。

| #     | 失敗                                                         | 段        | 見せ方                                              | ボタン                     |
| ----- | ------------------------------------------------------------ | --------- | --------------------------------------------------- | -------------------------- |
| F-13  | Finder で開けない                                            | `info`    | toast（自動で消える）                               | —                          |
| F-15  | SFEN のパース失敗                                            | `info`    | toast（消えない）**同種を1つに畳んで N 件と数える** | —                          |
| F-3   | ファイル操作の失敗                                           | `warning` | modal                                               | 再試行                     |
| F-4   | イベント購読の失敗                                           | `warning` | banner                                              | 再試行※                    |
| F-10  | 研究局面の削除失敗                                           | `warning` | toast                                               | 再試行                     |
| F-11  | 研究局面の読み込み失敗                                       | `warning` | toast                                               | 再試行                     |
| F-17  | 検索の索引が作れない                                         | `warning` | 検索モーダル内インライン                            | 作り直す                   |
| F-12a | 棋譜の**保存**失敗（`entities/game` の `persistIfPossible`） | `warning` | modal                                               | 再保存                     |
| F-1   | 設定の読み込み失敗                                           | `danger`  | 起動画面                                            | 設定を初期化               |
| F-9   | エンジン初期化の失敗                                         | `danger`  | banner                                              | 設定を開く                 |
| F-2   | 解析エラー／同期タイムアウト                                 | `danger`  | 解析ペイン内インライン                              | 再試行 ＋ エンジンを再起動 |
| F-6   | 解析の開始／停止の失敗                                       | `danger`  | 解析ペイン内インライン                              | 再試行 ＋ エンジンを再起動 |
| F-7   | `stop_analysis` の失敗                                       | `danger`  | 解析ペイン内インライン                              | 再試行 ＋ エンジンを再起動 |
| F-5   | プリセット保存の失敗                                         | `danger`  | 設定タブ内インライン                                | 再保存                     |
| F-12b | 棋譜の**操作**失敗（8箇所）                                  | `danger`  | modal                                               | —                          |
| F-8   | エンジン停止の失敗                                           | `fatal`   | banner                                              | アプリを再起動             |
| F-18  | エディタ内部エラー                                           | `fatal`   | toast（消えない）                                   | アプリを再起動             |
| G-3   | React が落ちた                                               | `fatal`   | `AppErrorBoundary`（**囲った範囲だけ**）※           | 再読み込み                 |
| F-14  | 改名の名前が不正                                             | —         | 入力欄の下                                          | —                          |
| F-16  | `cancelSearch` の失敗                                        | `silent`  | —                                                   | —                          |

※ F-4 は**再試行の口が実装に無い**。effect が1回走るだけなので、作る必要がある。

※ `AppErrorBoundary` は全画面ではない。`AppLayout` の中で
**モーダル層と棋譜ペインをそれぞれ囲っている**（`pages/AppLayout.tsx` の2箇所）。
囲われていない場所で throw すると、いまも root ごと unmount する。
**`fatal` の出方は「囲った範囲だけが差し替わる」**であり、
どこを囲うかは通知の分類とは別の判断になる。

**F-2 / F-15 / F-17 の置き場は「利用者が対処できる場所」で決めた。**
F-17 を起動直後の toast にしないのは、起動時点では検索を使うか分からず、
実際に検索する頃には消えているため。この失敗の唯一の実害は
**「壊れている」と「1件も無い」が区別できない**ことなので、その区別が要る瞬間に出す。

## やらないこと

- **移行を一度に行わない。** 既存の `KifuReadErrorDialog` と `AppErrorBoundary` は
  段の割り当てだけ決めて、見た目の作り直しは分ける
- **`success` を置かない**（決定5）
- **取り消し（undo）を作らない**（決定8）
- **`state.error` を消さない**（決定6）

## 影響

- issue #157（解析やファイル操作の失敗が利用者に届かない）の前提が揃う
- issue #85（エンジン preset 切替の失敗表示）は決定7の悲観的更新に含まれる
- ADR-0003 が意味色をここに委ねていた分が埋まる。トークンは `src/index.scss` に置く
- **分類とは独立に潰すものが4件ある。** どの分類を選んでも直す必要がある
  - F-5 の unhandled rejection（issue #85）— 保存失敗が黙ってデータを捨てる
  - F-3 のツリー消滅 — `widgets/file-tree/ui/FileTree.tsx:133` の `return;`
  - F-9 の再試行が効かない構造 — `clearError` の呼び出し元が無い
  - F-7 の Rust セッション残留 — issue #120 の再発経路
