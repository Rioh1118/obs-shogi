# ADR-0016: USI のやりとりを状態機械・アクター・手順の3つに分け、呼び手を先に手順へ移してから中身を作り直す

- 状態: 採用
- 日付: 2026-11-05
- 決めたもの: `/decide`（人の確認なし。見てほしい点は PR の確認事項に残す）
- 関連: ADR-0008（`engine/` のレイヤと逆転）/ ADR-0015（エンジン周りの目標の構造）
- 入力: `docs/proposals/engine-usi-rebuild.md`。棚卸しは `docs/audits/2026-11-engine.md`
- 事実を確かめた基準: `origin/main` の 1f94ab27

## 文脈と問題

読みやすさの整理の範囲 5c は、利用者の決定で、整理ではなく USI のやりとりを作り直すための設計の段階になった。
利用者の言葉（要旨）は「タスクの間の通信をある程度型で表し、低いレイヤにも処理の単位を作って分かりやすくする。
一から作らず、いまの形を活かす。そのうえで性能と可読性を上げ、責務と定義を明確にする」。

いまの `UsiProtocol` は手順を持たない。`go` から `bestmove` までの手順は、呼び手が生の行の受け手を登録して組む。
どの探索の `bestmove` かを決める判断は、受け手を外す時機、`drain_stale`、対局の `req`、検討の `unanswered` に散っている。
作り直す前に、何をどこへ置き、どの順に移すかを決める。

## いまの形の事実（基準のコミットで数えた）

| 何 | 数 | どこ |
| --- | --- | --- |
| `register_listener` を呼ぶ箇所 | 8 | `protocol` の中に2（`readyok` の待ち、名乗りの集め）、`analyzer` に4、`setup` に1、`game/search.rs` に1 |
| `UsiProtocol` の `Arc<Mutex>` か `Arc<RwLock>` の欄 | 8 | `Link` の `listeners` `pending`、`state` `listen_active` `declared` `info_gate` `init_task` `init_cancel`。ほかに `watch` 1つと `AtomicBool` 2つ |
| 1本のプロセスのために `protocol` が起こすタスク | 3種 | 書き込みの列（1本）、読んだ行を配るタスク（1本）、`isready` ごとの `readyok` の待ちと掃き出し。書き込み1件ごとにも1本起こす |
| 実プロセス（`/bin/sh` の台本）を起こすテスト | 68 | `child` 11、`protocol` 10、`registry` 9、`setup` 5、`probe` 5、`analyzer` 11、`bridge` 17 |
| そのうち、対局のエンジンを起こすテスト | 0 | `game/session.rs` の73本は人間どうしか、起こす前に断られる設定だけを使う |

`CLAUDE.md` の「実プロセスを要する経路は1つも固定されていない」は、実物のエンジン（やねうら王など）を要する経路の話で、
台本のエンジンなら検討の経路は厚く踏まれている。**対局の経路だけが、台本でも1本も踏まれていない。**

## 判断の基準

1. 利用者の明示した言葉（上）。加えて、線の名前（Tauri コマンド、serde の欄、イベント名、保存形式）を変えない。USI の語はフロントへ出さない
2. R-DEC-1: 並行性の振る舞いが変わりうる。変わる箇所を、固定されている所と固定されていない所に分けて扱う
3. R-DEC-2: ADR-0008 の決定2（trait は差し替えが実在する所だけ。`docs/rules/rust.md` の R-RST-1）と決定3（判断は1箇所）、ADR-0015 の群の向き
4. R-DEC-5: 各段階の後で止められる。止めても、そこまでの形が読める

## 決定

### 1. 3つの単位と、それぞれの責務・入力と出力・持ち主

| 単位 | 責務 | 入力 | 出力 | 持ち主 |
| --- | --- | --- | --- | --- |
| 状態機械 `UsiMachine` | 1本のプロセスの USI の状態と、行と頼みごとをどう扱うかの判定。**時計も IO も持たない** | 受けた行（`ReadEvent` をそのまま。`option` 行は生の行から解く）、出力の終わり、書き込みの詰まり、頼まれたこと（番号札つき） | 書く行（`GuiCommand`）、札への答え、探索への行、探索の終わり、遅れて答えた知らせ、プロセスの終わり（`EngineEnd`）、落とす指示 | アクター |
| アクター | 状態機械を1本のタスクで持ち、入力を順に渡し、出力を順に実行する。判定を書かない | 頼みごとのチャネル、読み取りの行、書き込みの結果 | 書き込みの列への投入（同期。出た順のまま）、札ごとの `oneshot`、探索ごとのチャネル | 誰も持たない。ハンドルが全部落ちたら終わり、そのとき子プロセスも落ちる |
| 手順の関数 | 頼みごとを1つ送り、答えを上限つきで待つ。**待つ上限は手順が持つ** | 呼び手の引数 | `Result` と、探索なら `Search` | ハンドル（`UsiProtocol`）のメソッド |

手順と型の形は次のとおり。名前は U1 で `/naming` を通して決め直してよい。決めたのは役と型の形。

| 手順 | 送る行 | 待つもの | 返すもの |
| --- | --- | --- | --- |
| 名乗り | `usi` | `usiok`。2回目以降は覚えた名乗りを返す | `EngineInfo` |
| 準備 | `setoption` を並べて `isready` | `readyok` | 途中の `info string`（定跡を読めたかの判定に使う） |
| 値の確認 | `setoption` と `usi` | `usiok` | 途中の `info string`（`check_book_path_support` の判定に使う）。宣言は作り直さない |
| 新しい対局 | `usinewgame` | 書けたこと | `()` |
| 探索 | `position` と `go`（`go ponder` を含む） | 書けたこと | `Search` |
| 終局 | `gameover` | 書けたこと | `()` |

`Search` は探索1本の持ち分で、次の4つだけを持つ。

- 行を受ける: `info` と `checkmate` と最後の `bestmove` を、生の USI の形（`InfoParams` など）で順に返す。`bestmove` の後は何も返さない。
  集約の仕方（`apply_info_params`）は今の場所のまま。検討と対局が同じ関数を呼ぶので写しにはならない
- 先読みを本番にする: `ponderhit` を書く。先読みの探索でなければ断る
- 止める: `self` を消費する。`stop` を書いて `bestmove` を上限まで待ち、`StopAnswer` を返す。
  **D-1 の判断はここ1つ**（答えた／止めるものが無かった／上限まで答えない／届かない）。上限は呼び手が渡す（検討は3秒、対局は5秒のまま）
- 捨てる: 止めずに捨てたら、`Drop` が `stop` だけを書く（待たない）。**`Search` を持たない者は `stop` を書けない**

### 2. 時計は状態機械に入れない

待つ上限は手順が持ち、書き込みの上限（`WRITE_TIMEOUT`）は書き込みの列が持つ。状態機械の状態は、待つ者が諦めても変わらない。
止めの待ちを諦めても、エンジンは止め待ちのまま残り、遅れた `bestmove` が来るまで次の探索を断る。
これが検討の `unanswered` と、対局の `Activity::Unresponsive` の「話しかけない」を1つの状態にする。

### 3. 積み置きは状態機械へ移さない。`readyok` の前の `position` / `go` / `usinewgame` は断る

いまは `readyok` の前に来た `position` と `go` を積み、後で掃く。積み置きは、世代、`draining`、`PENDING_LIMIT`、
`DropReason` の5つの理由、掃き出しの競合の注釈をまとめて生んでいる。どれも「`Ok` を返したまま消える」を防ぐためのもの。

U2b の後、`readyok` の前に探索を頼む呼び手は無い（検討は `publish` の後、対局は `prepare_engine` の後にしか探索しない）。
状態機械は積まずに断る。断ると呼び手に見える。これで `StopEffect::CancelledQueued` も無くなり、`StopAnswer` の「止めるものが無かった」は
「既に `bestmove` が来ていた」だけになる。

### 4. kill は状態機械の入力。取り消しは呼び手の側

- kill: 状態機械は閉じた状態（`EngineEnd::Requested`）へ入り、待っている札に全部 `Cancelled` を答えてから、落とす指示を出す。
  アクターはその指示を、自分のループを止めずに実行する（`KILL_TIMEOUT` を待つ間も頼みごとに断りを返せる）
- 取り消し（呼び手が待つのをやめる）: `select!` か future を捨てることで行い、状態機械の状態は変えない。
  答えの `oneshot` が落ちていれば、アクターは答えを黙って捨てる
- `quit`: 状態機械は「こちらが終わらせた」のフラグを立ててから `quit` を書く。以後の出力の終わりは `Requested` として扱う

### 5. アクターは対局のアクターと同じ形にし、コードは共有しない

`game/session.rs` の `Runner` と同じ形にする: 状態を持つタスク1本、頼みごとは列挙と `oneshot`、自分あての送り手は weak、ハンドルが全部落ちたら終わる。
**共通の型や trait は作らない。** 入力の種類が違い、差し替える実装が無い（R-RST-1）。形を揃えるのは、読み手が片方を読めばもう片方も読めるため。

### 6. 2つのハンドル（`UsiProtocol` と `EngineShutdown`）を分ける

いまは台帳と呼び手が同じ `Arc<UsiProtocol>` を持ち、呼び手も `kill_engine` を呼べ、台帳も行を送れる。
U4 でハンドルを2つの型に分ける。

| 型 | できること | 持つ者 |
| --- | --- | --- |
| `UsiProtocol` | 手順、終わりの見張り、直近の出力 | 呼び手（`analyzer`、`game`、`probe`）。台帳から受け取る |
| 落とすハンドル（名前は U4 で決める。`EngineShutdown`） | `quit`、kill、終わりの見張り | 台帳だけ |

どちらもチャネルの送り手を包むだけなので `Clone` と `Debug` を持てる。`EngineRegistry` の `Debug` はここで付く。

### 7. 状態機械は別のレイヤにし、tokio を禁じる

状態機械は新しいレイヤ `usi_machine` に置き、`LAYERS` の `forbids` に `tokio` と `tokio_util` を挙げる。
「IO を持たない」を注釈ではなく `no_layer_uses_a_crate_it_must_not` で止める。`protocol` がそれを使う。
**辺は U3 で使うようになってから足す**（ADR-0008 決定1）。

### 8. 段階の順

**呼び手を先に手順へ移し、その後で中身を作り直す。** 手順の表面を先に固め、呼び手の変更は、中身がいまの実装のまま行う。
中身の作り直しは、表面が狭くなってから行う。

| 段階 | やること | 振る舞いを何で固定するか | 止めたときに残る形 |
| --- | --- | --- | --- |
| U0 | 載せ替えの前に要るテストと、性能の基準線（`docs/state-transitions/engine.md` の T1〜T10、下の M1〜M2）。製品のコードは変えない | 足したテスト自身。直した箇所の変異で落ちることを確かめる | テストが増えただけ |
| U1 | 手順の関数と `Search` を、**いまの** `UsiProtocol` の上に置く（中身は今の受け手の登録と `send_command`）。`registry` `setup` `probe` を手順へ移す。B-10 の `protocol` の側（起動の失敗の理由を列挙で持ち、直近の出力を別の欄で持つ。`Display` の綴りは変えない） | U0 と既存の68本。`StopAnswer` への写像は純関数で全通り | 手順が読める。呼び手の半分はまだ受け手を登録する |
| U2a | `analyzer` を手順へ移す。`collect_until_bestmove` の止め方、`drain_stale`、`StopVerdict`、`infinite_listener` を消す | `bridge` の17本と `analyzer` の11本、U0 の T7・T8 | 検討の側から受け手の登録が消える |
| U2b | `game` を手順へ移す。`run_search` は `Search` を回すだけになり、`outcome_of_stop` を消す | U0 の T1〜T6 と `session.rs` の73本 | 受け手を登録するのは `protocol` の中だけ |
| U3 | 状態機械をレイヤ `usi_machine` に作り、`UsiProtocol` は1つの std の `Mutex` の下でそれを持つ。受け手の表と積み置きを消す | 状態機械の表（`docs/state-transitions/engine.md`）の全セルを純関数で。台本の68本と U0 | 判定が純関数で読める。ロックは1つ |
| U4 | アクター: タスク1本で状態機械を持ち、配るタスクと `readyok` の待ちのタスクを消す。2つのハンドル（`UsiProtocol` と `EngineShutdown`）を分ける。C-3 | 全部の台本のテスト、U0 の T10（探索中にハンドルを捨てるとプロセスが落ちる）、M1〜M2 を基準線と比べる | 目指す形 |

U3 と U4 を分けるのは、判定の置き場の変更と並行性の変更を別の差分にするため。U3 の `Mutex` は await を跨がない（状態機械は同期）。

### 9. 性能は2つの時間と1つの数で見る

| 指標 | 何を測るか | どう測るか | 良くなったと言える条件 |
| --- | --- | --- | --- |
| M1 | `info` の流れの遅れ | 台本のエンジンが `go` を受けたら `info` を2000行続けて書き、`bestmove` を書く。`go` を書いてから呼び手が `bestmove` を受け取るまでの時間を5回測り、中央値と最小・最大を残す | U4 の中央値が、基準線の最小より小さい |
| M2 | 停止から `bestmove` までの時間 | 台本のエンジンは `stop` に即 `bestmove` で答える。止める手順を呼んでから答えが返るまでを20回測り、中央値と最小・最大を残す | 同上 |
| M3 | 1本のプロセスのために持つロックの数 | `protocol` の `Arc<Mutex>` と `Arc<RwLock>` の欄を数える（基準は8） | U4 で0 |

- 測るのは呼び手から見た時間。台本の書く速さは前後で同じなので、差は取り次ぎの側に出る
- テストは `#[ignore]` を付けて `cargo test -- --ignored` でだけ走らせる。CI の時間に入れない
- 値は `research/engines/usi-measurements.md` に、日付と基点のハッシュを付けて足す
- **U1〜U3 では性能を合否に使わない**（変える見込みが無い）。U4 で基準線の範囲より悪くなったら、理由を書くまでマージしない
- 測るまで「速くなった」と書かない。範囲に収まったら「変わらない」と書く

### 11. 振る舞いが変わる箇所

作り直しは振る舞いを変えないのが原則だが、次は意図して変える。どれも、いまの呼び手が踏まない経路で、
積んで `Ok` を返す代わりに断る向き。U3 で、呼び手が踏まないことを `dead_code` と grep で確かめてから入れる。

- `readyok` の前の `position` / `go` / `usinewgame` を積まずに断る（決定3）
- 探索中（止め待ちを含む）の `setoption` / `isready` / `usi` / `usinewgame` / `gameover` と、2本目の探索を断る。
  いまは呼び手（`bridge` の席、`Activity`）が守っていて、`protocol` は通す
- 頼んでいない `bestmove`（探索していないときに来たもの）を捨てて記録する。いまは受け手が居れば配る

## 検討した選択肢

| 判断 | 選んだもの | 選ばなかったもの | 最初に差がついた基準 |
| --- | --- | --- | --- |
| 段階の順 | 呼び手を先に手順へ移し、中身を後で作り直す | 提案の順（状態機械 → 手順 → 呼び手） | R-DEC-1: 対局の経路はテストが0本で、そこを動かす差分を、中身がいまの実装のうちに入れられる。提案の順だと、中身の並行性と呼び手の両方が変わった後に対局を動かすことになる。加えて R-DEC-5: 提案の順では積み置きを状態機械へ移してから消すことになる |
| 時計の置き場 | 手順が持つ | 状態機械が締切を持ち、アクターが時刻を渡す | R-DEC-2: いまの上限は手順ごとで、対局は全体の締切から借りて縮める（`START_TIMEOUT`）。状態機械が持つと締切の計算が2か所に割れる。状態が諦めで変わらないので、持たせる理由も無い |
| `info` の流れ | `Search` が受け手を包む | 呼び手が受け手を登録する（いま）／生のチャネルを返す | 利用者の言葉（型で表す）: 生のチャネルでは `stop` を `Search` に縛れない。登録はいまの取り違え（次の探索の受け手が前の `bestmove` を受ける）の元 |
| アクターを揃えるか | 形を揃え、コードは共有しない | 共通のアクターの型か trait | R-DEC-2（R-RST-1）: 差し替える実装が無い |
| kill の扱い | 状態機械の入力 | アクターだけで扱う | R-DEC-1: 待っている札に答える順と、閉じた理由（`Requested` が優先）を状態機械の表で固定できる。アクターだけで扱うと、kill の後に来た出力の終わりを「エンジンが終わった」と読む経路を、アクターの作りで防ぐことになる |
| 積み置き | 移さずに断る | 状態機械へ移す | R-DEC-1: 積んで `Ok` を返す形は、捨てたときに呼び手が気付けない。断れば見える。呼び手が踏まないことは U3 で確かめる |
| ハンドル | 2つのハンドル（`UsiProtocol` と `EngineShutdown`）に分ける | 1つのハンドル | R-DEC-1: 落とすのは台帳の責務（ADR-0008 の「作る場所が1つ」）で、呼び手が落とせる道を型で塞げる |
| 状態機械の置き場 | 別のレイヤで tokio を禁じる | `protocol` の中のファイル | R-DEC-5: 「IO を持たない」を機械で止められる。`LAYERS` はレイヤの単位でしか禁じられない |
| 性能の合否 | U4 だけで、基準線の範囲と比べる | 毎段階で比べる／測らない | 利用者の言葉（性能を上げる）と、測っていない見込みであること。変える見込みの無い段階で比べると、揺れを差と読む |

## 結果

- 良い: どの探索の `bestmove` かを決めるのが状態機械の1か所になり、受け手を外す時機・`drain_stale`・`unanswered`・積み置きの世代が要らなくなる
- 良い: 判定が純関数になり、`docs/state-transitions/engine.md` の状態機械の表とセルが1対1になる
- 良い: 各段階で止めても、そこまでの形が読める（U1 で止めても、手順の表面は残る）
- 悪い: U1 で作る手順の中身は、U3・U4 でもう一度書き直す。表面を先に固めるための手戻りとして引き受ける
- 悪い: 段階が9つ増え、整理の範囲と交互に並ぶ。並びの正本を進捗の表1か所に置いて追う
- 悪い: 対局の経路を固定する U0 のテストのうち、止めの上限（5秒）を待つものは遅い。`#[ignore]` にはしない（載せ替えの回帰テストなので）

## 戻し方

- 段階ごとに止められる（決定8の表の右端）。止めた段階より後は進捗の表から消す
- 積み置きを断る変更（決定11）は U3 の1コミットに閉じる。戻すなら、そのコミットを戻して状態機械に積み置きを足す
- 段階の順を提案の順へ戻すなら、U1〜U2b の前に U3・U4 を置き直す。U0 はどちらの順でも先頭に要る
