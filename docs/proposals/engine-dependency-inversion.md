# 提案: engine の残った境界を、どこまで逆転するか

ADR-0008 が段と逆転の型を既に決めている。ここで決めるのはその続き
——**「まだ逆転していない境界」に並ぶ3つのうち、どれをやるか**と、
**やらないと決める境界はどれで、なぜか**。

論点は「抽象を増やすか」ではない。**どこは密結合のままがよく、
どこは柔軟性が要るのか**を、この repo の中で判定できる基準に落とすこと。

## 基準: 黙っている場所を減らすときだけ逆転する

「差し替えたいか」では決まらない。この repo は一度も差し替えのために
逆転していない。実際に入れた2つは、どちらも**観測できないことが理由**だった。

- `GameEventSink`——「`emit` は黙って捨てるだけになり、`Over` を出したか、
  `TurnChanged` に何を載せたかを確かめる手段が無い」（`engine/game/events.rs`）
- `SideClock` が経過時間を外から受け取る形——「`Instant` を内側に持つと
  『30 秒使った』をテストで書けない」（`engine/game/clock.rs`）

どちらも「実装を替えたい」ではなく「**正しいかどうかを外から言えない**」。
逆転はその黙りを1つ潰すために入っている。

逆向きも同じ基準で読める。**逆転が黙りを増やすなら、入れない。**
密結合が安全性そのものになっている境界がそれで、この engine には1つある。

|                        | 密結合のままにする                           | 逆転する                           |
| ---------------------- | -------------------------------------------- | ---------------------------------- |
| 何を見るか             | 逆転すると**間違いが黙って通る**ようになる   | いま**正しさを外から観測できない** |
| 間違えたときに出るもの | 型か検査が落ちる／唯一性が壊れると事故になる | 何も出ない                         |
| この repo の例         | エンジンの台帳                               | 対局の出来事の宛先、持ち時間の経過 |

## 境界ごとの判定

### 1. 解析のファサードが `tauri::AppHandle` を持つ — 逆転する

ADR-0008 が「次に効くのはここ」と書いている境界。決定も実装の置き場
（`commands::analysis`）も既にある。残っているのは実装だけ。

いまの形は `Arc<RwLock<Option<tauri::AppHandle>>>` と `set_app_handle` で、
**`None` の枝が「黙って捨てる」そのもの**になっている。`DiscardEvents` の doc が
「`Option` にしないのは、`None` の分岐が呼び出し側に出るのを避けるため」と
名指しで避けた形が、解析側にはそのまま残っている。

観測できていないものが具体的にある。`"analysis-update"` の payload に
`session_id` を載せる理由は、前の探索が畳まりきる前に次が始まったとき
「前の局面の読み筋が現在の盤面の解析結果として画面に出る」のを受け手に
照合させるためだと doc が書いている。**その取り違えが起きる経路を再現する
テストは1本も無い**——宛先が具象なので、何が流れたかを溜められない。

対局側と同じ形にする。口は `bridge` が決め、実装は `commands::analysis` に置く。
テスト用の宛先は `RecordedEvents` と同じ形でよい。

**併せてラチェットを閉じること。** ADR-0008 は「決定を書いただけだと
`verify:rust` は全部緑のまま通る」と書いていて、それは今の `bridge` に
当てはまる。`tests/layering.rs` の `LAYERS` で `bridge` の `forbids` に
`tauri` を挙げるところまでやって、はじめて戻せなくなる。

### 2. プロセスとの行のやり取り — 逆転する。ただし別 PR

CLAUDE.md が「実プロセスを要する経路は1つも固定されていない」と書き、
名指しで2つ挙げている（終局の通知が実際にワイヤへ出ること、先読み確定の
書き込みが落ちたとき）。**これがこの engine でいちばん大きい黙り**で、
基準にまっすぐ当たる。

ただし**どこで切るかを間違えると、逆転が黙りを増やす側に回る。**

`UsiProtocol` そのものを trait にしない。あの型の中身は並行性そのもので、
書き込みの列、`WRITE_TIMEOUT` の打ち切り、`fail_writes`、3値の ready、
詰まりと終了を分ける印、`Drop` の `kill().unwrap()` を避けるための
`Option` + 忘却まで全部そこに載っている。trait にすると、テスト用の実装は
それを**もう一度書くことになる**。そうして書いた偽物に対して通ったテストは、
本物の待ち方を1つも保証しない。

切るのは**1段下、行の口**。並行性は具象1つ（`UsiProtocol`）に残したまま、
その下に「1行書く／読んだ行を1本の受け口へ流す／落とす」だけの口を置く。

```rust
/// 1本のプロセスとの行のやり取り。**行より上のことを何も決めない。**
///
/// 同期で持つ。呼ばれるのは書き込みの列の中と `spawn_blocking` の中だけで、
/// 逃がす責任は上（`UsiProtocol`）にある。ここを async にすると、
/// 逃がし方まで実装ごとに決まってしまう。
pub trait EngineChannel: Send + Sync + 'static {
    fn write(&self, command: &GuiCommand) -> Result<(), String>;
    fn start_reading(&self, out: mpsc::UnboundedSender<EngineCommand>) -> Result<(), String>;
    fn kill(&self) -> Result<(), String>;
}
```

本物の実装は `usi` のハンドラを包むもの1つ。テスト用は台本を持つもの1つで、
書かれた行を全部溜め、返す行を順に流し、**stdin を読まなくなる**／
**出力を終える**を別々に起こせるようにする。この2つが別々に起こせることが
要る——いまは詰まりと終了で文言も直し方も違うと doc が書いているのに、
どちらが起きたのかを確かめる経路が無い。

これで埋まるセルは、CLAUDE.md が挙げた2つのほか、1行の長さの上限3つ
（手数・option の件数・欄の長さ）が**実際に線に出る1行を短く保っている**
ことの確認まで届く。いまはどれも入口の値しか見ていない。

**この PR ではやらない。** `protocol.rs` は大きく、触るのが `Drop` の
まわり——コードが意図的に避けている場所——になる。加えて、段の表に
`protocol` の下の段を1つ足す必要がある。`forbids` はクレート単位なので
「`usi` の型は使ってよいが、ハンドラの型だけは持ってはいけない」を
今の走査では書けない。**綴りを名指しする検査が別に要る**ことを、
着手する側が知っている必要がある。

### 3. 探索と解析が `Arc<UsiProtocol>` に直に依存する — 逆転しない

ADR-0008 は独立した境界として挙げているが、**2をやれば継ぎ目は自動的に付く**。
台本を持つ口の上に本物の `UsiProtocol` を載せて、その上で探索も解析も
そのまま回せる。逆転がもう1枚要るわけではない。

ここに別の trait を置くと逆に困る。口は `UsiProtocol` の表面
（送る、聞く、`stop` の効き方、ready の3値）をほぼ全部写すことになり、
写した先で**本物と挙動の違う実装をテストが選べる**ようになる。
継ぎ目は1プロセスにつき1つ、**観測できないものが実際に居る場所**に置く。

### 4. エンジンの台帳 — 逆転しない。ここは密結合が安全性そのもの

ADR-0008 の一覧に「`EngineRegistry` が `usi::UsiEngineHandler` に直に依存する」と
あるが、これは**台帳を抽象化する話ではなく、上の2の話**。台帳が持つ
「どのプロセスが生きているか」という責務のほうは、逆転してはいけない。

理由は `GameManager` の `registry` 欄の doc が既に書いている。別の台帳を
渡すと対局は消え、落とす呼び出しは知らない ID として `debug` を1行出して
**成功で返り**、プロセスは誰からも参照されずに残る。`Result` も警告も出ない。

いまその間違いが起きないのは、台帳を作る場所がアプリに1つしか無いからで、
`EngineRegistry::new` の doc は「1つにするのは終了時の掃除の宛先を1つに
保つため」と書いている。**唯一性が不変条件になっている。**

台帳を trait にすると、その不変条件は「作る場所が1つ」という構造の性質から
「渡す側が正しく渡す」という呼び出し規約に降格する。**破ったときに何も
出ないので、降格したことに誰も気付けない。**基準の逆向き——逆転が黙りを
増やす側——に当たる。

台帳のテストが要るなら、口を割らずに 2 の台本を渡せばよい。起こす経路が
`spawn` 1本に絞ってあるのは「検査を通らない起動経路を後から足せないようにする」
ためで、口を増やすとその絞りも同時に緩む。

## 順序

1. 解析の宛先を逆転し、`bridge` の `forbids` に `tauri` を足す（この境界だけで閉じる）
2. 行の口を切り出す。段を1つ足し、名指しの検査を併せて書く（別 PR）

3 と 4 は**やらないと決める**ぶんなので、ADR-0008 の「まだ逆転していない境界」を
そのままにしておくと、読み手には3件の宿題に見える。1件は 2 に畳み、
1件は「逆転しない」に書き換えること。

## この提案が引き受けないこと

- 差し替えのための抽象は増やさない。基準に「いま観測できないもの」を要求して
  いるので、**踏める経路が無いうちは足さない**（ADR-0008 の末尾と同じ）
- `Arc<dyn Trait>` の動的ディスパッチは、行の口では1手あたり数回〜
  秒あたり数十行の頻度になる。ADR-0008 が対局の出来事について
  「問題になる規模ではない」と書いたのと同じ範囲に収まる
