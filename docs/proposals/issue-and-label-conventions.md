# 提案: issue とラベルの規約

- 日付: 2026-09-01
- 状態: **提案。**対応する問いは `docs/OPEN-QUESTIONS.md` **Q-007**。
  合意できたら `docs/decisions/` へ ADR として起こし、この案と Q-007 の両方を消す
- 関連: `docs/OPERATING-MODEL.md`、`docs/IDEAS.md`（issue を立ててよい条件）、
  ADR-0001（ブランチと PR の方針）、ADR-0006（WIP 制限をやめた）

## 文脈

### いま2つの規約が併存していて、片方だけが文書になっている

`CONTRIBUTING.md` の「1. Issue を立てる」は**外から来る人向け**の一般論で、
「何をしようとしたか / 何が起きたか / 本来どうなってほしかったか / OS / 再現手順」を挙げている。
`.github/ISSUE_TEMPLATE/bug_report.yml` もその形。

一方、**実際にこのリポジトリに立っている issue はまったく違う形**をしている。

```
#325 文字コードの判定が3層に散っていて、検索に出るのに開けない棋譜がある
#330 {preset: HIRATE, data: 別盤面} の JKF を Rust と TS が逆に解釈する（検索は当たるが別の盤が出る）
#332 レビュー7ラウンドで「空振りのテスト」が毎回出た。判定関数に cargo-mutants を掛ける
```

本文の構造も決まっている（#325 を例に）。

1. **事実の表** — 経路ごとに「何を試すか」「場所（ファイル:行）」
2. **何が起きるか** — 利用者から見た症状。「検索では出るのに開けない」
3. **付随** — 直接の原因ではないが同じ場所で見つかったこと
4. **直し方の案** — 断定しない。判断が要る点を明示する
5. **出どころ** — レビュー報告書のパス、あるいは元の issue 番号

**この形はどこにも書かれていない。** 書かれていないので、
新しく立てるたびに再発明されるし、質が振れる。

### ラベルが定義されているのに、ほぼ付いていない

2026-09-01 に数えた。

| 対象            | ラベル0件 | 1件 | 2件 | 3件 |
| --------------- | --------- | --- | --- | --- |
| open 60件       | **45**    | 3   | 6   | 6   |
| closed 直近20件 | **20**    | 0   | 0   | 0   |

`area:engine` / `area:book` / `area:analysis` / `area:ui` / `track:T1-foundation` /
`epic` を作ってあるのに、**open の75%・closed の100%が無ラベル**。
`area:` は4つしかなく、実際の issue が集まっている領域
（棋譜の読み書き・文字コード・索引・検証の穴）を1つも指せない。

**使っていないラベルは、無いより悪い。**「ラベルで絞れる」と思って絞ると取りこぼす。

### 無いもの

- **CHANGELOG.** ただし `docs/RELEASE.md` は**手順**を持っている
  （`v0.1.3` 以降は人手で書く、雛形は前回のものを引く）。**決まっていないのは本文の見出し語彙だけ。**
- **コミットの trailer.** `Fixes:` で修正対象のコミットを指す習慣が無い

## 決定（案）

### 決定1: issue の型を成文化する。ただし2種類に分ける

**外向けと内向けを混ぜない。** 混ざっているのがいまの問題。

|            | 外向け（`.github/ISSUE_TEMPLATE/`）        | 内向け（`/write-issue`）                      |
| ---------- | ------------------------------------------ | --------------------------------------------- |
| 誰が書くか | このリポジトリの外の人                     | メンテナ（と `/implement` のレビュー）        |
| 求めるもの | 再現手順・環境・スクリーンショット         | **測った事実・利用者から見た症状・出どころ**  |
| 前提       | コードを読んでいない                       | **コードを読んで再現を確かめている**          |
| 置き場     | **Issue Forms を唯一の場所にする**（下記） | `.claude/skills/write-issue/SKILL.md`（新設） |

**外向けの必須項目がいま2箇所にある。**`.github/ISSUE_TEMPLATE/bug_report.yml`（Issue Forms）と、
`CONTRIBUTING.md` の散文の一覧（「何をしようとしたか / 何が起きたか / …」）。
**Issue Forms を唯一の場所にし、`CONTRIBUTING.md` 側はテンプレートへのリンクに置き換える。**
この変更は同じ PR に含める。

内向けの型は、上の1〜5をそのまま規約にする。**タイトルの規則**も足す。

- **症状を書く。原因や対策を書かない。**
  ✅ `検索に出るのに開けない棋譜がある` / ❌ `read_text_portable を直す`
- **数えたなら数字を入れる。** `（5経路のうち塞がっているのは1つ）`
- **「〜すべき」を使わない。** `〜という入力で〜になる` の形にする（`/write-issue` の「タイトル」と同じ）

### 決定2: `epic` の使い方を決める

いまの `epic`（#290 など）は**吸収した issue を checkbox で並べ、
吸収した理由と、独立して残したものを書く**形になっている。これは良い形なので固定する。

**epic を立ててよいのは、次の両方を満たすときだけ。**

- 束ねる issue が**同じ判断を共有している**（判断を1回にまとめれば PR が1本で済む）
- 吸収する issue を**close する**（open のまま束ねない。二重管理になる）

**進捗管理のために epic を立てない。** それは `docs/OPERATING-MODEL.md` の週次レビューの仕事。

### 決定3: ラベルは「必ず付ける2軸」だけにして、残りは消す

**付けないラベルは消す。** 残すのは機械か習慣で必ず付くものだけ。

| 軸       | 値                                                        | 必須か              |
| -------- | --------------------------------------------------------- | ------------------- |
| **種類** | `bug` / `enhancement` / `documentation`                   | **必須。1つだけ**※  |
| **領域** | `area:*`                                                  | **必須。1つ以上**   |
| 束ね     | `epic`                                                    | 該当時のみ          |
| 募集     | `help wanted` / `good first issue`                        | 該当時のみ          |
| 自動     | `dependencies` / `javascript` / `rust` / `github_actions` | dependabot が付ける |

`area:` を実態に合わせて張り直す。**いまの4つでは足りない。**

```
area:engine     USI エンジン（Rust プロセス、プロトコル）
area:analysis   解析・評価値
area:kifu       棋譜の読み書き・変換・文字コード     ← 新規。いま一番多い
area:search     横断検索・索引                       ← 新規
area:ui         UI / UX / レイアウト
area:book       定跡
area:game       対局                                 ← 新規（これから）
area:build      検証・CI・ハーネス                   ← 新規
```

※ `question` は種類から外す。`.github/ISSUE_TEMPLATE/config.yml` が「使い方の質問」を
Discussions へ誘導しているので、`question` ラベルが付く issue の入口が無い。

**`blank_issues_enabled: true`**（同 config.yml）なので、テンプレートを通らずに
空の issue を立てる経路が残っている。**種類・領域を必須にするなら、この扱いを決める必要がある** → 未決。

**消すもの**: `track:T1-foundation`（使われていない。優先順位は `docs/` が持つ）、
`duplicate` / `invalid` / `wontfix`（close の理由はコメントで書く方が情報が多い）、
`codex`（説明が空）。

**移行**: 既存の無ラベル issue に遡って付け直す。65件を手で付けるのは高いので、
**open のぶんだけ**付ける。closed は放置してよい（検索の対象にならない）。

### 決定4: コミットの trailer を2つだけ入れる

Linux カーネルの慣習のうち、**1人開発でも効くもの**だけを採る。

| trailer                       | いつ               | なぜ                                                                                                               |
| ----------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `Fixes: <短縮sha> ("<件名>")` | **退行を直すとき** | どのコミットが壊したかが `git log` から辿れる。`/implement` 手順8 の「自分が作った退行は隠さず先に書く」と対になる |
| `Closes: #N` / `Refs: #N`     | issue に紐づくとき | GitHub の自動 close と、close しない参照を区別する                                                                 |

**採らないもの**と理由。

- `Signed-off-by:`（DCO）— 外部からの PR がまだ無い。**要るのは他人のパッチを取り込み始めてから**
- `Reviewed-by:` / `Acked-by:` — レビュアーが1人（自動レビュー）なので情報量が無い
- `Reported-by:` — 報告者がまだ自分だけ

### 決定5: CHANGELOG は置かない。リリースノートの**語彙**だけ決める

`CHANGELOG.md` を手で書くと必ず腐る（`CLAUDE.md` の「件数をここに書かない」と同じ理由）。
**GitHub のリリースノートを唯一の場所にする。**

**手順は `docs/RELEASE.md` が既に持っているので、そちらへ節を足す。**
この提案が決めるのは語彙だけで、書き方の手順は増やさない。

- 見出しは `Added` / `Changed` / `Fixed` / `Removed`（Keep a Changelog の語彙）
- **各行は「利用者から見て何が変わったか」を書く。** コミット件数や内部の改名を並べない
- **破壊的変更は別の見出しで先頭に置く**（設定ファイルの移行が要るものなど。→ ADR-0007）
- バージョンは SemVer。`0.x` の間は minor で破壊的変更を許す

## 結果

### 得られるもの

- issue の質が人（とセッション）によって振れなくなる
- **ラベルで絞れる**ようになる。いまは絞ると 75% を取りこぼす
- 退行を直したコミットから、壊したコミットへ辿れる

### コスト

- **open 60件にラベルを付け直す。** 1件30秒でも30分
- ラベルを消すと、それが付いた closed issue から情報が落ちる（`wontfix` など）

### 失効条件

- 外部からの PR が来始めたら `Signed-off-by:` と `Reviewed-by:` を再検討する
- issue が200件を超えたら `area:` の粒度が足りなくなる

## 参考にした外部の慣習

**出典を明記する。** 「OSS 標準」と書いて根拠を書かないのは、この ADR がやってはいけないこと。

| 慣習                               | 出典                                                 | 採ったか                                         |
| ---------------------------------- | ---------------------------------------------------- | ------------------------------------------------ |
| 件名は命令形・本文は「なぜ」を書く | Linux `Documentation/process/submitting-patches.rst` | **既に採っている**（`CLAUDE.md` のコミット規約） |
| 1コミット1論理変更                 | 同上                                                 | **既に採っている**（`/implement` 手順3）         |
| `Fixes:` trailer                   | 同上                                                 | **採る**（決定4）                                |
| `Signed-off-by:` / DCO             | 同上                                                 | 採らない（決定4）                                |
| Conventional Commits               | conventionalcommits.org                              | **既に採っている**（`<type>: <description>`）    |
| SemVer                             | semver.org                                           | **採る**（決定5）                                |
| Keep a Changelog の語彙            | keepachangelog.com                                   | **語彙だけ採る。**ファイルは置かない（決定5）    |
| Issue Forms                        | GitHub Docs                                          | **既に採っている**（`bug_report.yml`）           |
| Contributor Covenant               | contributor-covenant.org                             | **既に採っている**（`CODE_OF_CONDUCT.md`）       |

**このリポジトリは外形の作法（テンプレート・行動規範・SECURITY・dependabot）を既に満たしている。**
欠けているのは外形ではなく、**実際に書いている内容の規約**と**ラベルの運用**。

## 未決

- **ラベルを消す判断。** `wontfix` などを消すと過去の close 理由が読めなくなる。
  消さずに「新規には使わない」にする案もある
- **`area:` を必須にする強制手段。** GitHub Actions で無ラベルの issue に
  コメントする案があるが、1人開発では自分に催促するだけになる
- **`blank_issues_enabled` を false にするか。** false にすると外部の人の敷居が上がる
- **`.claude/plans/` を追跡下に出すか。** いま `.gitignore` 済みで、
  「何を作るか」の記録が公開リポジトリから読めない
- **`specs/` 相当の層を置くか**（→ `research/shogihome/07-project-ops.md`）。
  「何を作るか」の置き場が `.claude/plans/` しか無く、そこは実装計画と混ざっている
