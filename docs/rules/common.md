# 設計の共通ルール

`/design-before-implement` は書く前に、`/review-and-plan` と `/cross-cutting-audit` は書いた後に、同じルールを使う。
言語ごとの追加は [rust.md](rust.md) と [ts.md](ts.md)。

- **ID は再利用しない。** 消したルールの番号は欠番にする
- `機械` の列に名前があるルールは検査が見ている。**レビューで指摘しない**
- 迷ったら守る理由を答えられるかで判断する。理由が言えないルールは `/cross-cutting-audit` で消す案を出す
- 正本が別にあるものは写さない。コメントは `CONTRIBUTING.md`、レイヤは `CLAUDE.md`、見た目は `docs/spec/design-language.md`

## 責務

| ID      | ルール                                                                   | 判断の基準                                                 | 機械                    |
| ------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- | ----------------------- |
| R-RES-1 | 変更の理由が同じものを同じ場所に置く                                     | 1つの変更で触るファイルが増えていくなら、置き場を疑う      | —                       |
| R-RES-2 | 1つのモジュールは1文で説明できる責務だけを持つ                           | 説明が「と」で繋がるなら割る。行数では割らない（ADR-0009） | —                       |
| R-RES-3 | モジュールは深くする。呼び手が知ることを少なくし、内側で多くを引き受ける | 消しても複雑さが呼び手へ移らないなら、その層は要らない     | —                       |
| R-RES-4 | 依存は下向きだけ。共有するなら共有できる位置まで下げる                   | 上向きに読みたくなったら、置き場が違う合図                 | `no-restricted-imports` |
| R-RES-5 | 知識は持ち主に置く。他のモジュールのデータを外から組み立てない           | 同じ欄を束で渡し続けるなら、型か持ち主のメソッドにする     | —                       |

## 変更のしやすさ

| ID      | ルール                                                 | 判断の基準                                                 | 機械         |
| ------- | ------------------------------------------------------ | ---------------------------------------------------------- | ------------ |
| R-CHG-1 | 種類が1つ増えたとき、1か所に1行足せば済む形にする      | 同じ分岐が2か所にあるなら、1つの表か型へ寄せる             | —            |
| R-CHG-2 | 種類を網羅できる形で書く。足し忘れはコンパイルで落とす | 既定の枝で受けず、全部の場合を書く                         | —            |
| R-CHG-3 | 見えている要求の分だけ作る。推測の拡張点を作らない     | 使う場所が1つも無い引数、設定、差し替え口を足さない        | knip（一部） |
| R-CHG-4 | 呼び手が知る順序や前提を減らす。1つの口で完結させる    | 「先に A を呼ぶこと」と書くなら、1つにまとめられないか問う | —            |

## 共通化（AHA）

**早すぎる共通化より重複のほうが安い。** 形が同じでも、変更の理由が同じときだけまとめる。

| ID      | ルール                                                     | 判断の基準                                                           | 機械 |
| ------- | ---------------------------------------------------------- | -------------------------------------------------------------------- | ---- |
| R-DUP-1 | 変更の理由が同じときだけまとめる                           | 「片方の仕様が変わったら、もう片方も必ず変わるか」。はいならまとめる | —    |
| R-DUP-2 | 2回までは重複を許す。3回目に共通点と差分を見てから決める   | 回数は確認の合図で、条件ではない。1回でも同じ規則の写しなら R-DUP-3  | —    |
| R-DUP-3 | 規則の写しは数によらず1つにする                            | 判定、丸め、形式、上限が2か所にあるなら、1か所へ寄せる               | —    |
| R-DUP-4 | 共通の関数に引数と分岐が増え始めたら、その抽象は誤っている | 呼び手ごとの旗で動きを変えるなら、呼び手へ戻してから作り直す         | —    |
| R-DUP-5 | まとめたものには素直な名前が付くこと                       | 名前が `common` `util` `handle` `process` になるなら、概念がまだ無い | —    |

## 命名

| ID      | ルール                                          | 判断の基準                                                     | 機械 |
| ------- | ----------------------------------------------- | -------------------------------------------------------------- | ---- |
| R-NAM-1 | 名前だけで役割が読める                          | 素直な名前が付かないなら設計を疑う                             | —    |
| R-NAM-2 | 同じ概念に同じ語を使う。語の正本は `CONTEXT.md` | コード、画面、文書で同じ語。新しい語は先に `CONTEXT.md` へ足す | —    |
| R-NAM-3 | 1語に2つの意味を持たせない                      | 「閉じる」のように複数の動作を指すなら語を分ける               | —    |
| R-NAM-4 | 同じ形の処理には同じ命名の型を使う              | 同じ役割の関数が別の動詞、別の語順なら、どちらかに揃える       | —    |
| R-NAM-5 | 真偽値は肯定形で、問いとして読める名前にする    | `disabled` の否定を重ねない。二重否定を書かない                | —    |

## 副作用

| ID      | ルール                                                          | 判断の基準                                     | 機械 |
| ------- | --------------------------------------------------------------- | ---------------------------------------------- | ---- |
| R-EFF-1 | 判定と作用を分ける。判定は純関数に置く                          | 判定が IO や状態の書き換えを含むなら外へ出す   | —    |
| R-EFF-2 | 名前どおりの作用だけを持つ。読む名前の関数は書き換えない        | `get` `is` `to` が状態を変えない               | —    |
| R-EFF-3 | 非同期の完了を待つ間に何が古くなるかを答える                    | 宛先、本文、基準を、完了後に確かめ直す         | —    |
| R-EFF-4 | 外部の状態機械と歩調を合わせる処理は、両方の状態を1つの表で扱う | `docs/state-transitions/` の表に外部の列がある | —    |
| R-EFF-5 | 状態を書き換える口を1つにする                                   | 同じ状態の書き手を数える。複数なら理由を言える | —    |

| ID      | ルール                                                     | 判断の基準                                     | 機械 |
| ------- | ---------------------------------------------------------- | ---------------------------------------------- | ---- |
| R-COR-1 | 受入条件どおりに動く                                       | 入力と結果の組で言える                         | —    |

## エラー

段は「復帰に何が要るか」で切る（ADR-0004）。

| ID      | ルール                                 | 判断の基準                                                  | 機械                                   |
| ------- | -------------------------------------- | ----------------------------------------------------------- | -------------------------------------- |
| R-ERR-1 | 失敗を黙って捨てない                   | 捨てるなら理由を書く。「起きても害が無い」を説明できる      | `kill_result_is_not_discarded`（一部） |
| R-ERR-2 | 失敗は利用者が手を打てる場所まで届ける | 誰が読むかを言える。読み手が0なら届いていない               | —                                      |
| R-ERR-3 | 失敗には復帰の口を用意する             | 再試行、別の操作、再起動のどれかが画面にある                | —                                      |
| R-ERR-4 | 呼び手が分岐する失敗は型で区別する     | 文字列を読んで分岐しない                                    | —                                      |
| R-ERR-5 | 待ちには上限を持たせる                 | 外部プロセス、IO、応答待ちに上限がある                      | —                                      |
| R-ERR-6 | 部分的に失敗した状態を残さない         | 書き込みは一時ファイルと rename。途中で止まっても元に戻せる | —                                      |
