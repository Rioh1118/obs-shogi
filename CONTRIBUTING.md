# Contributing to ObsShogi

ObsShogi に興味を持っていただきありがとうございます。

ObsShogi は、**定跡・序盤研究のワークフローに特化した将棋 GUI アプリ**です。  
局面検索、棋譜の切り替え、分岐の移動、USI エンジンによる検討を、研究の流れを止めずに行えることを目指しています。

このプロジェクトでは、Issue / Pull Request の両方を歓迎します。

---

## まず知っておいてほしいこと

ObsShogi はまだ発展途中のプロジェクトです。  
特に、開発者は **将棋AI・研究実務の現場でのユースケースをまだ十分に把握しきれていません**。

そのため、以下のような報告はとても助かります。

- 実際の研究で困ったこと
- 欲しい機能
- UI / UX 上のつまずき
- 棋譜管理や局面検索のワークフロー上の不満
- 不具合や再現手順
- USI エンジン連携で困るケース
- 将棋AI用途として不足している導線

「この機能がないと研究で使いにくい」
「こういうユースケースがある」
「この局面検索の仕様だと困る」

といった Issue は特に歓迎します。

---

## 参加方法

### 1. Issue を立てる

以下のような内容は、まず Issue で共有していただけるとうれしいです。

- バグ報告
- 機能提案
- 仕様の相談
- 研究用途・AI用途での要望
- ドキュメント改善案

Issue では、できるだけ具体的に書いていただけると助かります。

例:

- 何をしようとしたか
- 何が起きたか
- 本来どうなってほしかったか
- どの OS か
- 使っているエンジン
- 再現手順
- スクリーンショットやログ

### 2. Pull Request を送る

コードによる改善も歓迎します。

- バグ修正
- UI 改善
- ドキュメント改善
- テスト追加
- 開発体験の改善
- 将棋研究ワークフローに沿った機能追加

大きめの変更は、先に Issue で相談してもらえると助かります。  
方向性のずれを減らし、レビューもしやすくなります。

## 歓迎するコントリビューション

特に歓迎するもの:

- バグ修正
- 再現性のある不具合報告
- 研究ワークフローに基づく機能提案
- 将棋AI・USI エンジン利用者の観点からの改善提案
- キーボード操作・UI/UX 改善
- セットアップ手順や README の改善
- テストの追加
- エラーメッセージ改善

## Issue を立てる前に

ただし、完全に同じか判断しづらい場合は、遠慮なく立てて大丈夫です。

## コメントの書き方

前提として、**このコードを読むのは、その変更を書いた人ではありません。**
数ヶ月後の自分か、事情をまったく知らない他人です。

### 言語

日本語で書いてください。

### 書くもの / 書かないもの

- 書くのは **なぜそうなっているか**。何をしているかはコードが語ります
- 名前で表せるものはコメントにしません。コメントが要ると感じたら、まず名前と関数の分割を疑ってください
- 自明なことは書きません（`i += 1; // i を1増やす`）
- 逆に、**次のものは必ず書いてください**。コードからは読み取れないからです
  - 外部仕様による制約（USI プロトコル、KIF/CSA の仕様、Tauri の制限）
  - 順序への依存（「この初期化はエンジン起動より前でなければならない」）
  - 意図して選んだ値（なぜこの閾値なのか、なぜこのタイムアウトなのか）
  - ワークアラウンドと、それが必要になる条件
  - 素直でない書き方をした理由（性能、ライブラリの都合）

### 変更の経緯を書かない

- 「今回の修正で」「〜に変更した」「PR #123 で対応」は書きません
- 「元は〜だった」も書きません。消したコードの説明は履歴の仕事です
- 経緯は `git log` と PR に残ります。コードには**いま何がどうあるべきか**だけを書いてください

> AI 支援で書かれたコードでは、この違反が特に出やすいです。
> 修正作業の文脈がそのままコメントに残ることがあるので、`npm run test` の `commentHistory` が機械で止めます。

### 置き場所

- 関数の頭に置きます。何をするか / 前提 / 不変条件 / 呼び出し側が守るべきこと
- **関数本文の中に説明コメントが何行も必要になったら、関数を分ける合図です**
- 行末コメントは短い補足だけにしてください

### 嘘をつかない

コードを変えたらコメントも変えてください。**腐ったコメントは、無いより悪いです。**
コメントとコードが食い違っていたら、それはバグとして扱ってください。

### TODO / FIXME

issue 番号を必ず伴わせてください。

```
// TODO(#123): 分岐が 100 を超えると線形探索が効かなくなる
```

番号を付けられないものは TODO ではなく願望なので、書かないでください。

### 公開 API

- **Rust**: 公開する関数・型・モジュールに `///` を付けてください。`cargo doc` で読める形にします。
  panic する条件、エラーの意味、呼び出し順の制約を明記してください
- **TypeScript**: 外部から使われる関数・型に TSDoc を付けてください

### 量

コメントがコードより多いファイルは、たいてい設計に問題があります。
説明が必要な状態を、説明で埋めないでください。

## SCSS の書き方

根拠は [ADR-0003](docs/decisions/0003-scss-scale-tokens.md)。

### 寸法はトークンから選ぶ

文字サイズ・間隔・角丸・影・モーション・等幅フォント（`$font-mono`）は
`src/index.scss` のトークンを使ってください。`@use "@/index.scss" as index;` で読み込みます。

```scss
// こう
font-size: index.$font-hint;
gap: index.$space-4;
border-radius: index.$radius-4;

// これは通りません
font-size: 1.15rem;
gap: 0.75rem;
```

**文字サイズはサイズではなく用途で選んでください。** `$font-hint`（注記）・`$font-aux`（説明文）・
`$font-body`（本文）のように役割で名前が付いています。近い大きさだからという理由で選ぶと、
段の中で値が再び割れます。

`body` に `$font-body` が入っているので、本文サイズなら `font-size` を書く必要はありません。

### 直値は増やせません

`src/__tests__/scssScaleRatchet.test.ts` が `src/**/*.scss` を走査し、
**スケールに載るプロパティ**の直値を数えます（`font-size` / `border-radius` /
余白 / 影 / モーション / フォント。枠の全体は [ADR-0003](docs/decisions/0003-scss-scale-tokens.md) を参照）。
**件数が基準値と一致しないと `npm run test` が落ちます。** 増えたときも減ったときも落ちます。

**枠の外のプロパティは数えません。** `min-height` / `width` / `top` などの直値は
検査を素通りします。緑で通ったことは「規約に沿っている」を意味しません。

既存の直値はまだ大量に残っていて、基準値として許容されています。
直値をトークンへ寄せたら、その分だけ基準値を下げてください。**`exempt` 以外の枠は下げる方向にだけ動かします。**

下げ方は失敗メッセージが教えてくれます。件数が減ると
`減ったなら BASELINE を N に下げること` と出るので、
`src/__tests__/scssScaleRatchet.test.ts` の `BASELINE` をその数に書き換えてください。

寸法をローカル変数・カスタムプロパティ・at-rule のパラメータ（`@include` の引数、
`@mixin` の既定値、`@return`、`@each` のマップ、`@use ... with`）へ移しても数えます。
プロパティ名から離しても逃げ道にはなりません。

スケールに載らない寸法（盤の中の文字など）は、その宣言の行末に `// scale-exempt` を付けると
`exempt` の枠へ移ります。**印は必ずその宣言の場所に書いてください。** `@include` の引数にも効きます。

**枠が移るだけで数は消えません。** 印を1つ足すと元の枠が1減り `exempt` が1増えるので、
**`BASELINE` の2行を同時に動かす**ことになります。`exempt` だけは上がる方向にも動きます。

なお、この検査が見るのは `.scss` だけです。`.tsx` の `style={{ fontSize: "1.3rem" }}` は
対象外なので、インライン style で寸法を書かないでください。

### 意味色

失敗や注意を表す色は `src/index.scss` の4つから選びます。**新しく発明しないでください。**

| トークン         | 段             | いつ使うか                                     |
| ---------------- | -------------- | ---------------------------------------------- |
| `$color-info`    | 伝えるだけ     | 利用者は何もしなくてよい                       |
| `$color-warning` | 再試行で直る   | 同じ操作をもう一度で直る見込みがある           |
| `$color-danger`  | 別の操作が要る | 繰り返しでは直らない。危険な操作の確認にも使う |
| `$color-fatal`   | アプリ再起動   | アプリの中では直せない                         |

**軸は「復帰に何が要るか」で、深刻度ではありません。** 見た目の派手さで選ばないでください。
根拠は [ADR-0004](docs/decisions/0004-notification-taxonomy.md)。

`success` は置いていません。成功を通知する場面が現物に1件も無いためです。必要になったら足します。

**面と文字で使うトークンは分かれています。**

| 用途                   | トークン                                      |
| ---------------------- | --------------------------------------------- |
| 枠・薄い面・アイコン   | `$color-warning` / `$color-danger` ほか意味色 |
| 押せる面（確認の実行） | `$color-danger-solid` / `-hover`              |
| 暗い面の上に置く文字   | `$color-danger-text`                          |
| 失敗を伝える箱の面     | `$surface-warning` / `$surface-danger`        |

失敗の箱を新しく作るときは `$surface-*` を使ってください。
`color-mix(...)` を手で書くと、同じ式が複数のファイルに散ります。

危険な操作の色は、まだ全部が寄り切っていません
（[#180](https://github.com/Rioh1118/obs-shogi/issues/180)）。

| 場所                   | いまの値                                          | 状態                                                                                                                                                                         |
| ---------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IconButton`           | `#dc3545` を CSS 変数の既定値として直書き         | 自前の値のまま                                                                                                                                                               |
| `KifuForkActions`      | `rgba(215, 96, 96, …)` / `rgba(235, 160, 160, …)` | 自前の値のまま                                                                                                                                                               |
| `KifuMoveActions`      | 同上                                              | 自前の値のまま                                                                                                                                                               |
| `ContextMenu --danger` | `$color-secondary-dark`（アクセントの銅）         | トークンだが**危険色ではない**。比の話は [#185](https://github.com/Rioh1118/obs-shogi/issues/185)、意味の取り違えは [#180](https://github.com/Rioh1118/obs-shogi/issues/180) |
| `FileConflictDialog`   | `$color-danger-text`                              | 寄せ済み                                                                                                                                                                     |

### 機械で止めているもの

人の注意では止まらなかったものを検査として置いてあります。

**「何を見ているか」と「どこで走るか」は別です。** `（Rust）` の付いた行は
`src-tauri/tests/` に置いた `#[test]` で、`npm run verify:rust` で走ります。
それ以外は vitest で、`npm run verify` で走ります。ただし**vitest の検査の
いくつかは `src-tauri/**`と`docs/**` も歩きます**（コメントの経緯、表の識別子、
表が指すパス）。`.rs` や `docs/` だけを触ったコミットでもそれらが走るよう、
`.claude/hooks/verify-gate.sh` は種類で二分せずに選びます
（何を選ぶかは `verify-gate.test.sh` が固定しています）。

落ちたときの逃げ道はそれぞれ違います。

走査の対象と起点は `src/__tests__/walk.ts` が1箇所で決めます。ファイルの中身を
読む走査で `readdirSync` を書かないでください（除外を足すとき直す場所が散り、
1つ直し忘れても違反が減るだけなので緑のまま通ります）。

例外はディレクトリ名そのものを数える場合（`sliceBarrels` がスライスを、
`testsLayerBoundary` がレイヤを、`stateTransitionIndex` が表を数えます）。
起点（`REPO_ROOT` / `SRC` / `RUST_SRC`）はその場合も `walk.ts` から引きます。

Rust のテストの置き場は2つに分かれます。crate の内部（private / `pub(crate)`）を
見るものは `src` の `#[cfg(test)]`。crate の公開面か、ソースを文字列として読む
リポジトリ横断の検査は `src-tauri/tests/`。

### 並行作業の worktree

置き場は `.claude/worktrees/<slug>`（`.gitignore` 済み）。

```bash
git worktree add .claude/worktrees/<slug> -b issue-<番号>/<slug> main
npm ci   # worktree ごとに要る
```

終わったら `git worktree remove .claude/worktrees/<slug>`。
Rust のビルドキャッシュは共有されません。

### まだ決まっていないもの

命名（ブロック / エレメント / モディファイア）の規則は未決です。
`@use` は上の1通りに揃えてください（別の書き方が残っていますが、新規は合わせてください）。
機械で落とせるかは [#160](https://github.com/Rioh1118/obs-shogi/issues/160) で調べます。

## Pull Request のガイドライン

PR には、できるだけ以下を書いてください。

- 何を変更したか
- なぜ変更したか
- どの Issue に対応するか
- 影響範囲

### ブランチの切り方

**`main` から切って、`main` に出してください。**

```bash
git switch main && git pull
git switch -c issue-123/short-description
```

- ブランチ名は `issue-<番号>/<説明>`
- 未マージの他のブランチから切らないでください。PR の差分に無関係な変更が混ざります
- 他の PR の成果に依存する作業は、その PR がマージされてから始めてください

詳しい理由は [ADR-0001](./docs/decisions/0001-branch-and-pr-policy.md) にあります。

### 検証を通してから出してください

```bash
npm run verify        # TypeScript / SCSS / docs / CONTRIBUTING.md を触った場合
npm run verify:rust   # Rust を触った場合
```

**Rust を触ったときは両方が要ります。** コメントの経緯と、表が指す識別子・パスを
見ている検査は vitest 側にあって、`src-tauri/**` を歩いているからです。

Rust のツールチェーンは `rust-toolchain.toml` で固定しています。手元と CI で同じ結果になります。

**通していない場合は、PR にその旨を書いてください。** 通したふりをされる方が困ります。
未検証の PR は歓迎します。

### 小さく分けていただけると助かります

大きすぎる PR はレビューが難しくなるため、可能なら小さく分けてください。

### 設計方針について

ObsShogi は「研究のやりやすさ」を大事にしています。

- 研究の流れを止めないか
- キーボード中心の操作に合っているか
- 棋譜管理・局面検索・分岐移動と自然につながるか
- 将来的な拡張に無理がないか

を重視してレビューします。

---

## レビューについて

Pull Request は歓迎します。
メンテナが内容を確認し、**できるだけ積極的にレビュー**します。

ただし、以下の理由でそのまま取り込めないことがあります。

- プロジェクトの方向性とずれる
- UI / UX の一貫性を損なう
- 保守コストが高い
- 仕様の整理が不足している
- 先に Issue で議論したい

却下されることがあっても、提案自体はとてもありがたいです。

---

## Discussion / Issue の使い分け

- **Issue**: バグ、機能要望、作業として追いたいもの
- **Discussions**: アイデア相談、使い方、研究ワークフローの相談、雑談寄りの話題

迷ったら Issue でも大丈夫です。

---

## コミュニケーション

建設的で丁寧なやり取りをお願いします。
強い断定や攻撃的な言い方よりも、

- どう困っているか
- どう使いたいか
- どのような文脈で必要か

を書いてもらえると、より良い改善につながります。

## 最後に

ObsShogi は、既存の将棋 GUI と競争するというより、
**研究・序盤研究のワークフローをより良くする**ことを目指して育てているプロジェクトです。

将棋を研究する方、将棋AIを使う方、GUI を改善したいエンジニアの方、
Issue / Pull Request / Discussion いずれも歓迎します。
