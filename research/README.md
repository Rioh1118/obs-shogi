# research — 方針判断のための調査ループ

`docs/PREMISES.md` の未確認前提を、**公開一次情報で潰す**ための作業場。
手順は `~/osint`（OSINT CTF 環境）の osint-core から移植した。あちらで実測済みの負け方を、こちらで繰り返さないため。

**この場所の成果物は「調査メモ」ではない。`docs/PREMISES.md` の状態を書き換える権限を持つ証拠である。**

---

## なぜこの型なのか

将棋界隈は小さく、需要の直接観測ができない。だから「正確に知る」は目標にしない。
代わりに **何を仮定していて、それが何で覆るか** を管理する。osint-core が測った3つの負け方は、そのままこのプロジェクトの負け方でもある。

| 負け方                       | obs-shogi での実例                                                               | 対策           |
| ---------------------------- | -------------------------------------------------------------------------------- | -------------- |
| 未検証の前提の上に積む       | P-001「横断検索は ShogiHome が持てない領域」が誤りと判明するまで30日以上         | 前提レジスタ   |
| 見落とし                     | 注釈機能が2実装に分裂したまま数ヶ月、issue にも無かった                          | 全数精査を先に |
| 時期尚早な「詰み」「決まり」 | 定跡11件を「やる」と決めたまま、ShogiHome が既に解決済みかを一度も確認していない | 詰み宣言の要件 |

## 証拠の等級（例外なし）

| 等級       | 意味                                                       |
| ---------- | ---------------------------------------------------------- |
| `[確定]`   | 一次情報で裏取り済み。ソース・公式リリース・公表資料の原典 |
| `[推定]`   | 状況証拠のみ。**何をもって推定したかを併記する**           |
| `[未確認]` | 未検証の仮説                                               |

- **検索エンジンの要約・AI要約を事実として扱わない。** 必ず原典を開く。要約器はバージョン番号・日付・桁を落とす。
- GitHub を根拠にするときは**ファイルパス＋行番号**、またはリリースタグの URL。
- 消えそうなページは Wayback URL も併記する。
- **推測で数値を埋めない。** 埋めた数字は次の週には「実測」として扱われ、判断を汚染する。

## 調査の規律（`~/osint/CLAUDE.md` から移植）

1. **受動的な公開情報の閲覧のみ。** issue へのコメント、DM、問い合わせフォーム、アカウント作成、フォロー、star — 調査対象への**能動的接触は一切しない**。
   - これは `docs/PREMISES.md` P-004 の「#236 のコメント主に直接あたる」を**明示的に取り消す**。代わりに公開された発言の集計で測る。
2. **出典のない主張を結論に使わない。**
3. **サブエージェントの報告は仮説として受け取る。** 検証の結論として引用しない。`[確定]` として採用する出典は、こちらで再確認したものだけ（osint P-0020: エージェントの grep ヒット0を根拠に書いたら実際は2件あった）。
4. **エージェントの「失敗」通知は成果物の不在を意味しない。** まず `ls` と末尾を見る（osint P-0021: 5本中4本は書き終えた後に落ちていた）。

## ループの1周

**周期は週1回、`docs/OPERATING-MODEL.md` の週次レビューに乗せる。** コミット毎ではない。

1. **レーンを選ぶ** — `ROSTER.md` の未閉レーンから。決定への効き目が大きい順
2. **収集** — 軸ごとに並列エージェント。成果物は**返り値でなく `findings/` のファイル**に書かせる
3. **再確認** — 結論に使う出典を**自分の目で開く**。ここを飛ばすと 3. の規律が死ぬ
4. **notes 更新** — `lanes/<ID>.md` の前提レジスタと仮説の状態を書き換える
5. **前提の書き換え** — `docs/PREMISES.md` の状態（✅/⚠️/❌）と確認日を更新。**覆ったら依存する決定を直すまでがワンセット**
6. **決定を1件だけ** — `docs/OPEN-QUESTIONS.md` の最上位を1つ ADR 化。**2件目に手を出さない**
7. **タスク化** — 決定から出た作業を issue へ。6週間以内に着手しないものは `docs/IDEAS.md` へ1行

### 軸チェックリスト（詰まったとき）

**手を10個試しても軸が1本なら進捗はゼロ。** 張っていない軸を探す。

| 軸           | 具体的に                                                           |
| ------------ | ------------------------------------------------------------------ |
| 言語         | 日本語 / 英語 / 中国語。将棋の話題は日本語に偏るが、設計論は英語側 |
| 時間         | Wayback / 直近2年に新しく出たもの / 更新が止まった年               |
| 隣接ドメイン | **チェス側**。同じ問題を先に解いている（合流・注釈・定跡管理）     |
| 配布経路     | GitHub / npm / crates.io / PyPI / Vector / ストア                  |
| 一次仕様     | フォーマット仕様書の原文。「できない」は仕様で確認する             |
| 実数         | Releases の download_count、API のレスポンス。**検索でなく計測**   |
| 反証         | 支持証拠と**同じ熱量**で反証を探したか                             |

## 「結論」を書く前の要件

次を全部満たさない限り、`docs/PREMISES.md` を ✅ にも ❌ にもしない。

- [ ] 結論に使った出典を**自分で開いた**（エージェントの報告のままでない）
- [ ] 軸チェックリストのうち、張っていない軸が無い
- [ ] 「無い / 存在しない」と言うなら、**試した検索語を全部列挙した**（検出力の記録が無い不在証明は採用しない）
- [ ] 反証側の証拠を探した
- [ ] **失効条件**を書いた（何が起きたらこの結論は覆るか）

満たせないなら、前提の状態は変えず「この軸は閉じた。次はこの軸」と `lanes/<ID>.md` に書く。

## 置き場

| パス         | 内容                                                         |
| ------------ | ------------------------------------------------------------ |
| `ROSTER.md`  | レーン一覧と状態。**ループの入口**                           |
| `lanes/`     | 1前提1ファイル。前提レジスタ・仮説・試した検索語・結論       |
| `findings/`  | エージェントの生成果物。**加工前の証拠**。ここは書き換えない |
| `knowledge/` | 再利用可能になった知見のカード（1ファイル1事実）             |

`findings/` は追記しない・上書きしない。次の周では新しいファイル名で足す。
**矛盾の累積が最大の失敗モード**なので、確定した結論は `lanes/` 側に一本化する。
